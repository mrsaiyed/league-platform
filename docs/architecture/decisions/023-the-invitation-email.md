# 023 — The invitation email: templates, the link's address, and what waits

Date: 2026-11-13. Step 1.19 part 2 and its review; carries out T-226 (record 014) and T-131; decides T-235. Decided by the lead (technical).

## What

- **Templates are plain TypeScript for now.** T1 and T7 §6 say templates are React Email components. The repository has no React toolchain yet (the web app's arrives with step 1.17), and a template is a small piece of HTML. So `packages/emails` holds plain TypeScript functions that take the data and the words (from the message files, T-187) and return a subject, HTML text and a plain-text version, with every value escaped (`escapeHtml`). The first template, the invitation email, carries no league logo or colors yet. When React is in, templates may move to React Email; their callers do not change, since each still returns `RenderedEmail`. T1 and T7 §6 are reworded to say this.
- **Header text cannot break a line or name a second address.** `fromHeader` puts the league's name before our sending address. The name is the league's own words, so every control character (C0, DEL and C1: `\r`, `\n`, `\t`, `\v`, `\f`, NUL, U+0085), U+2028 and U+2029 become a space, `<`, `>` and `@` are removed, and quotes and backslashes are escaped. The sending address must be one plain `local@domain`. The subject goes through the same `headerText`.
- **Settings are checked once, at startup.** The worker's site origin is checked with leagueUrl's own check (`checkedSiteOrigin`) and the sending address with `fromHeader`, when the worker is wired and when the handler is made, before anything is opened and before any job runs. A bad setting stops the worker; it never reaches a job.
- **The email is built before the link is committed.** The job reads the league, makes the new link (`issueInvitationLink`), builds the address and the whole email, all in one transaction, and commits; only then is the email handed to the email service (record 014's order). A mistake in building it (a league row the address helper refuses, say) rolls the new link back, so the link the person already has keeps working, and fails the job at once (`EmailNotBuiltError`: kept as `unexpected`, not retried), since trying again would build the same email. A bad setting or row can therefore never replace a working link five times.
- **The idempotency key is per link.** Each run of the job makes a new link, so each run's email is a different email, and its key (`invitation-{invitationId}-{part of the SHA-256 of the link}`) is different too: the service never drops the second email as a repeat of the first, and one send of one link is never delivered twice (T-137). The key reveals nothing of the link (a one-way hash of a 256-bit random secret). It follows, and is accepted as record 014 accepted a second run: a retry after the service's answer was lost or unreadable (`unavailable`, `unexpected-answer`), when the service may in fact have accepted the first, sends a second email whose link ends the first. The person uses the newer email. A key that stays the same across runs would need the link to stay the same too, which would mean storing it in a form we can read back; T-226 keeps only its hash, so the key stays per link.
- **The link stays in the address path:** `/{league}/invitation/{token}` (P2 §4, T-226). A link in an email has to carry its secret somewhere in the address; a fragment (`#token`) would keep it out of server logs but need the page's script to read it before anything works, and the query string is logged as often as the path. What the accept page must do instead (steps 1.14 and 1.17):
  - answer with `Referrer-Policy: no-referrer`, so the link never leaves in a Referer header;
  - answer with `Cache-Control: no-store`, so no browser, proxy or Cloudflare cache keeps it;
  - leave the path out of our request logs and out of any analytics: the request is logged as `/{league}/invitation/[link]`, never with the token.
- **`invitation` is a name the site uses.** Since the page sits directly under the league, a program or custom page cannot be called `invitation` (P2 §5); `leagueSiteNames` already holds it, because it is read from the list of pages.

## Not done yet, and where it goes

- **A recorded delivery row and its outcome** (T7 §2 "records the outcome", T7 §5, T-137): needs the deliveries table. Until then the invitation email's duplicate protection is the email service's, per link, and the job row's own state.
- **Replies to the league's contact address** (T7 §6): the league has no contact address field yet. The email goes with no Reply-To.
- **The `email_suppressions` check** (T7 §6, N-10): needs the table and `email.status`. Until then an invitation is sent even to an address that bounced.
- **The league's language.** The email is in English; it takes the league's language when leagues have one.
- **The worker's config file** (`apps/worker/src/config.ts`): reads the worker's settings from the environment, reusing the web app's names, `PUBLIC_BASE_URL` for the site origin and `EMAIL_FROM` for the sending address, and checks them as above.
- **Starting the queue with the handlers.** `wireWorker` returns the handlers; the worker's entry point passes them to `queue.start` when it exists.
- **An end-to-end test on PGlite** (invite, the job in the jobs table, the worker running it, accepting with the emailed link) waits for step 1.21's seed. Today the same path is tested on the in-memory stand-in with the real commands, the real address helper, the real template and words, and the capture adapter.
