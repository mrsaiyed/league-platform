Date: 2026-11-17. Step 2.98 (T-285). Serves T4 §3, §5, §6 and §12, T-79, record 031. Decided by the builder of step 2.98 for the lead (technical), to be confirmed when the step lands.

## Scripts only from us, and HTTPS always (T-79)

**The script policy** (`apps/web/src/server/security-headers.ts`): a script runs only when it comes from our own address or carries the nonce made for that one answer: `script-src 'self' 'nonce-…'`, with `object-src 'none'` (no plugins), `base-uri 'none'` (no `<base>` that would send our own scripts' addresses elsewhere), `frame-src 'none'` and `frame-ancestors 'none'` (record 020's "no other site may frame us", kept). No `'unsafe-inline'`, no `'unsafe-eval'`, no `'strict-dynamic'` and no wildcard. So a script that reaches a page any other way (an inline `<script>`, an `onclick=`, a `javascript:` address or a script from another site, as injected text would try) does not run, and the browser reports it (`tests/browser/script-policy-test.mjs` tries all of them).

**The nonce** is 18 random bytes made by the proxy (`src/proxy.ts`) for every request it handles, which is every page, API answer, form answer, refusal, error page and redirect, and the live feed. The proxy writes the policy into the answer, and Next.js puts the nonce on every script it draws (its own files and its inline page data); the bot check's Turnstile script takes it the same way (`nonceOf`). The nonce stamped is always the answer's: Next.js 16.4.6 copies every header the proxy puts on its answer into the request as well, after the request's own (`node_modules/next/dist/server/lib/router-utils/resolve-routes.js`: `if (value) { resHeaders[key] = value; req.headers[key] = value; }`), so the request the page is drawn from carries the answer's `content-security-policy`. The proxy also writes the policy into the request, replacing any the browser sent; that is not what makes it work, but it is harmless and kept as a guard should the framework change. Tried on 2026-11-22: a wrong nonce written into the request's policy alone changes nothing, and `script-policy-test` passes (as it should); a nonce the browser enforces that differs from the one stamped, or a nonce in the header with none stamped, fails `script-policy-test` on all 18 pages in under 2 minutes. A nonce the browser chose is used for nothing (`check-web-shell.mjs`). What the proxy never sees (the built script files, the two stylesheets, the icon, Next.js's own early answers) gets the fixed policy from `next.config.ts`, the same words with no nonce, so nothing inline could run there. **One exception, and why it is harmless:** an address the framework cannot even decode, such as `/%ff` (a broken percent sign), is answered by Next.js itself before the proxy or `next.config.ts`'s headers are reached: a `500` in plain text with none of the headers (no policy, no `Strict-Transport-Security`, no `nosniff`). It was the same before this step. Its body is the framework's own fixed words with nothing of the request in it, and it is plain text, not a page, so there is nothing in it a script could use or a browser could run; a browser that has once had `Strict-Transport-Security` from any other answer keeps to it. In staging and production the bot check's one origin, `https://challenges.cloudflare.com`, is added to `script-src` and `frame-src`, taken from the widget the pages draw, so the two cannot drift. `next dev` alone adds `'unsafe-eval'`, which React needs there for its error stacks; a built server never does.

**Why a nonce and not the alternatives.** `'unsafe-inline'` (Next.js's way without a nonce) would let any injected inline script run: the policy would forbid only other sites' files. Hashes cannot work: Next.js's inline scripts hold each page's own data. Next.js's experimental `sri` covers files, not the inline data. A nonce needs every page drawn per request, which they all are today (every route is dynamic in the build). **Step 2.176 (pages kept by a cache again): nothing can be built ahead under a nonce policy.** A page built ahead, at build time, has no nonce at all: the framework's own guide says so (`node_modules/next/dist/docs/01-app/02-guides/content-security-policy.md`, line 181: "To use a nonce, your page must be **dynamically rendered** … Static pages are generated at build time, when no request or response headers exist—so no nonce can be injected"; and line 391: "When you use nonces in your CSP, **all pages must be dynamically rendered**", with "Static optimization and Incremental Static Regeneration (ISR) are disabled" just below). Its inline `self.__next_f` scripts would be refused and React would never run on it. The framework's own page cache is no way out either: it would pair a new nonce from the proxy with old HTML. So a page is kept only by a cache that stores its policy header together with its body (Cloudflare's does), for a short time: the kept page and the policy that names its nonce travel together. The reviewer measured that this step undoes nothing that works today: before (merge-base 81c83c0) and after, the home, schedule, team and game pages answer the same `Cache-Control: private, no-cache, no-store, max-age=0, must-revalidate` (since 2.127), all 60 routes are rendered on every request in both builds, and the time to the first byte (median of 20 runs, two runs each) moved from 12.9/11.6 to 15.0/11.6 ms (home), 12.3/10.9 to 11.1/10.7 (schedule), 7.7/7.8 to 8.2/8.2 (team) and 6.9/6.5 to 7.8/7.8 (game). The lead has rewritten step 2.176's line in the plan to match; its done test must load a kept page in a browser with the policy on.

**Zod and `eval`.** Zod, which reads the live game's messages and the tracker's answers in the browser, asks once whether it may build its checks with `new Function`; refused, it checks without it, with the same answers. `apps/web/src/instrumentation-client.ts` (Next.js runs it in the browser before any app code) tells it not to ask (`jitless`), so the browser reports no refusal on every page and the policy's reports stay for real attacks.

**Left for later steps, on purpose:** `style-src` (our pages draw the league's design as inline styles, step 1.18), `img-src`, `font-src` and `connect-src` (the live service's address differs per environment), `form-action` (the no-script Google sign-in posts to our own server action, which sends the browser on to the sign-in service and Google; Chrome checks `form-action` on each of those hops, which cannot be checked on this computer), and a `report-to` address (a place for reports is an outside service). The embeds of C-9 are added, each origin by name, with the step that builds them. T-79 asks for scripts and frames; those are done.

**HTTPS always:** `Strict-Transport-Security: max-age=31536000; includeSubDomains` on every answer, from `next.config.ts` (the static files and redirects too; not the framework's early answer to an address it cannot decode, above). A browser keeps to it only once it has had it over HTTPS, so on this computer's plain http it is ignored and nothing local changes. A year, as browsers' own guidance asks before the preload list; `includeSubDomains` because everything of ours is HTTPS, the league subdomains of U-13 included. **Not** `preload`: putting the founder's domain on the browsers' built-in list is a commitment that takes months to undo, and it is the founder's to make once the domain is settled. If any address under the domain will ever be plain http (an old site, an email service's tracking address), that must be known before the first HTTPS answer is sent; the founder's supervised session checks it.

## Which visitor a request came from, behind Cloudflare (`TRUSTED_PROXY=cloudflare`)

**The problem.** The attempt limits of T-225 count wrong guesses per network as well as per address. The network is read from the request (`networkAddressOf`, `apps/web/src/server/sign-in/device.ts`), and record 031 gave two choices: `none` (nobody's word is taken; every visitor shares one key, so one person's guesses lock out everyone) and `one` (exactly one proxy of the host appends the address it was reached from, and that last entry of `X-Forwarded-For` is believed). T1 puts Cloudflare in front of Render. Then Render's proxy is reached by Cloudflare's servers, not by visitors, and with `one` every visitor is keyed by whichever Cloudflare server passed them on: thousands of people would share a handful of keys, and 100 wrong guesses from any of them would lock every one of them out for 15 minutes.

**The choice: a third value, `cloudflare`.** Cloudflare names the visitor's address in a header of its own, `CF-Connecting-IP`, which it sets itself on every request it passes on, replacing whatever the visitor sent. But the host can also be reached without Cloudflare, at its own address (on Render, `*.onrender.com`), and there anyone can send `CF-Connecting-IP` with any value: believed blindly, it would let a guesser start a fresh count with every try. So the header is believed only when the request came through Cloudflare, and the app knows that from the one entry nobody but the host writes: the last entry of `X-Forwarded-For`, appended by the host's proxy (the same entry `one` believes). When that address is one of Cloudflare's published addresses (`isCloudflareAddress`, `packages/providers/src/cloudflare`), the visitor is `CF-Connecting-IP`. When it is not, the request reached the host some other way: `CF-Connecting-IP` is refused as a spoof, and the request is keyed by the host's entry, the address that really reached the host, as `one` would. A request through Cloudflare whose `CF-Connecting-IP` is missing or is not exactly one address shares the unknown key (`0.0.0.0`): it fails closed, as `none` does.

What it guarantees: a visitor can change neither key by anything they send. Through Cloudflare, Cloudflare writes the header; around Cloudflare, the header is not read and the host writes the entry that is. A new cookie, another browser or another value of the header leaves the count where it was (`flows.test.ts`, "the network behind Cloudflare"). An address missing from our copy of Cloudflare's list only makes the visitors behind that Cloudflare server share one key: it never lets anyone choose their address.

Cloudflare's list (`cloudflareIpv4Ranges`, `cloudflareIpv6Ranges`) is copied by hand from `https://www.cloudflare.com/ips-v4` and `https://www.cloudflare.com/ips-v6`; nothing fetches it. The comparison uses Node's own `BlockList`, no vendor library. On made-up data (local work and tests), a request carrying `CF-Connecting-IP` is one passed on by another server and is answered with the plain "not answered here" page (`this-computer.ts`, step 2.152).

**Not chosen:** believing `CF-Connecting-IP` whenever it is present (anyone reaching the host directly picks their own key); refusing here every request not from Cloudflare (which requests reach the app at all is the host's setting, point 5 below, not the attempt limits'); fetching Cloudflare's list at start-up (a start that depends on a vendor's page, and nothing to check it against).

**Checked on the real host, in the founder's supervised session, before `TRUSTED_PROXY=cloudflare` is set** (none of it can be checked on this computer):

1. Compare `cloudflare-addresses.ts` with the two published lists, the day it is set.
2. Render's proxy appends the address it was reached from as the last entry of `X-Forwarded-For` (record 031 assumes it for `one`). Through Cloudflare that entry must be a Cloudflare address; straight to the `onrender.com` address it must be the sender's own.
3. A request sent straight to the `onrender.com` address with a made-up `CF-Connecting-IP` is keyed by the sender, and one through Cloudflare by the visitor: watch the per-network wait come for one and not the other.
4. Cloudflare's "Pseudo IPv4" stays off (it rewrites the visitor's address headers). If Render's own edge is itself on Cloudflare, the last entry could be a Cloudflare server for every request, also one sent straight to the `onrender.com` address; then point 3 fails and `cloudflare` is not set until the host's entry tells the two apart (Cloudflare's "authenticated origin pulls" is one way).
5. Whether to refuse requests that do not come through Cloudflare at all (Render's settings, or authenticated origin pulls) is decided there, with the health check in mind.

**Keeping the list right after that** (the 2.98 review, C6). A range Cloudflare adds that the list lacks would not let anyone choose their own address, but every visitor through it would share one key, and 100 wrong guesses from any of them would lock all of them out. So the server writes one line of fixed words, with no address in it (`outsideCloudflareRangesLine`, `apps/web/src/server/sign-in/device.ts`), whenever `CF-Connecting-IP` arrives on a request whose last forwarded entry is not in the list: exactly the sign of a missing range (a spoof straight to the host's address looks the same, so one now and then is expected; many a day, from ordinary visitors, is not). The list is compared with the two published lists, by hand, by the lead: the day `TRUSTED_PROXY=cloudflare` is set; then once a month, on the first working day; whenever Cloudflare announces a change to its ranges (it says so in advance); and the same day the host's log shows that line more than a few times. A difference is a one-line change to `cloudflare-addresses.ts` with its test; nothing fetches the list, so nothing changes it unseen.

## The bot check in front of sign-in and sign-up (T4 §6)

**The interface** (`packages/providers/src/bot-check`): a `BotCheck` has a `widget`, what a page draws inside its form, and `verify`, which takes what the widget answered, and the form it was for (`sign-in`, `sign-up` or `reset`), never the visitor's address, and says passed or refused with a fixed word: `missing`, `failed`, `did-not-load` (the person's browser could not load the check), `unreachable` (our server could not reach the service) or `unavailable` (our key refused, or an answer we cannot read). It never throws. The web app names no vendor: its ports carry a `botCheck`, and `botCheckFor` picks the adapter, as `emailSenderFor` picks the email sender: the local stand-in in local work and tests, whatever keys are given, so a test never asks Cloudflare; Cloudflare Turnstile in production, which needs `TURNSTILE_SITE_KEY` and `TURNSTILE_SECRET_KEY` (the settings refuse to start without them). **Staging takes both keys or neither** (the lead, 2026-11-17, for T-270: the first online test copy has no Cloudflare account and holds made-up people only): with both it uses Turnstile; with neither the check is switched off (`createBotCheckOff`: the forms draw no widget and ask for no answer) and start-up says so in one plain line (`botCheckOffLine`); with only one the settings refuse to start, naming the missing one. Tested in `bot-check-for.test.ts`, `config-schema.test.ts`, `startup.test.ts` and, against a real staging start, `check-web-shell.mjs`.

**The local stand-in** draws a hidden field holding the one answer that passes (`LOCAL_BOT_CHECK=stand-in`, the default). `LOCAL_BOT_CHECK=made-up-turnstile` (local work and tests only) draws Turnstile's own box instead, in explicit mode, from an address that cannot exist (`https://bot-check.made-up.invalid`), and passes each `made-up-answer:{form}:{id}` once, for its own form; `tests/browser/bot-check-box-test.mjs` serves a made-up copy of the script there from the test itself, so no request leaves the computer. A person's browser, and every browser test, sends the form as it was drawn and passes; a form posted without the field, or with any other answer, is refused as Turnstile would refuse it. It refuses to be made outside local work and tests. "Be this made-up person" (step 2.96) sends the same answer, as the page would.

**The Turnstile adapter** draws Turnstile's box in explicit mode: a small client part (`features/sign-in/bot-check-box.tsx`) loads the script from `https://challenges.cloudflare.com` once (the page's script policy allows that one origin in staging and production, below), draws the box when its form appears and removes it when the form goes, so a form drawn again after a refusal has a box of its own (before the fix round, implicit mode drew only the boxes present when the script first loaded: a second try sent no answer until a reload). When a form is sent its answer is spent, and the box is asked for a fresh one at once; the form's buttons wait for an answer, only while scripts run. If the person's browser cannot load the check, the box writes the fixed word `did-not-load` into the answer's field: the server then says truly that the check could not load on this connection and names the ways on (try again, another connection, and Continue with Google only on a screen that draws it: step 2.163, M27); the word is refused like any wrong answer, since a bot could send it. Our server asks `POST /turnstile/v0/siteverify` with the secret key and the answer only, and waits at most 4 seconds. An answer passes only when Turnstile says so and says it was made on our own host name for this very form (`hostname` and `action`), so an answer solved on another site, or on the sign-up form and replayed at sign-in, is refused; Turnstile itself refuses one used twice or older than five minutes. No answer in time, no connection, or Turnstile's own fault (`internal-error`, a 5xx) is `unreachable`; our key refused or an answer we cannot read is `unavailable`. Each is reported in one error-level log line of a fixed shape, `bot check not asked` with `kind` only (`no-answer`, `key-refused`, `unexpected-answer`), never with the key, the answer or an address (T-86), so an alarm can be set on it.

**What leaves the person's browser and our server when the check is on** (C8, the lead's decision): the person's browser loads Turnstile's script and frame from Cloudflare, which sees what any site it loads from sees (their address, their browser) and runs its check there; our server sends Cloudflare the answer and our secret key, and nothing else: not the visitor's address (Turnstile's `remoteip` is optional, and we leave it out: `turnstile-bot-check.test.ts` proves the request carries no address), not the email typed. The Terms and Privacy step is to say that the check exists and is Cloudflare's. Written from Turnstile's published API and tested against made-up answers only: not verified against the live service.

**Where it stands** (`flows.ts`): in front of signing in with a password and of asking for a code (sign-up and the forgotten password), before anything else the form does. A refused form goes back to its own screen with its problem ("We could not check that you are a person…") and the place to go after; the sign-in service never hears of it, so nothing is counted, emailed or set in the browser, and the answer is the same whether or not an account exists (T-68). A refused form counts no wrong guess, so the check cannot be used to lock someone out. "Send a new code" on the code screen asks for a code, so it stands behind the same check, with a box of its own, and its refusals are shown on the code screen (`resendCode`). Not in front of: entering the code and the new password (they need a code emailed after a check), "Continue with Google" (Google's own; a plain form that works without scripts, proved in `bot-check-box-test.mjs`), and the password again (a signed-in person, limited per account). A form the check turned back keeps the email typed: the box keeps it in the tab's own storage until the form is drawn again, so nothing is set on our side.

**When the check itself fails (Q2, the lead's decision, 2026-11-17).** When OUR SERVER cannot reach the check's service (`unreachable`: a network failure or a timeout on our side, never a missing or failed answer from the person), password sign-in lets the form through on the attempt limits alone, and the error-level line above says so: a game night must not hang on an outside service. Asking for a code (sign-up, the forgotten password, "Send a new code") stays closed, because it emails any address typed: "We cannot send a code just now, because the check that you are a person is not answering. Please try again in a few minutes." A refused key stays closed at all three. A missing, failed or `did-not-load` answer from the person is refused at all three, whatever the service is doing (`flows.test.ts`). With scripts off, Turnstile cannot run and the three forms are refused; each says so in its own words, and sign-in and sign-up add that Continue with Google works without them where its button is drawn (the lead accepted that sign-in without scripts goes through Google). A refusal reads "We could not check that you are a person. Please wait a moment and try again. If it keeps happening, your browser may be blocking part of this page: allow JavaScript for this site in your browser's settings, or use Continue with Google." (the lead's words, made plain in step 2.163's fix round); on a screen without Google's button (Google not set up, the test copy, the code and forgotten-password screens) it ends "…or try again in a few minutes." instead (M27). It is drawn as a refusal: a warning mark and the danger colour.

**Checked in the founder's supervised session, before real people sign in:** whether the test copy runs with the check off (its start-up line says so; that is safe only while it holds made-up people); a Turnstile widget made in the founder's Cloudflare account for the site's host name (Turnstile's own test keys answer for `example.com`, so they would be refused by the host name check here: the test copy needs a widget of its own); the two keys in the host's secret store; sign-in and sign-up from a phone and a laptop pass; a form posted without the widget is refused.

## Harmful text comes out as text (T4 §12)

React writes every value as text, and nothing in the product takes HTML from anyone (T-78); the places our own code writes markup itself (the league's and the staff screens' style variables, drawn from a checked design whose values are colors and fixed words; the plain "not answered here" page; and the emails, whose values are escaped, `packages/emails`) escape or refuse anything else. `tests/browser/harmful-text-test.mjs` proves it the way an attacker would meet it: an attacker's text (ending a quoted attribute, an element with a handler, a script) is typed through the screens' own forms into every free-text field there is today: a team's name, a person's first and last names, a round's name, a reason to reopen a result, an imported file's name and a venue in it, a name typed at the scorer's table, the email boxes and the numbers' boxes (refused, and drawn back), and the addresses' own questions. Every page that shows them is then opened as a visitor, the owner and the scorekeeper with the browser's script policy switched off, and each shows the text as typed with nothing of it run or made into an element; with the policy on, the browser had nothing to refuse; the raw answer never holds it unescaped. Since the fix round (F3) it also walks every page route, listed from the app's own folders, as six made-up roles (the owner, a scheduler, a coach, the scorekeeper, a signed-in person with no role, a visitor), and fails on a page route, a free-text field or a field kind it does not know, so a new page or field must be added to it. Every field a plain form holds, of every kind (number, date, time, colour and hidden fields, choices and ticks too), is posted the attack by hand, with no typing, and the answer must be a refusal or a harmless page; every route is then opened again in the browser, as each role and with the attack in its questions; every answer route is fetched, and JSON carries the attack only as data, the style sheets never. What it does not cover, and prints by name when it runs: the draft league's own roles (admin, registrar, editor, club admin, a program's scheduler, another league's admin), which hold no role in the league it fills; text a script draws only after a tap, beyond the games list's question, the reopen form and the scorer's table; the scorer's own Reopen question, whose reason is posted to its answer route by hand instead; and the check with the policy on, which runs only on the pages that show typed text (the walk of every route runs with it off, the stronger proof).

## How the attempt limits meet (for the supervised session's list)

Nothing in this step adds a limit. The sign-in service already counts wrong passwords twice (T-225): against the **address typed**, on every network (from 5 wrong in 15 minutes each try waits 30 seconds; at 10 the address is locked for 15 minutes, whichever network the next try comes from), and against the **network** (from 30 each try waits 5 seconds; at 100 the network is locked for 15 minutes, whatever address it tries). A try is refused when either says so. This step changes only what the network is: with `TRUSTED_PROXY=cloudflare` it is each visitor's own address behind Cloudflare, so one person's guesses count against their own network and the addresses they type, never against everyone behind the same Cloudflare server (with `one` behind Cloudflare they would). The bot check counts nothing: a form it refuses never reaches the service, so it adds no wrong guess to the address or the network, and it cannot be used to lock someone out.
