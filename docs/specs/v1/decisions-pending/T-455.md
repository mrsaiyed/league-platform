## T4 — Keeping leagues apart, sign-in, security

| T-455 | A pending change of email lives in the sign-in service behind its interface, not in a table of our own: the service already makes, keeps, limits and spends the codes, and Supabase itself holds a pending address on its user. The interface gains startEmailChange (access token, current password, new address, network address, whether our own records already give the address to another account) and confirmEmailChange (access token, code, network address). Start checks the password as confirmPassword does (the same guesses), then asks a code for the new address under the same limits as any code (per address, per network, 10 minutes, 5 attempts); an address that is taken, in the service or in our records, gets no code and the same answer. Asking again replaces the pending change. Confirm spends one attempt of the account's own pending code (wrong codes count against the network); a right one moves the address, ends every other session and keeps this one; a code spent, expired, used up or asked by another account changes nothing. The stand-in keeps it in memory beside its codes; the Supabase adapter asks Supabase for the code (generate_link email_change_new, our email service sends it), keeps its attempts in its store under the new address as every code (verify type email_change, migration 0031) and confirms with Supabase's verify. Not yet verified against the live service (Supabase's "secure email change" setting must be off: we ask the old address nothing, T-73 only tells it). | Agreed (delegated) | |
