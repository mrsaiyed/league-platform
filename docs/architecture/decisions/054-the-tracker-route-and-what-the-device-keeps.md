# 054 — The tracker's address, the scorekeeper's games and what the device keeps

Date: 2026-11-14. Step 2.33; serves P7 §5.1, P4 §4, P2 §4, T6 §2 and §4, U-6, T-115, T-116. Decided by the lead (technical). T-258.

## Problem

`/{league}/score/{game}` was a placeholder that any account holding `games.score` anywhere in the league could open, for any game, real or not. T6 §2 replaces the Al-Hadi tracker's shared passcode with accounts, P4 §4 gives a scorekeeper a list of their games and nothing else, P7 §5.1 has the scorekeeper confirm the game format, and T-115 stores the game's rosters and state on the device when it is opened. Record 049 built the controller and the state read and left two things to this step: rosters (the state names players by id only) and where on the device the opened game is kept.

## What

- **Who opens the tracker.** Two checks on the server before anything is drawn. The league's (league-gate.ts, unchanged): someone who scores nowhere in the league, a visitor and another league's admin included, gets "you do not have access" (U-6, 403). The game's: the page runs `games.read_tracker_rosters` (below), which runs only for whoever may score this game (`mayScoreGame`, read fresh, T-75), so a scorekeeper in a league that scores assigned games only is refused a game not theirs the same way (403). An address that is not a game id, or a game not in this league (another league's game asked for through this one's address included), is "not found" (404). In a league that is archived or suspended the page says so in the games list's words (`admin.games.notScorable`) instead of "you do not have access", and reads nothing of the game. A game not recorded live (a final score or a box score) is not opened: the page says it is entered in the games area, and nothing goes to the device.
- **`games.read_tracker_rosters`** (`packages/core/src/modules/games/commands/read-tracker-rosters.ts`): the game's home and away team ids and the players of both rosters, names and numbers only (R-16), those who have left marked (R-17), and how the game is recorded (`recording`), in the shape of a command (record 014), `games.score` for that game. It reads the existing `GamesStore.listRoster`, so no new query. A team that shows its players to staff only (S-22) is listed in full, as the state read names them by id. It writes nothing to the activity log, has rows in the role matrix and a case in the two-league harness. There is no HTTP door for it yet: the page reads it on the server and hands the rosters to the device with the page. Team names come from the names the games area shows (`games.namesOf`); they are public.
- **The device keeps the opened game** in a browser database of its own, `srleagues-tracker-games` (`indexeddb-opened-game-storage.ts`), beside the queue's (record 024), so adding it upgraded nothing a tracker already open holds (T-127). One row per game: the league, the signed-in account that opened it, the rosters and when they were stored, the engine's state as the server last gave it, and the format confirmed. It also keeps the device's own id for the scoring session (T-116), made once. A memory version runs the same contract in tests.
- **Players' names do not stay on the device for good.** Opening a game first deletes every other row the device should not keep (`stillKept`): another account's, another league's, a final game's, and one whose rosters were stored more than 14 days ago (`openedGameKeepMs`, long enough for a game opened ahead of the day). Signing out on the device ("Sign out" or "Sign out everywhere" on the account page) clears the store (`forgetOpenedGamesOnDevice`), keeping only the device id: the form waits for the clearing before it is sent, at most 1.5 seconds, so it never holds up signing out. The scorekeeper's games and the tracker both say "On a shared phone or tablet, sign out when you finish" with a link to the account page, as the league's menu offers no sign-out. The tracker clears the store too once the server turns it away as signed out (401), so a session that ran out, or "sign out everywhere" from another device, does not leave the names behind. The queue's taps are not touched: they hold ids, not names, and unsent ones must still reach the server.
- **The state is stored as it is loaded, through the one state read.** `createStoringTrackerServer` wraps the controller's door to the server: each answer of `GET …/state` (opening, after a refusal, after a takeover) is written to the device before the controller sees it. A failure to write does not stop scoring (the taps are in the queue); the page says the device could not save. No second state read was added (record 049).
- **Opening, in order** (`open-tracker-game.ts`): open the device's storage (none, as in some private windows: nothing is opened and the page says why); store the rosters; read or make the device id; make the controller, which takes the session and loads the state. It is opened once per game, league and account: the page drawn again hands the same rosters over as a new object, and that does not let go of the game and take it again. Leaving releases the session: "Leave the game", "Back to your games", the link to sign out, and the page going away (`pagehide`, the release sent with `keepalive`); a page brought back from the back-forward cache opens the game afresh. `screenOf` picks what is shown from the controller's status: opening, held by another device (with "Take over scoring", which asks before it takes the game: T6 §5, P7 §5.2), read-only with its reason (with "Open the game again"), confirm the format, or scoring.
- **Confirming the format** (P7 §5.1): once the device holds the game, the scorekeeper sees the periods and their length, the overtime length and the clock, from the state's rules, and confirms. The confirmation is kept on the device, so the same device is not asked again for the same game; a format changed since is asked again. A game that already has plays is not asked about at all: a device taking it over mid-game carries on scoring under the format it started with (P7 §5.2, "continues from the last saved tap").
- **The scorekeeper's admin**: whoever's only admin area is Games sees "Your games" on the admin's home: `games.list_my_games` (its own rule for which games), each card with "Score this game" to the tracker for a game recorded live, scheduled or live, in a league that may score. Everyone else's admin home is unchanged.
- **Words on the device.** The page hands the device the tracker's own messages (`tracker.*` from the language's message file) and the device makes its translator from them, so the controller's notice and banner helpers (record 049) are used as they are (T-187).
- **The scoring screen** is a placeholder: steps 2.35 to 2.37 draw there.

## Considered

- **An HTTP door for the rosters** (`GET …/rosters`). Not needed while the page is drawn by the server: the rosters reach the device with the page, and offline opening (step 2.38) starts from what the device stored. It can be added when something on the device needs to refresh them alone.
- **Rosters in the state read.** Record 049 kept the state the engine's document; names are not the engine's.
- **A new store in the queue's database.** It would have bumped the queue's version, which a tab of the previous release holding the database open blocks (record 024, T-127).
- **Asking for the format every time the game is opened.** It would ask mid-game after a reload or a takeover; once per device per format is enough for P7 §5.1's purpose.

## Revisit if

- The device opens a game with no network at all (step 2.38): the controller should start from the stored state and rosters (record 049 says the same).
- What the device keeps changes, or step 2.38 opens a game offline: the stored games must still be let go of on signing out and on opening (another account's or league's, final, older than `openedGameKeepMs`), and a game opened offline must not be deleted before it is scored. Signing out in a way that does not pass through the account page's forms (a session that runs out, "sign out everywhere" from another device) leaves the rows until the tracker is next opened on the device, which then finds itself signed out (401) and clears them; a device never opened again keeps them until then.
- The rosters change during a game (a player added on the spot, S-6, step 2.35): the device's copy must take the new player.
- The founder wants a scorekeeper to correct a wrong format at the scorer's table: the lead decided for them that a scorekeeper may not, and the screen tells them to ask a league admin.
