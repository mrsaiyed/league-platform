# 081 — Safety before real accounts

Date: 2026-11-17. Step 2.98 (T-285). Serves T4 §3, §5, §6 and §12, T-79, record 031. Decided by the builder of step 2.98 for the lead (technical), to be confirmed when the step lands.

What must be true of the website before any real person signs in to it online, as the stage 1 report's finding R6 listed it (step 2.98): the browser told to run only our own scripts and to always use HTTPS, a bot check in front of sign-in and sign-up, visitors told apart behind Cloudflare, harmful text typed into a field coming out as text, and a starter list of offensive short names (U-16).

## Scripts only from us, and HTTPS always (T-79)

**The script policy** (`apps/web/src/server/security-headers.ts`): a script runs only when it comes from our own address or carries the nonce made for that one answer: `script-src 'self' 'nonce-…'`, with `object-src 'none'` (no plugins), `base-uri 'none'` (no `<base>` that would send our own scripts' addresses elsewhere), `frame-src 'none'` and `frame-ancestors 'none'` (record 020's "no other site may frame us", kept). No `'unsafe-inline'`, no `'unsafe-eval'`, no `'strict-dynamic'` and no wildcard. So a script that reaches a page any other way (an inline `<script>`, an `onclick=`, a `javascript:` address or a script from another site, as injected text would try) does not run, and the browser reports it (`tests/browser/script-policy-test.mjs` tries all of them).

**The nonce** is 18 random bytes made by the proxy (`src/proxy.ts`) for every request it handles, which is every page, API answer, form answer, refusal, error page and redirect, and the live feed. The proxy writes the policy into the answer and into the request itself, replacing any policy the browser sent: Next.js reads the nonce from the request's policy and puts it on every script it draws (its own files and its inline page data); the bot check's Turnstile script takes it the same way (`nonceOf`). A nonce the browser chose is used for nothing (`check-web-shell.mjs`). What the proxy never sees (the built script files, the two stylesheets, the icon, Next.js's own early answers) gets the fixed policy from `next.config.ts`, the same words with no nonce, so nothing inline could run there. In staging and production the bot check's one origin, `https://challenges.cloudflare.com`, is added to `script-src` and `frame-src`, taken from the widget the pages draw, so the two cannot drift. `next dev` alone adds `'unsafe-eval'`, which React needs there for its error stacks; a built server never does.

**Why a nonce and not the alternatives.** `'unsafe-inline'` (Next.js's way without a nonce) would let any injected inline script run: the policy would forbid only other sites' files. Hashes cannot work: Next.js's inline scripts hold each page's own data. Next.js's experimental `sri` covers files, not the inline data. A nonce needs every page drawn per request, which they all are today (every route is dynamic in the build). **This meets step 2.176**, which wants league pages kept by a shared cache again: a page kept with one answer's nonce would carry a nonce every later visitor's policy does not name, and its scripts would not run. Step 2.176 must keep pages without scripts' nonces (for example a page kept by the cache with the policy it was drawn with, both kept together, or the inline data moved out of the page), and its done test must load a kept page in a browser with the policy on.

**Zod and `eval`.** Zod, which reads the live game's messages and the tracker's answers in the browser, asks once whether it may build its checks with `new Function`; refused, it checks without it, with the same answers. `apps/web/src/instrumentation-client.ts` (Next.js runs it in the browser before any app code) tells it not to ask (`jitless`), so the browser reports no refusal on every page and the policy's reports stay for real attacks.

**Left for later steps, on purpose:** `style-src` (our pages draw the league's design as inline styles, step 1.18), `img-src`, `font-src` and `connect-src` (the live service's address differs per environment), `form-action` (the no-script Google sign-in posts to our own server action, which sends the browser on to the sign-in service and Google; Chrome checks `form-action` on each of those hops, which cannot be checked on this computer), and a `report-to` address (a place for reports is an outside service). The embeds of C-9 are added, each origin by name, with the step that builds them. T-79 asks for scripts and frames; those are done.

**HTTPS always:** `Strict-Transport-Security: max-age=31536000; includeSubDomains` on every answer, from `next.config.ts` (the static files and redirects too). A browser keeps to it only once it has had it over HTTPS, so on this computer's plain http it is ignored and nothing local changes. A year, as browsers' own guidance asks before the preload list; `includeSubDomains` because everything of ours is HTTPS, the league subdomains of U-13 included. **Not** `preload`: putting the founder's domain on the browsers' built-in list is a commitment that takes months to undo, and it is the founder's to make once the domain is settled. If any address under the domain will ever be plain http (an old site, an email service's tracking address), that must be known before the first HTTPS answer is sent; the founder's supervised session checks it.

## Which visitor a request came from, behind Cloudflare (`TRUSTED_PROXY=cloudflare`)

**The problem.** The attempt limits of T-225 count wrong guesses per network as well as per address. The network is read from the request (`networkAddressOf`, `apps/web/src/server/sign-in/device.ts`), and record 031 gave two choices: `none` (nobody's word is taken; every visitor shares one key, so one person's guesses lock out everyone) and `one` (exactly one proxy of the host appends the address it was reached from, and that last entry of `X-Forwarded-For` is believed). T1 puts Cloudflare in front of Render. Then Render's proxy is reached by Cloudflare's servers, not by visitors, and with `one` every visitor is keyed by whichever Cloudflare server passed them on: thousands of people would share a handful of keys, and 100 wrong guesses from any of them would lock every one of them out for 15 minutes.

**The choice: a third value, `cloudflare`.** Cloudflare names the visitor's address in a header of its own, `CF-Connecting-IP`, which it sets itself on every request it passes on, replacing whatever the visitor sent. But the host can also be reached without Cloudflare, at its own address (on Render, `*.onrender.com`), and there anyone can send `CF-Connecting-IP` with any value: believed blindly, it would let a guesser start a fresh count with every try. So the header is believed only when the request came through Cloudflare, and the app knows that from the one entry nobody but the host writes: the last entry of `X-Forwarded-For`, appended by the host's proxy (the same entry `one` believes). When that address is one of Cloudflare's published addresses (`isCloudflareAddress`, `packages/providers/src/cloudflare`), the visitor is `CF-Connecting-IP`. When it is not, the request reached the host some other way: `CF-Connecting-IP` is refused as a spoof, and the request is keyed by the host's entry, the address that really reached the host, as `one` would. A request through Cloudflare whose `CF-Connecting-IP` is missing or is not exactly one address shares the unknown key (`0.0.0.0`): it fails closed, as `none` does.

What it guarantees: a visitor can change neither key by anything they send. Through Cloudflare, Cloudflare writes the header; around Cloudflare, the header is not read and the host writes the entry that is. A new cookie, another browser or another value of the header leaves the count where it was (`flows.test.ts`, "the network behind Cloudflare"). An address missing from our copy of Cloudflare's list only makes the visitors behind that Cloudflare server share one key: it never lets anyone choose their address.

Cloudflare's list (`cloudflareIpv4Ranges`, `cloudflareIpv6Ranges`) is copied by hand from `https://www.cloudflare.com/ips-v4` and `https://www.cloudflare.com/ips-v6`; nothing fetches it. The comparison uses Node's own `BlockList`, no vendor library. On made-up data (local work and tests), a request carrying `CF-Connecting-IP` is one passed on by another server and is answered with the plain "not answered here" page (`this-computer.ts`, step 2.152).

**Not chosen:** believing `CF-Connecting-IP` whenever it is present (anyone reaching the host directly picks their own key); refusing here every request not from Cloudflare (which requests reach the app at all is the host's setting, point 5 below, not the attempt limits'); fetching Cloudflare's list at start-up (a start that depends on a vendor's page, and nothing to check it against).

**Checked on the real host, in the founder's supervised session, before `TRUSTED_PROXY=cloudflare` is set** (none of it can be checked on this computer):

1. Compare `cloudflare-addresses.ts` with the two published lists, the day it is set.
2. Render's proxy appends the address it was reached from as the last entry of `X-Forwarded-For` (record 031 assumes it for `one`). Through Cloudflare that entry must be a Cloudflare address; straight to the `onrender.com` address it must be the sender's own.
3. A request sent straight to the `onrender.com` address with a made-up `CF-Connecting-IP` is keyed by the sender, and one through Cloudflare by the visitor: watch the per-network wait come for one and not the other.
4. Cloudflare's "Pseudo IPv4" stays off (it rewrites the visitor's address headers). If Render's own edge is itself on Cloudflare, the last entry could be a Cloudflare server for every request, also one sent straight to the `onrender.com` address; then point 3 fails and `cloudflare` is not set until the host's entry tells the two apart (Cloudflare's "authenticated origin pulls" is one way).
5. Whether to refuse requests that do not come through Cloudflare at all (Render's settings, or authenticated origin pulls) is decided there, with the health check in mind.

## The bot check in front of sign-in and sign-up (T4 §6)

**The interface** (`packages/providers/src/bot-check`): a `BotCheck` has a `widget`, what a page draws inside its form, and `verify`, which takes what the widget answered, the form it was for (`sign-in`, `sign-up` or `reset`) and the visitor's network, and says passed or refused with a fixed word (`missing`, `failed`, `unavailable`). It never throws. The web app names no vendor: its ports carry a `botCheck`, and `botCheckFor` picks the adapter, as `emailSenderFor` picks the email sender: the local stand-in in local work and tests, whatever keys are given, so a test never asks Cloudflare; Cloudflare Turnstile in staging and production, which need `TURNSTILE_SITE_KEY` and `TURNSTILE_SECRET_KEY` (the settings refuse to start without them).

**The local stand-in** draws a hidden field holding the one answer that passes. A person's browser, and every browser test, sends the form as it was drawn and passes; a form posted without the field, or with any other answer, is refused as Turnstile would refuse it. It refuses to be made outside local work and tests. "Be this made-up person" (step 2.96) sends the same answer, as the page would.

**The Turnstile adapter** draws Turnstile's box and its script from `https://challenges.cloudflare.com` (the page's script policy allows that one origin in staging and production, below), and asks `POST /turnstile/v0/siteverify` with the secret key, the answer and the visitor's address (never the shared unknown key). An answer passes only when Turnstile says so and says it was made on our own host name for this very form (`hostname` and `action`), so an answer solved on another site, or on the sign-up form and replayed at sign-in, is refused; Turnstile itself refuses one used twice or older than five minutes. No answer from Turnstile, an answer we cannot read, or our key refused is `unavailable`, and the last two are also reported to the log in a fixed word (`key-refused`, `no-answer`, `unexpected-answer`), never with the key, the answer or the address (T-86). Written from Turnstile's published API and tested against made-up answers only: not verified against the live service.

**Where it stands** (`flows.ts`): in front of signing in with a password and of asking for a code (sign-up and the forgotten password), before anything else the form does. A refused form goes back to its own screen with its problem ("We could not check that you are a person…") and the place to go after; the sign-in service never hears of it, so nothing is counted, emailed or set in the browser, and the answer is the same whether or not an account exists (T-68). A refused form counts no wrong guess, so the check cannot be used to lock someone out. Not in front of: the code screen and the new password (they need a code emailed after a check), "Continue with Google" (Google's own), and the password again (a signed-in person, limited per account).

**Fails closed.** When Turnstile cannot be asked, nobody signs in or signs up until it can ("…just now. Please try again in a minute."). With scripts off, Turnstile cannot run and the forms are refused; the page says the check needs scripts. Both are the cautious answers where the spec is silent, and both are product questions for the founder (below).

**Checked in the founder's supervised session, before real people sign in:** a Turnstile widget made in the founder's Cloudflare account for the site's host name (Turnstile's own test keys answer for `example.com`, so they would be refused by the host name check here: the test copy needs a widget of its own); the two keys in the host's secret store; sign-in and sign-up from a phone and a laptop pass; a form posted without the widget is refused.

## Harmful text comes out as text (T4 §12)

React writes every value as text, and nothing in the product takes HTML from anyone (T-78); the places our own code writes markup itself (the league's and the staff screens' style variables, drawn from a checked design whose values are colors and fixed words; the plain "not answered here" page; and the emails, whose values are escaped, `packages/emails`) escape or refuse anything else. `tests/browser/harmful-text-test.mjs` proves it the way an attacker would meet it: an attacker's text (ending a quoted attribute, an element with a handler, a script) is typed through the screens' own forms into every free-text field there is today: a team's name, a person's first and last names, a round's name, a reason to reopen a result, an imported file's name and a venue in it, a name typed at the scorer's table, the email boxes and the numbers' boxes (refused, and drawn back), and the addresses' own questions. Every page that shows them is then opened as a visitor, the owner and the scorekeeper with the browser's script policy switched off, and each shows the text as typed with nothing of it run or made into an element; with the policy on, the browser had nothing to refuse; the raw answer never holds it unescaped. The test reads every admin and public page it opens for free-text fields and fails on one it does not know, so a new field must be added to it.
