# 030 — The live game, calculated and import tables in the database

Date: 2026-11-13. Step 2.4; serves T3 §7, §8, §9, §11 and §12, T6 §1, §3 and §5, S-5, S-6, S-9, S-10, T-40 to T-47, T-80, T-116, T-220. Decided by the lead (technical). T-242.

## Problem

T3 lists the columns of `scoring_sessions`, `game_events`, `game_states`, `player_game_stats`, `standings_rows`, `standings_adjustments`, `season_player_totals` and `imports`, and §12 says each `command_id` and `seq` appears once in a game. It does not say how the tracker's own tables map onto these, what the stats JSON may hold, which rows are history and which are rebuilt, what an import's statuses are, or where the mark for a player added at the scorer's table (S-6) lives. Migration 0010 needed answers.

## What

- **The tracker's tables carry over.** The Al-Hadi tracker's `game_events (sequence, command_id, command, accepted_at)` become `game_events (seq, command_id, type, payload, tapped_at)`: the engine's command is split into its `type` and the rest, as T6 §3 sends it; when the server accepted it is `created_at`. Its `player_game_lines (appeared, ms, points, fg1, fg2, fg3, fouls, turnovers, name, jersey)` become `player_game_stats (played, seconds_played, stats, jersey_number)`, with the counts keyed by stat in `stats`. The state it keeps on its games row is `game_states.state`, the engine's versioned `GameState`. Names are never copied (T-220); the number worn in the game is, because a roster's number can change later.
- **Every tap is saved once, in order, and never changed.** `game_events` is history: its trigger refuses any change or removal even for the tables' owner, the app has SELECT and INSERT only, and `purge_league_history` now also removes a purged league's events. Within a game each `command_id` and each `seq` is unique, and event n needs event n − 1 of the same game, so the log has no gaps and a replay is the whole game. The order check looks only for a row that is never removed, so it takes no lock and holds at every isolation level, as the schedule revision check does (record 025). The per-game lock of T-111 stays in the scoring command. `account_id` names the scorer by id and is empty for an event the system wrote. The payload is an object of at most 16 KB (a whole set of game rules fits). It carries no version of its own: the command's type names its shape, and T-127 already keeps the previous tracker's commands working.
- **One device scores a game.** `scoring_sessions` has one row per game. Taking over updates that row's account, device and lease; ending removes it. The command refuses a tap whose session id is not this row's (T6 §5); a lease that ran out is the command's to read, since the database cannot refuse a row for time passing.
- **One state per game.** `game_states.seq` is the last event applied, 0 before any. The state is a versioned document of at most 2 MB, room for thousands of plays. A state stays while its game does: the app cannot remove one.
- **Stat counts are whole numbers.** `stats` maps stat keys (a letter then letters, digits, `_` or `-`, up to 40) to whole numbers from 0 to 9,999,999, checked by `is_stat_counts`. Which stats a sport has is the sport's code, never the database's, so the tracker's rule that points are 1 × fg1 + 2 × fg2 + 3 × fg3 is the engine's, not a column check. A missing key means the stat was not recorded; `seconds_played` is empty when minutes were not. A line is for one of its game's two teams (`player_game_stats_team_in_game`, a trigger that reads the game as the caller and takes no lock: a game's teams change only by a schedule edit or a correction, after which the lines are worked out again).
- **The calculated tables are rebuilt, not edited.** `standings_rows`, `player_game_stats` and `season_player_totals` can be removed and written again by the app; nothing marks them as typed by hand, because only the calculation commands write them. A team has one standings row in its season (its division names the table it sits in, empty for a season without divisions), and seeds are unique in each table, a season without divisions counting as one table (`nulls not distinct`). Win percentage and point difference follow from the counts and are not stored. `decided_by` takes the season rules' tiebreaker names and `still-tied`. The streak is a result and a length, both or neither. A player has one totals row per season; `stats` is a versioned document holding each stat's total and the games it was recorded in, which the averages need (`PlayerSeasonTotals`).
- **Adjustments are the admin's, with reasons, and go to the bin.** An adjustment is whole-number changes to wins, losses, ties and standings points, at least one of them not zero, with a reason of 1 to 500 characters and who entered it. Removing one sets `deleted_at` (T-45); the app has no DELETE. Where coin flips are stored stays open (T3 §9).
- **Imports.** An import has a kind (`fixtures`, `people`, `teams`, the three of steps 2.22 and 2.75; a later kind widens the check), a status (`reading` by the worker, `ready` to preview, `applied`, `undone`, `failed`), who started it, the season it goes into (empty for people), the file's name and never the file (T-80), the report and what it created as versioned documents with ids and the file's own words. `applied_at` is set exactly when it was applied (applied or undone), and `undone_at` exactly when undone, never before it was applied. Kind, season and starter are fixed. Imports stay as the record of what was brought in and undone: the app has no DELETE.
- **The walk-up mark lives on the roster entry.** `roster_entries.added_at_game_id` names the game at whose scorer's table the person was added (S-6). It is fixed once the entry exists, like its team and person, so the history stays true. `needs_review` is on while the league flags such players and no admin has confirmed them; only an entry with `added_at_game_id` can have it. Which of S-6's three choices the league made is a setting (step 2.71), not a column here.

## Considered

- **Keeping the tracker's `command` as one JSON column.** One fewer split, but T3 and T6 §3 already name `type` and `payload`, and a real `type` column can be searched (T-44).
- **Keeping milliseconds, as the tracker does.** T3 says `seconds_played`, minutes are shown, and the statistics code (`packages/sports/src/stats`) already counts seconds. The Al-Hadi transfer (step 2.58) compares box score lines after rounding to seconds.
- **A column per stat.** Each sport has its own stats (P7 §5.6); a column per stat would name one sport in the schema.
- **Checking that a state's `seq` names an event that exists.** A foreign key cannot take 0 for "no events yet" without a second column; the scoring command saves both in one transaction.
- **A flag on the person rather than the roster entry.** The same person can be added at the table for one team and be on another team's roster properly; the mark belongs to how they joined that team.

## Revisit if

A sport needs fractional or negative stat counts, a game needs more than 2 MB of state, an import kind beyond fixtures, people and teams is built (the Al-Hadi and Faraj transfers are scripts and write through commands, not as an import kind), or coin flips need a place to be stored.
