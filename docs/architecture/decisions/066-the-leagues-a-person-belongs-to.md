# 066 — The leagues a person belongs to: the one read across the league fence for an ordinary signed-in person

Date: 2026-11-15. Step 2.127 ("A signed-in person can find their way"; the "nothing left out" audit, H3; the using-it audit, H1). Narrows T-28 and T-221 (T2 §5, T4). Decided by the lead (technical), migration 0018 approved for this lane. T-269.

## Problem

P2 line 67 ("Signed in: your leagues first"), line 71 (`/account` lists "the leagues you belong to") and line 141 ("The front page and the account button list them all") need one answer: which leagues is this account in? Every league table is fenced to the one league a transaction is set to (0005, T-61), and every query in `packages/database` takes a league (T-28). So no fenced query can answer it, and the only reads that run before a league is known are the narrow owner-run functions of T-221, none of which lists an account's leagues.

## What

One SECURITY DEFINER function, `public.my_leagues()` (migration 0018), read by `listMyLeagues` (`packages/database/src/queries/list-my-leagues.ts`) in a transaction opened for the session's account and no league; then core's `myLeagues` (`packages/core/src/modules/leagues/queries/my-leagues.ts`) decides what the person may see. What it returns for each state, after core's rule: **live** and **archived**: listed for the owner, every role and a roster place. **draft**: listed for the owner and anyone with an admin area (admin, registrar, scheduler, editor, scorekeeper, club admin, at any scope); not for a coach, a captain or a roster place alone. **suspended**: listed for the owner and an admin for the whole league; not for a program's admin, any other role or a roster place. **In the bin**: never returned at all.

### The guard inside

`require_view_of_every_league()` checks `current_user`. Inside a SECURITY DEFINER function `current_user` is the function's owner, not the caller, so the check asks whether the owner sees past row-level security. That is the right question here: owned by a role the fence still holds, `my_leagues()` would see no league row (no league is set), and tell every person "you belong to no league", a wrong answer that looks right. With the check it refuses instead, loudly (`app-role.test.ts`: "the leagues of an account refuse instead of answering none"). The check is not about the caller at all: what limits the caller is that the function takes no argument and reads only `current_account_id()`.

### What it trusts

`app.account_id` is set by the server, per transaction, from the session (T-61; `withTransaction`), the same setting every personal table's policy already trusts (T-62). The app role can set it to anything; so could it for `accounts`. The account comes from the server's session, never the request (`apps/web/src/server/signed-in-leagues.ts`: the session cookie, identified by the sign-in service).

## What else was considered

- **A wider policy on `role_grants`, `people` and `roster_entries`** ("rows of my own account are visible in any league"). Rejected (T-221): it would widen what every fenced query in the product can see, not one question.
- **Asking every league in turn.** No list of leagues is readable by the app role, and doing it would read every league for every page view.
- **Keeping a list of memberships on the account.** A second copy that can drift from the grants and rosters it repeats; removing access must work at once (T-75).
- **Deciding U-9 in the function.** It would put the visibility rule in two places (SQL and core) that could disagree; the league pages already use core's `mayOpenLeague`.
- **Returning each grant with its program, club or team id.** U-9's two rules need only "held at all" and "held for the whole league", so the ids are not returned.

## Revisit if

A screen needs more about a league than these columns (a logo, a next game): add it to the league's own fenced read, opened per league from this list, not to this function. Or the product gets a second read across leagues for a person (the one inbox, U-11): it gets its own reviewed function and record, never a widening of this one.
