## E-DATA-01 — Database conventions

Use PostgreSQL schemas `app` for authoritative records, `published` for approved read models and `internal` for transport/support control records. Disable browser Data API access to these schemas. Auth provider tables remain provider-owned. SQL migrations own all application DDL/grants; never edit provider-owned tables manually.

Every tenant-owned table includes `workspace_id uuid NOT NULL`. Its ordinary primary key is `id uuid`; add `UNIQUE (workspace_id, id)` for referenced entities. Child relationships use `(workspace_id, parent_id)` composite foreign keys, with competition identity included when the relationship must stay inside a competition. IDs are server-generated random UUIDs; their obscurity is not authorization. Do not encode customer names or counters in them.

Shared fields unless an append-only table specifies otherwise:

| Field                      | Type / rule                                                                                                                                      |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `id`                       | `uuid PRIMARY KEY`                                                                                                                               |
| `workspace_id`             | `uuid NOT NULL REFERENCES app.workspaces(id)`; omitted for the workspace root itself (its id is the tenant key) and truly global control records |
| `created_at`, `updated_at` | `timestamptz NOT NULL`; database/server UTC                                                                                                      |
| `revision`                 | `bigint NOT NULL DEFAULT 1 CHECK (revision > 0)`; mutable aggregate roots                                                                        |
| `created_by_account_id`    | Nullable FK to platform account; a separate actor kind/reason records system creation                                                            |
| `archived_at`              | Optional `timestamptz`; use only when archive is a meaningful domain state                                                                       |

IDs serialize as strings. API revisions serialize as decimal strings to avoid JavaScript precision loss; bounded counters such as a draft pick number use integers. Numeric examples in UI are display only. Money uses `bigint` minor units plus ISO currency; API amounts are bounded safe integers before conversion to DB `bigint`. Duration uses integer milliseconds. Scores use bounded nonnegative integers unless the sport contract explicitly supports another unit. Never use binary floating point for money. Percentages/averages are calculated from integers and rounded at display boundaries.

Use `timestamptz` for instants and separate IANA timezone text for human scheduling. Date-only birth/eligibility dates use `date`; do not turn birthdays into midnight UTC. Country/language/currency identifiers use validated registries. User-facing names are Unicode, trimmed and length-bounded; comparison/search fields do not replace original display values.

Use text plus CHECK constraints for evolving statuses. Lists and object settings in JSONB have registered schemas, `schema_version` and size/depth bounds. Queryable ownership, money, permission, participant, capacity and relationship data is relational. JSONB is appropriate for versioned form answers, page composition, sport event payloads and provider evidence with controlled retention. Do not create a universal `objects(type, arbitrary_json)` table.

## E-DATA-07 — Representative constraint SQL

This fragment illustrates the scope contract; it is not a complete migration. Referenced tables, immutable-column controls, grants, RLS and indexes are implemented in the migration suite.

```sql
CREATE TABLE app.entries (
  id uuid PRIMARY KEY,
  workspace_id uuid NOT NULL,
  competition_id uuid NOT NULL,
  status text NOT NULL CHECK (status IN ('pending', 'active', 'withdrawn')),
  UNIQUE (workspace_id, competition_id, id),
  FOREIGN KEY (workspace_id, competition_id)
    REFERENCES app.competitions(workspace_id, id)
);

-- On app.games, after it defines its workspace/competition/home/away fields:
ALTER TABLE app.games ADD CONSTRAINT games_home_scope_fk
  FOREIGN KEY (workspace_id, competition_id, home_entry_id)
  REFERENCES app.entries(workspace_id, competition_id, id);
ALTER TABLE app.games ADD CONSTRAINT games_away_scope_fk
  FOREIGN KEY (workspace_id, competition_id, away_entry_id)
  REFERENCES app.entries(workspace_id, competition_id, id);
ALTER TABLE app.games ADD CONSTRAINT games_distinct_entries
  CHECK (home_entry_id IS NULL OR away_entry_id IS NULL
         OR home_entry_id <> away_entry_id);
```

For shared resources, use an exclusion constraint with `btree_gist` if supported by the selected provider:

```sql
ALTER TABLE app.resource_bookings
  ADD CONSTRAINT resource_no_active_overlap
  EXCLUDE USING gist (
    workspace_id WITH =,
    resource_id WITH =,
    occupied_range WITH &&
  ) WHERE (status IN ('held', 'confirmed'));
```

Validate nonempty finite bounds and reserve availability in a transaction. An expired hold remains conflicting until explicitly released; do not use a volatile `now()` predicate in an index/constraint. A cleanup worker and the booking command can expire due holds under the same resource lock.

PostgreSQL constraints provide row/relationship integrity; multi-row capacity and workflow rules still require transactions. [PostgreSQL constraint reference](https://www.postgresql.org/docs/current/ddl-constraints.html).

## E-DATA-08 — Locks and transaction ownership

Use READ COMMITTED with explicit row locks for the listed aggregates; use SERIALIZABLE only for a demonstrated predicate invariant that cannot be expressed with constraints/aggregate locks. Catch deadlock/serialization failures and retry the entire short transaction, at most three attempts with jitter, using the same command identity. No provider calls inside a retrying transaction.

Lock order across a multi-aggregate command: workspace access guard → aggregate roots ordered by type/key → capacity/resources in sorted UUID order → affected rows. The access guard uses a shared row lock for commands and an exclusive lock for permission changes. Once revocation commits, a new command cannot pass using an older grant. Do not make every command increment the workspace row.

| Operation               | Root locks                                        | Atomic writes                                                                   |
| ----------------------- | ------------------------------------------------- | ------------------------------------------------------------------------------- |
| Allocate place          | Capacity pool, application                        | Allocation, counters, admission state, receipt, audit, outbox                   |
| Draft pick              | Draft session, destination entry                  | Pick, roster membership, next pick/revision, receipt, audit, outbox             |
| Publish schedule        | Competition schedule root, sorted resources       | Current schedule pointer, bookings, changed games, audit, notice intents        |
| Accept scoring batch    | Game and scoring lease                            | Sequential events, snapshot/state, revision, receipt, outbox                    |
| Finalize/correct result | Game, affected competition projection coordinator | Result version, active pointer, rebuild request, audit; expensive rebuild later |
| Request refund          | Order and payment attempt                         | Reserved refundable balance, refund intent, receipt, audit, job                 |
| Publish website         | Site and draft                                    | Immutable release, active pointer, safe public document, audit, outbox          |

For large schedule publication, bound the batch (proposed maximum 500 games) and reject oversize synchronous publication. A larger schedule needs a staged reservation protocol before being supported; never partially publish a supposedly atomic season schedule.

## E-DATA-09 — Indexes, deletion and schema delivery

Create indexes for each supported query, including referencing foreign-key columns; PostgreSQL does not automatically create every useful child lookup index. Baseline patterns: `(workspace_id, competition_id, starts_at, id)` for schedules; `(workspace_id, competition_id, admission_status, submitted_at, id)` for applications; `(workspace_id, game_id, sequence)` for events; `(account_id, workspace_id, revoked_at)` for grants; `(workspace_id, account_id, created_at DESC, id)` for inbox. Use filtered indexes for active reservations/ready jobs where the predicate is stable. Do not add a JSONB GIN index to every payload without a measured query.

Core historical parents use `ON DELETE RESTRICT`. Cascade only ephemeral child data whose deletion is explicitly safe. Account closure cannot cascade-delete official scores or all finance evidence. Erasure processes redact eligible personal fields and derived publication with documented retention exceptions. Soft deletion is not a substitute for a retention policy.

First migration groups: (1) schemas/roles/identity/workspaces/access; (2) league/season/competition; (3) site drafts/releases/configuration and safe projection; (4) audit/receipts/outbox/jobs; then each feature's tables, policies and tests in the same change. Run from empty and upgrade from the previous release with realistic fixture data. CI verifies no tenant table lacks scope policy/constraints. Generated DB types must match migrations. A migration is not complete until constraints, grants, RLS and indexes are reviewed together.

## E-DATA-10 — External-competition team records

The October 27 stats-first use case adds a separately owned record family; hosted `games` and competition-entry constraints stay intact. Implement workspace-scoped team seasons, external competition references, participation links, team game records and frozen participants, with immutable result versions and explicit authority on published projections. An external source ID is a deduplication/provenance key, never an authorization grant. Require an explicit reviewed mapping before linking a team record to a hosted official game. The [varsity technical contract](../../../initiatives/alhadi-varsity/02-engineering-contract.md) defines the entities and local-to-production mapping.

The current `varsity_preview` SQL is intentionally an isolated single-season rehearsal. It contains workspace keys and atomic events/stat lines but not production roles, RLS, users, full competition scope or immutable final-result tables. Do not deploy that schema as proof that this production dictionary is implemented.
