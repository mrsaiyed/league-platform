## Problem

A scorekeeper who started the wrong game, or was only trying the tracker an hour early, could undo every play but not the start: the game stayed live, the public schedule said "Live, 0–0" before tip-off, and its rules were fixed for good. The server refused the tracker's `reset` and promised a command of its own (`live-game.ts`). Three things stood in the way or were open:

1. **The database fixes a started game's rules forever.** Record 025: once a game first goes live, its `format` cannot change "even if it later goes back to scheduled or is postponed, so a game cannot be stepped back to change its rules and then restarted", and `format_fixed_at` is never cleared.
2. **The event log is never edited** (T3: every tap, never edited), yet the game must start again from nothing, and the plays cleared must stay readable and never be replayed into the new start.
3. **Where S-40's line falls**, which plays count as "something recorded", and what happens to another device's waiting taps and to the scoring session.

## What

- **Not stepping back to change the rules of a game that was played.** Marking a game not started clears a game that was never played: everything recorded in it is cleared and kept in its events, and who may do it is limited by S-40. So S-1 ("a game keeps the rules it was played under") does not apply to it: it has no rules of its own again and takes its season's, as they stand, when it next starts (decided for you, S-40's details).
- **A game that was ever decided is never marked not started** (S-40, decided for you): a correction for it, or an `end` or `reopen` in its event log. It was played; it is reopened and corrected (S-7), never cleared, by anyone, even with every play undone after a reopen (`was-decided`).
- **The database allows it in one update only, and only for marking** (migration 0016). `format` may be emptied, and `format_fixed_at` is then cleared with it, only in the update that takes a game from `live` back to `scheduled` while the game's latest event is the `reset` marker and the game was never decided (`public.game_marked_not_started`, reading `public.game_ever_decided`). The command writes the marker and the new state before it changes the game, so this is the database's rule, not only the command's. Both together or neither: a live game sent back to scheduled that keeps its format keeps `format_fixed_at`, and every other change to a started game's rules is refused as before (a postponed or cancelled game that had started, a decided game, the format replaced rather than emptied, a log that does not end at a marker). Only functions change, each made whole (four new, granted to the app's role, and three replaced); the triggers stay as 0009 and 0010 made them, and the migration is safe to run again.
- **What looks past the marker.** Everything recorded before a game's last `reset` event is cleared, so whatever asks whether the tracker has recorded anything for a game counts only the plays that came after it (the players the scorer’s table added, changed or took off are events but never plays, record 058): `public.game_tracked_past_marker` in the database, and through it `gameHasPlays` (box score entry, `set-box-score.ts` and `get-box-score-sheet.ts`), `listGamesById` (a later schedule publication's "game cannot be removed", `publish-plan.ts`), `binPublishedGames` and the bin's own rule (`games_scored_not_binned`, through `public.game_scored_for_bin`: a cleared game never decided may go to the bin, and a game decided by hand with no events still goes with a correction as before; its events stay, since the app never removes a game's row), and the Al-Hadi transfer's plan (a game here counts as tracked only past the marker). Anything that reads the event log in future (the written recap and its job in stage 4, the tracker backup reader, T-126) must start after the last marker too, or the cleared plays come back.
- **One command, `games.mark_not_started`** (input: the game, the sequence number of the last play the asker has seen, and a reason, optional), behind `POST /api/v1/leagues/{leagueId}/games/{game}/not-started`. The tracker's own `reset` tap stays refused: a tap can carry neither the permission to correct games nor a reason.
- **Where the line falls** (S-40, decided for you): lineups, substitutions, timeouts, jersey colors and every clock tap (start, pause, period, setting the clock, the clock mode) are "lineups and clock taps". A basket, a foul or a turnover (a team turnover too) is "something recorded" while it stands in the game's present state, read from the engine's own counts: one undone, or a foul or turnover taken back with its own button, is nothing recorded, because the scoreboard the scorekeeper sees shows nothing. With nothing recorded, whoever may score the game may (`games.score`, as `mayScoreGame` decides); with something recorded, only someone with `games.correct` at the game's program, and a reason. The engine's own `hasRecordedStats`, which lets a game end, reads the play list and counts a foul even after its `unfoul`; this line reads the counts the plays leave, so the two differ on purpose: ending needs something tapped, clearing needs something standing.
- **The reason is chosen, never typed:** started by mistake, only trying the tracker, wrong game, wrong game format, another reason (`notStartedReasons` in `packages/contracts`). The activity log keeps ids and fixed words only (A-6, 0004), as for R-23’s reason.
- **Judged on what it clears.** The command's permission check takes the game's lock (T-111) before it reads the plays, so a batch saved a moment earlier is judged and cleared with the rest, and one sent a moment later waits and then meets the ended session.
- **The cleared plays stay in the log, behind a marker.** No event is edited or removed. A `reset` event, the engine's own command, is added after the cleared plays, by the account marking it, numbered after the game’s last event (its changes of players at the table included, record 058), with `clearedThrough` (that last event’s number) as its payload. The sequence number the asker sends is checked against the same last event. The saved state is replaced by a new game at the marker's sequence number: the engine's reset (the jersey colors are kept) with the season's rules put in, as the next batch would put them in anyway (`withCurrentRules`). Every read starts from the saved state, so nothing before the marker is ever replayed into the new start, and the sequence numbers run on with no gap. A tap the server took before the marker is still answered "duplicate" if it comes again, never taken as new.
- **The game goes back to scheduled** with no score, no lines and no rules of its own, in the same transaction. Standings never counted a game that was only live, so nothing is announced and nothing else moves.
- **The scoring session ends.** Another device's waiting taps then meet the server's own refusal (`session-not-held`, T-116) and are listed there as not saved (step 2.113's controller); the device that marked it opens the game again like any other and starts cleanly. While another account's scoring session is on the game, its lease run out or not, the command is refused (`session-held`, decided for you): a game scored with no signal looks from outside like a live game with only lineups, and that device may come back with every play. The way through is taking the game over, which asks first and names who was scoring (S-42). The holder's own account may mark it from any device.
- **Refused, each with its own words** (in the message files): not live yet (`game-not-started`), ended on the tracker (`game-final`: that is reopening), final once and reopened (`was-decided`), a final score, box score or forfeit entered by hand (`entered-by-hand`), postponed, cancelled, live with no tracker plays (`not-tracked`), plays that moved on since the asker saw them (`changed-since-read`), another account's session on the game (`session-held`), and something recorded with no reason (`reason-needed`). A basket, foul or turnover standing for someone who may score the game but not correct it has a code of its own (`plays-recorded`), with the way out in its words: undo them first, or a league admin clears it with a reason. `not-allowed` is kept for someone who may neither score nor correct the game (the role-by-command test reads `plays-recorded` as that row’s refusal of `games.correct`).
- **Written to the activity log** as `games.mark_not_started`, with who, `clearedThrough`, the reason when one is given, and what was cleared, as numbers: each team’s score, fouls and turnovers. That entry is how an admin reads afterwards what was cleared.
- **The public side follows at once.** The endpoint publishes the game's message after answering, as a batch of taps does (T-117): the snapshot reads the game as scheduled, 0–0, with the marker's sequence number, so open pages redraw and the home and schedule pages, which read the game's row, follow.

## Considered

- **A generation number on events, or removing the cleared events.** Either needs a table change, and removing them breaks "never edited" (T3). The marker and the replaced saved state give the same boundary with what is there.
- **A correction row (`game_corrections`) for the reason.** That table is for decided games, and the public page shows "corrected" for any game that has one, which would stay on a game played properly later. The reason goes to the activity log, chosen from a fixed list.
- **A typed reason.** The activity log keeps fixed words only (A-6); a typed reason can name a person.
- **Allowing it once the other device’s lease has run out**, as ending does. Two quiet minutes is what a gym with no signal looks like; the takeover is the door that asks.
- **Keeping the game's rules.** A game started by mistake would keep a format nobody chose for it; the scorekeeper's reason for marking it not started is often the wrong format (finding H2).
- **Counting plays in the log rather than the present state.** A basket recorded and undone would then need an admin, which no scorekeeper would expect.
