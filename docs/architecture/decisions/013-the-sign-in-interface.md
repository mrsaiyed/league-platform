# 013 — The sign-in interface and its local stand-in

Date: 2026-11-13. Step 1.13; carries out T-6, T-14, T-67 to T-71, T-85; decides T-225. Decided by the lead (technical).

## What

- **Where:** `packages/providers/src/sign-in/`, used through `@srleagues/providers`. The interface (`SignInService`) is in providers, not in core's ports, because nothing in core calls it: the web app signs people in and puts the account into the command context (T-23). If a core command ever needs it, the type moves to core and providers implements it, as the database does (record 010). The shapes of what reaches it (email, 6-digit code, passwords, device, network address) are Zod schemas in `@srleagues/contracts`, which gets its own `index.ts` for this. The service takes plain strings and checks them against those shapes itself; a device or network address that does not fit is the app's mistake and is thrown.
- **Operations:** start sign-up, start reset, check a code, set a password, sign in, start and finish Google, who is this, renew, the password again, sign out, sign out everywhere (with or without this session), list sessions. Each returns a typed result or a typed expected error (`{ code }`, core's `Result`).
- **One route for a new address and a forgotten password (T-67):** a code proves the mailbox, then `setPassword` either creates the account or replaces its password. Sign-up for an address that already has an account sends a code too, and finishing it is a reset. Replacing a password ends every session of the account and reports `password-changed`, so the app emails the account (T-85).
- **Identical answers (T-68):** asking for a code always answers "sent"; a reset for an unknown address still leaves a pending entry no code can match, so guessing, using up and expiry behave the same; a wrong address and a wrong password are one error; wrong guesses are counted against the address typed and the network, not against an account; an unknown address still does the work of a password check; and the sender is handed a message for every request (one with no code, for a reset to an address with no account, is recorded and sends nothing), so asking costs the same work. A test runs every entry point against both kinds of address.
- **The service says, the app decides:** a sign-in on a device the account has not used reports `newDevice` (T-70); a changed password reports `password-changed`; the session reports when the password was last typed, whether the account has one, and when the person last signed in by any means (a fresh Google sign-in is the proof for an account with no password). The password-again check answers `no-password` for such an account and never counts it as a guess: only the account's signed-in owner can get that answer. Sending the emails and the one-hour rule for sensitive actions are the app's and core's. A device is recognized by the app's own long-lived device cookie, passed in as an opaque id.
- **Codes go out through our email service (T4 §3).** The service hands a code to a `SignInCodeSender`; the app wires it to the email interface (step 1.19). With Supabase that is its send-email hook. If the sender reports it could not take the message, the answer is `code-not-sent` and no code is kept.
- **T-225, the numbers behind "a few":** code valid 10 minutes, 5 attempts per code, 5 codes per hour per address and 30 per network; a proof from a right code is good 15 minutes; access token 60 minutes, session with no limit (T-70); wrong passwords per address typed: from 5 in 15 minutes each try waits 30 seconds, at 10 locked 15 minutes; per network (wrong passwords and wrong codes together; IPv4 address or IPv6 /64): from 30 each waits 5 seconds, at 100 locked 15 minutes; passwords 8 characters (code points) to 72 bytes (the hash reads no further), in NFKC form. The Supabase project is set to the same numbers in step 1.15.
- **Parallel requests:** each try is counted before anything is awaited and taken back if it was right, and after an await the lookup and the change are finished without awaiting again, so tries at once cannot slip past a limit and two proofs at once make one account. Setting a password ends the address's other proofs and codes.
- **Google** may send the browser back only to an origin on the app's list (`isAllowedReturnAddress`, used by every adapter): https, or plain http to this machine in development.
- **The stand-in** (`createLocalSignInStandIn`) is in memory, refuses to start unless told `development` or `test` and refuses if the NODE_ENV the app's config read is `production` (it is passed in: only the config module reads the environment, T-30), uses cheap hashing, refuses a sample of 20 leaked passwords, and hands codes to `createSignInCodeCapture()`. Google is played by `approveExternalSignIn`. It is never for production.

## Considered

- **The interface as a core port.** Matches record 010's pattern, but core would hold a type it never uses. Moved there if that changes.
- **Separate sign-up and reset codes that cannot cross.** A stranger could then tell from the sign-up screen that an address has an account (the code would not come, or would say so on screen). One route keeps the screens identical; only the mailbox learns.
- **Checking the code and setting the password in one call.** Fewer calls, but the code screen could not say "wrong code" before the password screen, and Supabase's own flow is two steps.
- **The service sending new-device and password-changed emails.** Deciding who gets which email is core's (T2 §2).

## Revisit if

- Supabase cannot do something here the way the stand-in does (step 1.15): it has no list of sessions in its client API and no notion of a device, so the adapter will need a small store of its own; its refresh tokens allow a short reuse window, where the stand-in allows none; and whether it refuses passwords over 72 bytes or cuts them is to be checked on the live service.
- Owners get a second sign-in step (T-72) or an email change (T-73): both add operations here.
