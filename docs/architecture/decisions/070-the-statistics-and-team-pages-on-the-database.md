# 070 — The web app on the database, part 3: the statistics, the team pages and each league's name

Date: 2026-11-15. Step 2.93 part 3 (T-274); follows records 055 and 069. Serves T2 §4, T-81, T-30. Decided by the builder of step 2.93 part 3 for the lead, to be confirmed when the part lands.

**Not verified against a real PostgreSQL server or Supabase.** Everything below runs on the made-up database (PGlite) only.

## Problem

On the database the statistics page, the team pages and the home page's leaders refused (record 069), and every league's header showed its short name, since the name and design came from the stand-in's made-up leagues only. These pages show people's names, children's among them, so who sees which name must be read from the league itself (step 2.126's settings, its own audience) and never from a fixed value.

## What

- **Names only with the league's own settings, in one transaction** (T-81). `publicStats.statisticsOf(leagueId, work)` is new on the port: on the database it opens one transaction set to the league and gives `work` the statistics reads and the league's settings, read in that transaction: its audience (`findLeagueAudience`) and its name policy (core's `readNamePolicy` over `listSettingValues`). So a name is always shown by the setting saved when it was read, never by one read a moment before or after. The statistics page, the home page's leaders and a team's page (its head, statistics and roster) read through it. On the database the read store alone (`readStoreOf`) does not read people: it refuses with `NamesOnlyWithSettings`, so no page can put a name beside settings read at another moment. The stand-in answers `statisticsOf` from its one world.
- **One transaction is one snapshot only when it is opened as one** (the lead's technical decision at the reviews of this part). A transaction opened as by default is READ COMMITTED on PostgreSQL: each statement sees rows saved after the statement before it. So a league on full names, not confirmed, shows "Ava L."; the admin saves "first name and last initial", then ticks the confirmation; a page that read the names setting before the first save and the confirmation after the second would show "Ava Lindqvist" once, a state the league never had. The one transaction helper (`withTransaction`) now takes `{ snapshot: 'page' }`: REPEATABLE READ and READ ONLY, so every statement sees the database as it stood at the first, and nothing in it can write; the league and account are set exactly as before, for that transaction only. Every public page's read on the database is opened so: the statistics, the standings and the seasons (`databasePublicStats`), the schedule, its clock and a game's facts (`databasePublicSchedule`), the start page, a roster and a member's teams (`databasePublicTeams`) and the league's name (`databaseLeagueSites`). Commands, sign-in and the league lookup keep the default. Tested: the transaction's own `transaction_isolation` and `transaction_read_only` inside such a read, a write refused there (25006), the default left for the next transaction, and every public port asking for it. **Not proved here**: the local database has one session, so that a save made by a second session half-way through a page's reads is not seen is for the founder's supervised session on PostgreSQL.
- **A roster is read with the statistics, in the same snapshot.** A team's page shows a child in its roster and in its statistics; read in two transactions, a save between them could show the same child two ways on one page. So the roster is no longer a port of its own (`publicTeams.rosterOf` is gone): `statisticsOf` gives `work` a `rosterOf(teamId, viewer)` beside the store and the settings, which takes the viewer only (no caller hands a roster a policy) and names by the same name settings the statistics are shown by. On the database it is `listPublicRoster` in the same snapshot, which reads the audience from the league's row; on the stand-in, its made-up league's own setting from the one world.
- **No person's database id on a public page** (the area lead's review, M2). The statistics page's rows and leader boards and the home page's leaders were keyed by the player's id, which went to every visitor in the page (the table is drawn in the browser). A player hidden later at a guardian's request kept the same id on their nameless line, so a saved copy of the old page named them again, and the id carries when the record was made. Their keys are now places within this page's data, stable for this drawing only (`player-0`, `leader-0`), as the team page's were already; on the stand-in and the database alike, since both use the same builders. The T-81 scan on the database fails on any person id, in any capitals, in any public page's data or HTML (the statistics page, the home page's leaders, the team cards, each team page's head, statistics and roster); the stand-in's statistics page is checked the same way.
- **Every rule stays in core**: who is left out (a person in the bin, a team in the bin, a season not public, a team whose statistics are "team totals only" or staff only, a player on such a team, a person taken off at their request) and how a name is shortened (`statisticsSource`, `showName`, `publicRosterLine`). The queries only fetch named columns: `listPeopleForDisplay` reads names, `is_minor` and the person's request, never a birth date, a contact address, a guardian or a note.
- **A member's teams** for a "my team" league: `listTeamsOfAccount` (new) reads, in a transaction set to the league and the session's account, the season's teams the account has a roster place on now, through the person linked to its own profile (`relation = 'self'`, as the made-up world's person is an account), team ids only. Nothing yet links a seed person to an account (claiming comes later), so on the made-up database a member is sent to a team they coach or captain (their grants), or stays on the league home.
- **Each league's name** (`leagueSites`, new on the ports): on the database the name the owner gave the league (`findLeagueName`, new: the name and nothing else of the row); on the stand-in its made-up leagues', with LOCAL_DESIGN as before. **The database holds no design**: T3's `sites` and `site_releases` are not yet migrated, so every league on the database takes the neutral starting design (`clean-court`). Storing a design needs a migration; this part has none.
- **A season's statistics**: no command writes `seasons.stat_keys`, so on the database every season named none. Core now reads a season that names none as keeping what its rules' "Statistics kept" asks for (P7 §1): the columns the box score grid asks for, the rules read as the games module reads them (rules that cannot be read are the starting set). A season that names its statistics keeps those (the stand-in's do).
- **Minimum games for leaders** (P7 §6 says the league sets this rule; the builder's question, answered by the lead for the founder at the reviews of this part: 3 games to start, and the league can change it). A league setting, `statistics.minimumGamesToRank` (a whole number from 0 to 1000, 0 ranking everyone), declared once in core's settings list beside `privacy.*` and `games.whoMayScore`: settings are rows, so no migration. The statistics reads take it from the league's own rows, on the database (`listSettingValues`, in the page's snapshot) and on the stand-in (the one world's settings, where the made-up leagues that rank from 2 or 0 games save it) alike. A season one game old has no one at 3, so each seed league on the made-up database saves 1 through League settings' own command. The settings screen lists it under Statistics with the number field every setting gets; shaping that screen is step 2.169's.
- **The seed**: each seed league says who plays (Maple Street is now a youth league), its people carry made-up private fields for the scans, and `madeUpDatabase({ underWay: true })` puts the league's people on the teams that played and records each played game from its box score sheet (`setBoxScore`), by the product's own commands.
- **The T-81 scan through the database-backed ports** (`database-names-scan.test.ts`): the adult and the youth seed league, under every names setting the owner saves, with and without the parents' confirmation and with a player taken off; every page's data and the rendered statistics page and home leaders hold the names the rules give and no withheld name, private value or person's id. Its reach (the area lead's review, L1): an adult's own request for initials once the league lets adults ask; a team whose statistics are its staff's only (the child stays on the roster and is on no statistics page, leaders card or player line); a player who left their team (still on its roster, marked); the same person moved to the bin (no name anywhere, their games a nameless line); and a league of mixed ages (`madeUpDatabase({ audiences })`, new for tests), where a player of unknown age is a child. A league whose audience cannot be read is read as youth by `findLeagueAudience` (its own test, new): the column admits no other value (0003), so no league can be made one end to end. The browser test on the seeded database opens the adult league's child's own team page and finds them as "Quinn S.", their family name nowhere.

## Considered

- **Passing the policy into the roster, as before.** The caller read it in another transaction; a setting saved between the two reads would show names by a setting that was no longer the league's.
- **A second helper for page reads beside `withTransaction`.** Two helpers would each set the league's fence and could drift apart; an option of the one helper sets it once.
- **SERIALIZABLE for page reads.** It adds nothing for a transaction that only reads, and a read-only one can be made to wait or retry; REPEATABLE READ is one snapshot.
- **Leaving `readStoreOf` able to read people on the database.** Every page reads through `statisticsOf` now; a refusal makes a page that does not fail loudly, not show names by a stale setting.
- **A design kept as a league setting** (`setting_values`). T3 puts the design in `sites` and `site_releases`; a second place would have to be moved later. Left for the step that migrates them.
- **Writing `stat_keys` in the seed by hand.** Seasons the product makes would still keep none.
