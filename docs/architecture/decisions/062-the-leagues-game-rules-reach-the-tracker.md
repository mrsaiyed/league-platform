# 062 — The league's game rules reach the tracker: the engine's rules, and the platform's command shape in protocol version 2

Date: 2026-11-15. Step 2.122 (part A; the first half of step 2.68); answers the 2.107 audit's finding M7; serves P7 §1 and §5.2, S-1, S-21, S-32, T6 §1 and §3, T-127, T-128. Decided by the builder of step 2.122 for the lead (technical). T-265.

## Problem

The engine has known the clock mode's switch, the last-minutes stop clock, the mercy lead and the personal foul limit since step 2.67, but none of it reached a game on the platform. The function that turns a season's rules into the engine's (`engineRulesOf`, `packages/core/src/modules/games/engine-rules.ts`) dropped the three rules, so a league with a foul limit of four saw nobody marked out, and the tracker's door read taps in the Al-Hadi tracker's command shape (`Envelope`), which has no clock-mode switch, so the switch step 2.69 will draw would have been turned away. The Al-Hadi tracker dims a player at five fouls today: at the demo the rebuilt tracker would have done less than the one it replaces.

## What

**The rules.** `engineRulesOf` carries `playerFoulLimit`, `mercyLead`, `stopClockLastSeconds` and, with the last, `stopClockScope`, each only when the season sets it, and leaves it out when it is off (never `null`). That is how the engine keeps rules itself (`checkRules` in `packages/sports`), so the engine keeps the rules the server makes a game with as they are, and a season with none of them gives the same rules as before this step. One difference changes nothing: where the last seconds are (`stopClockScope`) is left out when there are no last seconds, where the engine's own check would keep it. Team fouls that reset by half or by game are still not carried: the engine has no such setting (finding M8, an engine step).

**One path to the device, so device and server cannot disagree.** The device never builds rules of its own: it loads the engine's state from the server (`games.read_tracker_state`, record 049), whose `rules` are those the next batch will be judged by, and applies its taps on that state with the same engine. The read and the batch both take the game's rules from one place (`effectiveRulesOf`, then `engineRulesOf`), and a state that holds only line-ups takes the game's rules as they stand in both (`withCurrentRules`). Nothing was added to the opened-game read or the page: the state the device already loads carries the rules.

**Until tip-off the rules can still move under a device.** The server plays a game that has not started under its rules as they stand at each batch, but a device keeps the state it loaded: an admin who changed the limit, the mercy lead or the stop clock after a device opened the game (or the night before, the device reloading from its own storage) would have the server judge the game by the new rules and the device by the old, and nothing would bring them together (the step's review, M1: a player out on the server and not on the device; under a new mercy lead the device's next start refused mid-game). So the controller (`tracker-controller.ts`, `settle`) loads the state again each time the server takes a batch while the state it works from has not started, and rebuilds on it with the taps the server does not have yet on top, as after a refusal; taps made while that load is under way are kept once each (`load`). A load that gets no answer is asked again after a growing wait, on a timer of its own, even if no batch follows; and an answer older than the state the device already built on (two loads answered out of order) is left, so no tap the server took leaves the screen. The batch that starts the game fixes its rules: once a load after it is answered, the device has the server's rules; for a game already under way nothing changes and nothing more is loaded. What is left: a device offline from before the change shows the game under the rules it loaded until it is back, its batch is taken and a load after it is answered, then it converges; and if the game was started offline, the server may refuse taps that the old rules allowed, which are then listed as not applied (T-113). So in that window a foul the device shows as the fourth is not always the fourth on the server: the two agree once a load after the device's first batch since the change has been answered.

**A game keeps the rules it started with (S-1).** Unchanged, and now tested for these rules: from the moment a game goes live its state keeps its rules and the game's `format` is fixed (record 049, `games_format_fixed_once_started`), so a season's limit changed mid-game or after the game ended reaches neither the server's state nor a device that reloads. A game started before this step has rules without a limit and keeps them: it plays on as before, though its fixed `format` says five. A game with only line-ups still takes a change.

**The command shape: the platform's, in protocol version 2.** A tap (`TrackerCommand` in `packages/contracts/src/tracker-protocol.ts`) is now `PlatformEnvelope` with its tap time: the Al-Hadi commands, the clock-mode switch, and a `rules` command in the platform's shape (still refused at the door: the rules come from the league). The protocol stays at version 2:

- Everything the present tracker sends is taken and answered exactly as before: the version 2 shape only got wider. Version 1 keeps the Al-Hadi shape as it was (`TrackerCommandV1`, `CommandBatchV1`), so a version 1 batch is read as it always was; nobody ever sent it a switch.
- A tracker opened before this release (an older client, the T-127 case) sends what it always sent, and reads states that may hold `clock-mode` plays and the new rules; its engine has known both since step 2.67 (the state's schema leaves the rules' other fields to the engine). A player marked out is a field it already reads (`Line.fouledOut`).
- Moving to version 3 would have dropped version 1 (the server takes the current version and the one before, T-127) for no gain: nothing an older client sends changed meaning.
- A newer client meeting an older server (only on a release taken back) would send a switch the older server cannot read: the batch is answered `invalid-input`, the queue sends its taps one at a time, and only the switch is set aside as not saved (record 024). Under a version 3 the older server would have turned the whole queue away until the page updated, which is worse at a game.

The engine's events keep the switch like any play (`game_events`, type `clock-mode`, payload `{ mode }`), it is undone like any play, and the public pages read it as an "other" play.

**The Al-Hadi transfer still reads that tracker's shape.** The transfer checks each stored action of an Al-Hadi backup against the Al-Hadi tracker's own command shape (`tracker-replay.ts`), now named `TrackerCommandV1`, so a backup holding a clock-mode switch is not taken as that tracker's.

**A transferred game is played, and kept, without the rules that tracker never had.** That tracker had no mercy rule and no last-minutes stop clock. Replayed under a season that sets one, a blowout would switch to a running clock, the tracker's next start would meet "the clock is already running", and the game would be blocked (the step's review, M2). So the transfer plans and replays each game under the season's rules less those two (`withoutMercyOrLastMinutes`, `engine-rules.ts`); the foul limit is kept, since it only marks a player. The plan's replay uses them (`plan-tracker-transfer.ts`), and the run sends its batches with `withoutMercyOrLastMinutes: true` (`run-tracker-transfer.ts`): the door then plays the game under them and fixes them as the game's own `format` when it goes live, so the rules kept with a transferred game say how it was played, while the season keeps its rule for the games scored here. The door takes that only from whoever may also correct the game (`games.correct`, which the transfer requires), and the endpoint refuses any tracker body that carries it (`invalid-input`). So the Al-Hadi season here no longer needs to keep those rules off for the transfer. The power the flag gives, plainly: someone who may correct games and holds the game's scoring session can start a game of their own league without the mercy lead and the last-minutes stop clock (its other rules, the foul limit included, stay the season's), and that game keeps it. Only the transfer, a script run on the server, sends it; no browser route can, since the endpoint refuses it, and the two-league harness proves it reaches no other league's game.

**What a player marked out means.** S-32 settles it: marked only, never taken off or kept off the floor; a foul for them is still recorded, and taking one back unmarks them. The mark is drawn by step 2.35 (checklist D10); what the public page says about it is not decided here.

## Considered

- **A separate read of the rules for the device**, beside the state: two paths that could drift apart, one of which a device offline would not have. Refused.
- **Carrying `null` for a rule that is off.** The engine drops `null`, so a state the server made would differ from the same rules sent through the engine's own `rules` command, and every existing game's rules would change shape. Refused.
- **Protocol version 3.** See above: it would drop version 1 and make a release taken back worse.

## Revisit if

- The format confirmed on the device (record 054) lists every rule (step 2.119, S-39): it compares only periods, their length, overtime and the clock mode today, so a limit changed after a scorekeeper confirmed, before tip-off, reaches the game without being shown again.
- The engine learns when team fouls reset (finding M8): carry `fouls.teamFoulsReset` here.
- A command is added whose meaning an older server would get wrong rather than refuse: that needs a version of its own.
