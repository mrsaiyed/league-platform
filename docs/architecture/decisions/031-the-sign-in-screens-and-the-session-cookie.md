# 031 — The sign-in screens and the session cookie

Date: 2026-11-13. Step 1.14; carries out T-67, T-68, T-69, T-70, T-71, T-85 and T-225 in the web app; decides T-243. Decided by the builder of step 1.14 for the lead (technical), to be confirmed when the step lands.

## What

- **The forms' work is plain functions** (`apps/web/src/server/sign-in/flows.ts`) of the form's fields, the browser's cookies (a small `CookieJar`) and the ports, tested without a server on the sign-in stand-in (`flows.test.ts`). Next.js server actions (`actions.ts`) call them and send the browser where they answer. The forms are plain HTML forms and work with no script; Next.js refuses an action posted from another site (its `Origin` must be ours), so every change comes from our own pages (T4 §5). Google's return (`/signin/google`) is a route of its own.
- **The screens:** `/signin` (email and password, Google, links), `/signup` (email), `/signin/forgot` (email), `/signup/code` and `/signup/password` (shared by sign-up and forgotten password, T-67), `/account` (devices, "sign out", "sign out everywhere", T-71) and `/account/confirm` (the password again, T-70). Their addresses are built by `platformUrl` (T-34); their words are in the message files (T-187).
- **A problem is shown by its name in the address** (`?problem=codeWrong&wait=30`, `problems.ts`), never by anything the person typed. The address being proved and, after the right code, the proof go between the screens in a cookie of their own (`srl_flow`, 15 minutes), so no email address is ever in an address bar.
- **T-68 in the web app:** asking for a code always goes on to "enter your code" with the same cookies; a wrong address and a wrong password are one problem; lock-outs answer alike. The tests compare the answers for an address with an account and one without.
- **The cookies (T-69):** all HttpOnly, `Path=/`, `Secure` when `PUBLIC_BASE_URL` is https (plain http only on this computer), and **`SameSite=Lax`**. T-69 says "not sent on requests started by other websites": Lax keeps them off every request another site starts except a plain link followed to one of our pages. Strict would make every link from an email, a chat or a search open our site signed out, and the one change Lax still lets through (a top-level GET) changes nothing here: every change is a POST, refused unless it came from our pages. T-69 (DECISIONS.md) and T4 §3 now say so (T-185). `srl_session` holds the access token and runs out 30 seconds before the token does; `srl_renew` holds the renewing token for about 13 months (the longest a browser keeps a cookie) and is set again on every renewal; `srl_device` is the device's own id (T-70), apart from any session; `srl_google` holds Google's verifier for 10 minutes.
- **Renewal is in the proxy** (`src/proxy.ts`, `renew-session.ts`). A request with the renewing token and no session cookie is renewed before any page sees it; the page sees the new token and the browser gets the new cookies. An ended session's cookies are cleared there, and so is a renewing cookie that cannot be a token (checked by its shape before the service is asked). When the service cannot be reached (renew throws), the cookies are left alone, the request is served as a visitor's and the next one tries again; a throw is never shared with other requests. No identify call is made in the proxy: the session cookie's own lifetime says when to renew. A token that still fails in a page (it ran out in between, or the session ended elsewhere) is drawn as for a visitor, and the next request renews or clears it.
- **Requests sent at once share one renewal.** The renewing token changes on every use and the stand-in allows no reuse (T-69), but a browser sends a page and what it fetches together, all with the same old token. Renewals of one token are shared, and for 30 seconds a late request with the token just used gets the same new tokens (keyed by a one-way hash, so the map never holds a working token; at most 10,000 are remembered, the oldest forgotten first). This is a small reuse window like Supabase's own; it lives in one server's memory, so two servers do not share it.
- **Signing in again on a device ends the session it had,** so the device list does not grow with old sessions. Starting or ending a session also forgets any sign-up or reset under way (`srl_flow`).
- **A place to go after signing in** is a path on this site only (`safeReturnPath`), checked as given, as the browser normalises it (`/.//elsewhere` becomes `//elsewhere`) and decoded, and checked again when it comes back from a cookie.
- **The emails (T4 §3):** the code, the new-device notice (T-70; not sent for a brand-new account) and the password-changed notice (T-85) are drawn by `packages/emails` (`sign-in-emails.ts`) and handed to the email interface (`sign-in-mail.ts`). A reset asked for an address with no account sends nothing. So that asking for a code answers alike either way (T-68), the request never waits for the email service nor learns whether it took the code: the email is drawn either way and handed over without waiting, and a failure is only reported (its kind, no address, T-86). The password-changed notice goes to the address the service holds for the account, never to one read from the `srl_flow` cookie, which the browser can change. A notice that cannot be sent never undoes the sign-in.
- **"Sign out everywhere" that cannot be done says so:** this device is signed out, and the person is asked to sign in and try again. An empty cookie counts as none.
- **The password again (T-70):** `needsPasswordAgain` (an hour since the password was typed; for an account with no password, an hour since a Google sign-in) and `passwordAgainAddress` for the sensitive actions' pages, which come in later steps.
- **The network a request comes from** (`networkAddressOf`) is believed only when the setting `TRUSTED_PROXY` says so. Next.js fills `X-Forwarded-For` from the connection only when the browser did not send one, so on its own the header is whatever the browser claims. With `TRUSTED_PROXY=none` (the default) every request shares one key (`0.0.0.0`): it fails closed, all guesses counting together. With `one`, exactly one proxy of the host stands in front of the app and appends the address it was reached from; its entry, the last one, is believed.
- **A made-up member** (`standInMember` in `stand-in-ports.ts`) is given an account through the service's own steps when the stand-in starts, so `npm run test:web` compares, over HTTP, an address with an account and one without, for sign-up, forgotten password and a wrong password.
- **The web app's stand-in runs the sign-in stand-in** of packages/providers (in memory, emails caught by the email capture). The four made-up people's tokens still work beside it, so the shell's checks can be someone with roles. The sign-in stand-in also refuses `NODE_ENV=production`, but Next.js's built server always sets that, including the test server of `npm run test:web`; the web app's own guards (APP_ENV local or test, and a site address on this computer or a `.test` name) decide instead, and the stand-in is passed the APP_ENV.

## Not done yet, and where it goes

- **Staging and production sign-in.** The Supabase adapter (record 018) is not wired into the web app: it needs the production sign-in store (devices, sessions, attempt counts, proofs; migration 0011 is reserved for it), the sending of sign-in emails on the real email service, and the database ports for staging (startup still refuses staging and production).
- **Sign-in emails through the queue.** Production should record a job for every request for a code, whether or not an account exists, and let the job send nothing when there is no code (record 013 says so of the code sender). Then the email is retried, not lost, and the request costs the same either way. Today the code email is handed over without waiting, and a failed one is lost (the person asks again).
- **`TRUSTED_PROXY=one` on the real host,** once it is checked that exactly one proxy appends the real address in front of the app. Until then every visitor's guesses count against one network key, so the per-network limits (30 codes an hour, 100 wrong guesses in 15 minutes) apply to the whole site at once.
- **The shared renewal is per server.** With more than one web server, a renewal race between two servers ends the session; the production store (or the vendor's own window) has to cover it.
- **Reading the codes in local work.** The stand-in's emails are kept in memory only; a developer cannot yet read a code on this computer. A folder for the capture (it can write files) or a local email page is a small follow-up.
- **The header's account button** (P6 §6) still says "Sign in" for everyone; it comes with the member pages.
- **A bot check in front of sign-in** (T4 §6) is not built.
