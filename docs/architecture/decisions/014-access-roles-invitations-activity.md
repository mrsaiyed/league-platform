# 014 — Roles, invitations and the activity log

Date: 2026-11-13. Step 1.12; decides T-226 and narrows T-221 (record 008); carries out A-3, O-7, A-6, T-74, T-75. Decided by the lead (technical).

## What

- **Where:** `packages/core/src/modules/access/` (roles, permissions, scopes, the permission check, invitations, grants, the activity log), with its queries and stores in `packages/database` (`src/queries`, `src/stores/access-store.ts`, `src/stores/activity-log-store.ts`). No table changed: the tables are those of 0004.
- **Roles are data.** `roles.ts` names every permission (T4 §4) and which role holds which, from P4 §4. The owner is `leagues.owner_account_id`, not a grant, and holds everything; an admin holds everything but `league.payout`, `league.transfer_ownership` and `league.delete` (O-7). Every module's policy calls the one check, `hasPermission(context, tx, permission, scope)`, which reads the owner and the account's grants inside the command's own transaction on every call, so removed access is gone on the next command (T-75). A league in the bin has no owner to read, so nobody may do anything in it, the owner included. The leagues module's settings commands now need `league.settings` instead of "is the owner".
- **Scope.** A grant is for the whole league or one program (clubs and teams once their tables exist). A league grant reaches everything; a program grant only its program. Managing access is itself scoped: a program's admin may invite to, re-send, cancel, remove, and list the people and activity of that program only.
- **Invitation links (T-226).** The link carries 32 random bytes (43 URL-safe characters). Only its SHA-256 is stored, and the plain token exists only in the email. Inviting and re-sending record an `email.send` job (T7 §2) holding the invitation's id and nothing else, in the same transaction (T-130, T-131): the jobs table takes UUIDs and dates only, so no token could ride in it. The invitation starts with the hash of a token no one has, so no link works until the email goes. The worker (step 1.19 part 2) calls `issueInvitationLink` in a transaction for the job's league as it sends: it makes a new token, stores its hash, ends the link before, and returns the token and what the email needs; it first checks the offer again, as accepting does, and returns nothing (leaving the link as it was) when the invitation is no longer pending, the league takes no new people (in the bin, archived or suspended), its program is gone, or the sender can no longer give the role (`senderStillMay` in `policy.ts`, shared by accepting, re-sending and this). Then the job has nothing to send.
- **The worker's order (step 1.19 part 2 must follow it).** First `issueInvitationLink` and commit its transaction, so the new hash is stored; only then hand the email to the provider. Sending first could email a link whose hash was never stored if the commit then failed, and that link would never work. A job run twice (a retry after the provider took the email, or a duplicate delivery) therefore sends two emails: the second link works and the first one stops working. That is accepted (see "Revisit if").
- **Only the worker calls `issueInvitationLink`.** It makes a working link with no permission check, so the structure check (rule T-226, `scripts/structure/worker-only.mjs`, list in `config.mjs`) fails any file outside `apps/worker/`, the access module and tests that names it. The link works for 14 days from inviting or re-sending; making the link at send time keeps that expiry. Re-sending makes a new 14 days and ends the old link at once. The link is the proof: any signed-in account that holds it may accept it, once, while it is pending; someone who already has that role keeps the grant they have, and a grant made a moment ago by another request is a clean "already held", never a thrown error.
- **Accepting needs no owner-run function.** The link is a league address (built by the address helper, T-34), so the app finds the league first (`find_league_by_slug`) and accepts inside that league's normal fence. A token from another league's link is simply not found. This takes "accepting an invitation" out of T-221's list; record 008 said it would need one.
- **The offer is checked again when accepted.** The person who sent it must still be able to give that role there (an invitation with no sender is withdrawn), its program must not be in the bin, and the league must not be archived or suspended. Removing someone's access cancels the open invitations they sent that they could no longer send. **Re-sending checks the sender too:** if whoever sent it can no longer give that role there (or it has no sender), re-sending is refused with `invitation-withdrawn`, the code accepting gives, and nothing changes. Re-sending never changes who an invitation is from, so an admin who wants it sent invites afresh, as themselves. Re-sending as the re-sender instead was considered: it would quietly move responsibility for the offer, and the activity log would show a grant from someone who never invited.
- **Archived and suspended leagues (U-9) take no new people.** Inviting, re-sending and accepting are refused there with `league-read-only`; cancelling an invitation and removing access always work. A safe default for now; the lead has asked the founder whether the owner should be able to invite helpers into an archived league.
- **Expiry is the database's clock.** Queries work out pending, expired, accepted or cancelled with `now()`, and accepting checks `expires_at > now()`, and that the link is still the one it was found by, in the same update. No caller's clock decides, two people using one link at once cannot both get in, and a link re-sent a moment ago no longer works. Not checked under true concurrency yet: PGlite has one connection (see `access-review.test.ts`).
- **One open invitation per person, role and place.** A unique index on `invitations` would say it in the table, but that needs a migration. Until then the check takes a transaction-long advisory lock on that question first, so two such invites at once run one after the other.
- **The activity log (A-6).** Every command that changes a league's settings or who has access writes one entry in its own transaction: the actor, the command's name as `action`, the target, and `details` holding ids and fixed words only (history keeps no copies of personal details, 0004). `summary` holds a message key, `activity.<command name>`, which the page turns into words from the message files (T-187), so the log can be shown in any language later.
- **Reads for a screen use the command shape.** `access.list_access`, `access.list_activity` and `access.my_access` live in the module's `queries/` folder but are made with `defineCommand`, so each has the same permission check, transaction, log line and isolation case. They write nothing.
- **Tests.** The two-league harness has a case for every new query and command. `packages/database/src/stores/role-matrix.test.ts` runs every role against every command in the registry on the real database, with who may do what written out from the spec; a command with no row fails it (T4 §12).
- **Stage 2 permissions (step 2.13).** `roles.ts` gains the permissions stage 2's commands need, each in one area of P4 §3: `season.settings` (a season's name, dates, status, rules and roster settings; adding a season and making it current now ask for it too), `divisions.manage`, `people.import`, `schedule.import`, `venues.manage`, `games.results` (forfeit, postpone, cancel), `bin.restore`. Already there: `people.*`, `teams.manage`, `rosters.manage`, `schedule.edit`, `schedule.publish`, `games.manage` (assigning scorekeepers), `games.score` (recording a game live, as a box score or as a final score only, T6 §9), `games.correct` (reopening), `standings.adjust`. The registrar gets People including importing; the scheduler gets the Schedule area (venues, importing a schedule) and the Games area (assigning, scoring, forfeits and postponements, corrections); the scorekeeper only `games.score` and reading the schedule; season settings, divisions, teams, standings adjustments and the bin are the owner's and admins' (P4 §4). Removing something to the bin needs its own area's permission.
- **Every command names its permission (T4 §4).** `defineCommand` takes a required `permission` and refuses an empty one; the registry keeps it. It is a permission from `roles.ts` or one of two needs that are no role's: `signed-in` and `platform-staff`. A core test fails any registered command whose name is missing or unknown (`commandsWithoutRequirement`), and the check fails closed at run time too: `allows` refuses a name that is not a permission to everyone, the owner included. The role matrix rows now say the permission the spec gives each command and its scope, and who should succeed follows from a table of who holds what, written from P4 §4 in the test; a command whose own named permission is not one its rows need fails. The matrix gained a program-scoped scheduler.

## Considered

- **An owner-run function for accepting** (record 008's plan): needed only if the league were unknown, and it is not. A function that can see every league's invitations is a wider door than the fence we already have.
- **The token in the job's ids** (this record's first plan): the email job held `invitationId` and `token`. Step 1.19 made the jobs table take ids only (UUIDs and dates), and a token kept in a job stays readable after the email is sent. `issueInvitationLink` is a step of the worker's job, not a command: it is not in the command registry, so no request can reach it, and it needs no context that tells the worker from a visitor.
- **Accepting only from an account with the invited email:** safer against a forwarded link, but P4 §4 says the person signs in or creates an account and is in, and people often sign in with a different address. The link is single-use, expires, and can be replaced.
- **A separate read shape for queries:** nothing it would add yet; the command shape already gives the check and the log.

## Revisit if

- An invitation should keep one link across retries (for example if a retried send gives two emails and people use the first): then the send would need to remember it had already made a link, which this design avoids.
- The names on an access list are needed (the admin shell, 1.17): that still needs its owner-run function (record 008), which needs a migration number.
- An association asks for build-your-own roles (A-3).
- A migration touches `invitations`: add the partial unique index for open invitations (league, lower(email), role, scope) and drop the advisory lock.
