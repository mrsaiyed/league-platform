# 063 — Removing a league made by mistake

Date: 2026-11-15. Step 2.150 (area 5 review of 2.125 part 1), migration 0017; extends [record 057](057-making-a-league-from-this-computer.md) and answers its "Not done here: a way to remove a wrong league"; serves P3 §8 (line 116), U-9, T-45, T-52, T-220, T-201. Decides T-266. The design was proposed by the step's builder after it stopped on the history rule and approved by the lead (technical), to be reviewed by the area 5 lead before it lands: it deletes across a league's fence and opens the history rule for one call.

**Not verified against a real PostgreSQL server or Supabase.** Everything is tested on PGlite only (T-201). PGlite is one session, so two transactions racing for the lock are not tested; what makes the lock hold is tested from the catalog (below). A hosted database is used only as [make a league on a real database](../../operations/make-a-league.md) says, in a session the founder started, on the test copy first.

## Problem

`npm run league:make` writes, for a new league: the `leagues` row, its default `programs` row, its first `seasons` row, two `activity_log` rows (`leagues.create`, `leagues.create_season`, both naming our staff member), and the owner's `accounts` row when the owner had none (and our staff member's, the same way). Nothing else: no grant, job, receipt or setting. Until now nothing could take such a league away:

- `app_user` may not delete a league (0005: removal is meant to be the bin);
- `activity_log.league_id` is a required link to the league, and the log is history (T-45): `refuse_history_change` refuses every delete except through `purge_league_history`, which refuses a league that has not been in the bin for 30 days (T-220). Going around it (setting `srleagues.history_purge` by hand, or `session_replication_role`) is not allowed;
- no table could hold an entry about a league that no longer exists: every log has a required link to its league.

## What

- **`npm run league:remove`** (`scripts/remove-league.mjs`, words in `scripts/remove-league.messages.mjs`) takes `--short-name`, `--as` (your own staff email), `--db` or `--hosted`, and asks for what is missing. It is the twin of `league:make` and runs the twin's own code for everything that keeps it safe: `sourceFor` (the tracker's database guard before anything connects, `.env` refused for addresses, `--hosted` only at a terminal, nothing after `?`, the certificate checked off this computer), `openLeagueMakingTarget` (the `live_stats` check after connecting, both logins reaching the same database, "Where" from the real connection), the maker's login probes and migration check (`targetProblem`, now exported from `make-league.ts`), and `answerGoesAhead` with the hosted rule. One question more: the migration login must be able to run the removal (`probe-removal-login.ts`, gap `removal`). The question is answered by typing the league's short name **on this computer too**, never "yes"; the question does not print it. A league that may not be removed is refused before anything is asked. Every sentence it prints is in its messages file; the twin's refusals are reused with "removed" for "made" (tested).
- **Core's command `removeDraftLeague`** (`leagues.remove_draft`, permission `platform-staff`, `packages/core/src/modules/leagues/commands/remove-draft-league.ts`): the league is the context's, never the input's; the input is only the short name as typed. Errors: `league-not-found`, `short-name-differs`, `league-in-use` with what was found. Its store (`LeagueRemovalStore`) passes the database nothing but the typed name. It writes no league activity entry (there is no league left to hold one).
- **The removal runs as the migration login** (`removal-transaction.ts`): one transaction of the migration login, set to the context's league and account the way `withTransaction` sets the app's (`app.league_id`, `app.account_id`), but not switched to `app_user`. This is the one thing in the twin that the app's own login does not do, because nothing else may: `app_user` may delete neither a league nor history, and giving it that would hand it to the web app. The app's login is still required on a hosted database and probed exactly as for making, so the tool cannot be run with less than its twin's safety. Our staff member is staff for this run only, in memory, as the maker names them.
- **Migration 0017** adds, all run as their caller with `EXECUTE` revoked from everyone (only the tables' owner may run them), each first calling `require_view_of_every_league` so a role that row-level security still fences (and would count too few rows) is refused:
  - **`platform.activity_log`**, the platform's own log, in a schema of its own: `action` (only `leagues.remove_draft`), `removed_league_id` (a plain uuid, no link), `league_slug`, `league_name` (not personal), `actor_account_id` (a link to `accounts`, ids only, T-220), `details` (`ownerAccountId` only), `at`. Rows are only ever added: the same `refuse_history_change` trigger, which can never let one of its rows go (it has no `league_id` for a purge to name). Row-level security on and forced, no policy, nothing granted to `app_user`, which cannot use the schema: the lead allowed select at most; nothing in the app reads it yet, and granting usage of a second schema would weaken the existing gate (`app-role.test.ts`: "app_user may use schema …"). A staff page that reads it gets its grant in its own migration.
  - **`league_rows(league)`**: the row count of every table with a `league_id` column, each named. No dynamic SQL, which T-183's check refuses: instead a test walks the catalog.
  - **`league_removal_problems(league)`**: why the league is not exactly what the maker writes, as words (`state:live`, `in-bin`, `league-changed`, `program-changed`, `season-changed`, `activity`, `rows:public.games:3`); empty when it may go. Read-only; the plan shows it.
  - **`remove_draft_league(league, typed short name, staff)`**: refuses unless the transaction is set to that league and that staff account (`current_league_id()`, `current_account_id()`: the fence the other way round), locks the league row `for update`, says `not-found` or `short-name-differs` (compared exactly, no trimming), asks `league_removal_problems` again under the lock, writes the platform log entry, sets `srleagues.history_purge` to that league (transaction-local), deletes its activity-log rows, puts the setting back to empty on the next line, and deletes its season, program and league. Anything refused changes nothing.
  - Safe to run twice (`if not exists`, `create or replace`, `create or replace trigger`); nothing dropped or renamed (T-183).

### What "exactly what the maker writes" means, and what counts as used

The league: draft, not in the bin, `version` 1 (never changed: every update moves it, 0002), no agreement, the default wording. Its program: exactly one, the default, `version` 1, not in the bin. Its seasons: at most one, in draft, not in the bin, `version` at most 2 (made, then made current), the default rules and no statistics chosen. Its activity log: exactly one `leagues.create`, at most one `leagues.create_season`, both by the same account, nothing else. Every other table with a `league_id`: no rows at all. So each of these is "used", and refused: a game; a person; any role grant, an ended one too (the owner is not a grant, O-7); published, archived or suspended (U-9); the league in the bin; anything of it in the bin; an invitation waiting; a setting saved; its season published, changed or a second one; a rename, a new short name (its forwarding row) or any other change to the league; an activity-log entry by anyone but the maker or of anything else; a job, a receipt or a support visit. When in doubt it refuses, and a league table added later refuses until it is named (below). A published or used league is step 2.133's ("handing over, deleting and leaving").

### The owner's account

Removed only after the league is gone, in a transaction of its own, through the existing `removeUnusedAccount` (which takes the address's lock and checks the sign-in link again), and only when the database shows it was made ahead and never used (`owner-account.ts`). What the database records: the maker adds the account with an email only (`version` 1); the first sign-in links it (`sign_in_id`, written only by `account_for_sign_in`, an update); erasure empties the link but rewrites the email to `<id>@erased.invalid`; the sign-in store keeps devices, sessions and sign-ups under that same sign-in id (0012), so an account with no link has none. So it is kept when: it has a link or was erased ("it has signed in before"); it changed since it was made, or has a profile ("used"); it owns another league; it holds or held a role anywhere; it is the account of our staff member running the removal (the platform log names it); a row the code does not know of still links to it ("something else … points at it", the foreign key refuses); or it could not be read ("not told for certain"). The tool says which, before and after. Our staff member's own account, even one the maker made, is never removed: the platform log names it.

### Where the entry lives, and when

In `platform.activity_log`, written inside `remove_draft_league` in the same transaction as the delete, after the checks and before anything is deleted: it exists exactly when the league is gone. Afterwards the tool reads it back (action, league, short name, who), with how many of the league's rows are left in every table (0), whether the short name is free, and whether the owner's account is there.

## Not done here

- Two removals or a removal and a write racing on a real server: PGlite cannot run two transactions at once. The catalog tests show every insert into a league table must take a lock that the league row's `for update` blocks.
- A whole run through two real logins (as record 057).
- Removing a published or used league: step 2.133.
- A staff page that reads the platform log, and its grant.
- On Supabase, the new schema is not in `revoke_hosted_api_roles` (it handles `public`); `platform` grants nothing to anyone, and the table is revoked from `public`. Not verified.
