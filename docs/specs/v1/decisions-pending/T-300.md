## T8 — Scale, reliability and operations

| T-300 | One image, `platform.Dockerfile` (never the tracker's `Dockerfile`), runs the web app by default and the worker by a command written at its top; it copies only named paths (the root `package.json`, each workspace, `supabase/site.json`, `supabase/migrations`), runs as a user that is not root, and its own ignore file, `platform.Dockerfile.dockerignore`, lets in only those paths and never a `.env` file. Each workspace declares the outside packages its code imports (R10). GitHub builds it and starts it on every push, publishing nothing. The release command, `npm run release`, is run by a person at their own terminal, with `--hosted` and the migration login given for that one command only (never in `.env`, never a setting on the host); it passes the tracker's database guard, takes the certificate from `PLATFORM_DATABASE_CA`, opens the database through the league-making tool's own checks (`openMigrationTarget`), applies the changes with `applyMigrations`, and only when every one applied names the commit to deploy by hand; a failed change names nothing (record 101). Before applying anything it counts the games live in every league and stops above 0 unless given `--go-ahead` (T-158; 0 until T-127 is proved). Going back is the previous commit deployed by hand, the database never taken back (T-156, T-183). The host is written down as a checklist, `docs/operations/render-test-copy.md`, not a `render.yaml` blueprint, so no file in the repository can create or change a service: every setting is typed by the founder and checked by eye | Agreed (delegated) | |
