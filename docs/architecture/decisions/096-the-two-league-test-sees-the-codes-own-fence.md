# 096 — The two-league test sees the code's own fence

Date: 2026-11-23. Step 2.224 (T-294). Answers data audit 2.108's finding D-M1. Serves T-28 (every query names its league), T-61 and T-65 (the two-league test; any success fails the build), T4 §2. **Agreed (delegated)**: a technical decision taken by the builder of step 2.224, to be confirmed by the lead when the step lands. The number 096 and T-294 were reserved for this step by the lead's brief.

## Problem

The two-league test runs every case in league A's scope with row-level security out of the way ("code-only"), so that only the query's own league filter keeps league B out. For 28 queries and both read stores that run could not fail: the case put league B into the state the query looks for (its season open to the public, a game postponed, something in the bin, no draft) with a write made in the run's own scope, which in A's runs is fenced to A and finds nothing of B. With a filter taken out, the bin's purge deleted B's venue for good and the test still passed. Other cases named no target, or depended on the day the tests ran.

## What is built

- **A case may arrange its target inside the target's own fence.** `IsolationCase.arrange(inTarget, target)` runs before every run of the case (control, app, code-only, both-leagues, no-league), in the same rolled-back transaction, as the app's role with the database set to league B and B's owner; then the run's own role and fence are put back exactly. Every run of that case is judged against the database as arranged (read once per case), so the arrange's own writes are the target's starting state, not a change the run made. While it runs the rows' triggers are held (`session_replication_role = replica`): the trigger that stamps `updated_at` reads the real clock, and each run's arranged rows would otherwise differ from the reading. Row-level security still holds the arrange to league B.
- **The cases the audit named are arranged:** every public read that opened the target's season (`list-public-*`, `find-public-*`, `list-season-teams`, `list-season-stat-keys`, and every case of both read stores), postponed games (query and command), the games-needing-a-result and earlier-rounds cases, the bin (list, purge, restore of a game and of a person, "does a game name a binned part"; the target's team, sub-division, venue, court, empty venue, former player and scheduled game are put in its bin), and the draft insert (the target's draft discarded first). `find-public-team` asks for the target's team by the short name the seed made (`LeagueRecords.teamSlug`), not one read through the run's fence.
- **The harness's SQL clock is fixed.** `now()` named in a query answers `harnessNow` (2026-12-13 18:00:30 UTC) through a function of that name in a schema searched before PostgreSQL's own, set before the leagues are seeded. Column defaults and the database's own trigger functions keep the real clock (they name `pg_catalog`); the seeded support visit therefore uses the real clock, since a trigger starts it.
- **The standing check:** `node scripts/fence-filter-check.mjs` takes each league filter of a known shape out of each query file and both read stores, one at a time, runs that file's own groups of `isolation-cases.test.ts` (and a read store's, when the store calls the query), and fails when they still pass. The file is put back byte for byte after each run and read back. Excused filters live in a reviewed list in the script with a stated limit (`mostExcused`); an excuse that is in fact caught fails too, and `tests/fence-filter-check.test.mjs` (in `npm test`) fails if the list grows past the reviewed 4 or names a filter the check does not find, and holds the filters of the audit's 12 gaps in the check's reach. The four excused today are the purge's team statements (`purge-binned.ts#3` to `#6`): #3 chooses the ids and #4 to #6 act only on those ids and name the league again, so no one of them alone can reach another league.
- **What it showed:** all 12 of the audit's confirmed gaps now fail their own cases with their filter taken out (run on 2026-11-23, each in about 8 seconds, the file put back after each).

## Choices made here

- **Arrange per case, not one changed seed.** Opening B's season or emptying its draft in the seed would change what every other case, and every other test using the seed, starts from. A per-case arrange touches only the cases that need it and keeps each case's name and file (other lanes add cases to the same files).
- **Where the standing check runs (for the lead to decide).** One test process per filter, about 8 to 12 seconds each; 215 filters of a known shape in 187 files today, so a whole sweep is 30 to 45 minutes. Recommended: not in `npm run verify`; in GitHub's check alone, as its own job, or nightly, with the gap queries run in the gate by name. Not wired into either here.

- The whole sweep has not been run: only 25 files (the 12 gaps and the audit's other named cases).
