# 056 — Who sees players' names: the two privacy settings, a confirmed value and the person's request

Date: 2026-11-14. Step 2.126 (part 1); answers the 2.105 audit's finding H2; serves T4 §7 (T-81), T5 §6 (T-98), R-14, R-15, R-17, R-23, R-24, R-25, R-26, R-27. Decided by the builder of step 2.126 for the lead (technical). T-259. Corrected the same day after the step's review: three choices for names (R-24), a child's request always honoured (R-25), protective changes in a read-only league (R-26), a recorded request that keeps taking effect (R-27), and each game surface told who plays in the league.

Extended by record 065 (step 2.162, R-29): the names setting is now followed for every player, an adult league starts on full names, and a stored full names is always a confirmed one. Where this record says the setting decides only how children are shown, record 065 is what holds.

## Problem

Step 2.11 built the one name function (`showName`) and the display policy it applies, but nothing set the policy: every public page, live message and statistic read the fixed starting value `defaultNamePolicy`. No setting held the league's choice (R-14, R-15), no command wrote a person's own request to `people.visibility` (R-23), and switching to full names had nowhere to ask the admin to confirm that the league has the permission it needs (R-14).

## What

**Two declared settings (T-98), in the leagues module's one list**, both for the whole league only, changed with `league.settings` (the owner and admins; a scorekeeper or registrar cannot):

- `privacy.publicNames`: `fullName`, `firstNameLastInitial` (the default, in every league) or `hidden` (R-24). It decides how children are shown, and a person whose age is not known counts as a child in a youth or mixed league (unchanged from step 2.11); adults are shown by full name unless they asked otherwise (R-15). Under `hidden` the name function answers "not shown, hidden": a team's roster shows the player as "#12" (`team.byNumber`), and anywhere else the player has their number and the nameless words a removed person gets ("Name not shown" in a box score, a play read as "#12", "A player (name not shown)" in the statistics, which list no numbers). A value the function does not know shows the least: hidden. A stored setting value the declaration refuses (or one written by a newer version) never reaches the function: `readNamePolicy` reads it as the default, first name and last initial.
- `privacy.playersMayAskForInitials`: yes or no, no to start (R-15). It is about adults (R-25), and it decides only whether a new adult request for initials may be recorded: switching it off takes no one's recorded initials away (R-27), and its words on the settings screen say so.

**A declared setting may ask the admin to confirm a value.** A declaration may list values in `confirm`; `privacy.publicNames` lists `fullName`. `leagues.set_setting` refuses such a value with `confirmation-needed` unless its input says `confirmed: true`, and the activity entry then records `confirmed: true`. The words of what is confirmed are the message `setting.<key>.confirm`, and the settings screen draws a box to tick from the declaration alone, so no setting is written into the screen by hand. The check is in the command, not only the screen, so no other caller can skip it. Moving to first name and last initial, or to hidden, never asks.

**A declared setting may say which way protects people (R-26).** A declaration may list its values in `protectiveOrder`, from the one that shows the most to the one that shows the least (two or more values, each once, or none). `privacy.publicNames` lists `fullName`, `firstNameLastInitial`, `hidden`. In an archived or suspended league, which is read-only (U-9), `mayChangeSetting` lets through only a change of the league's own value to a later one in that list: setting it (`leagues.set_setting`) or going back to the default (`leagues.clear_setting`) when the default is later than the stored value. The permission is still checked (`mayChangeLeagueSettings`); everything else, including the initials switch, is refused there as before.

**One read of the policy.** `readNamePolicy` (people module) reads the two settings at the league level, falling back to our starting values, and returns the `NamePolicy` that `showName` takes. It is not a command: a public page reads it with no permission. The web app reads it through `namePolicyOf` (`apps/web/src/server/name-policy-of.ts`) on the League settings screen's own stand-in transaction, and `namesShownOf` adds who plays in the league (adult, youth or mixed); a league whose audience is not known is read as youth, never as adult. There is exactly one League settings stand-in in `standInPorts`, shared by the settings screen and every public reader, and `standInAudienceOf` is the one place the stand-ins say who plays in each made-up league. Step 2.93's database-backed ports must read the same way (its done test).

**A person's request is a command.** `people.set_name_request` writes `people.visibility` (`none`, `initials` or `removed`; the column and its check exist since 0008, so no migration). It needs `people.manage` (the owner, admins and registrars, R-23), refuses a person in the bin and a stale version (T-46), and writes nothing when the request is already that. `people.update_person` cannot write `visibility`: its input has no such field, so one sent is dropped, and one sent alone is refused as invalid.

- R-25, in the one policy function (`mayRecordNameRequest`, asked by the command): a new request for "initials" is always recorded for a child, or a person of unknown age in a youth or mixed league, whatever either setting says. For an adult it is recorded only while the league lets adults ask; otherwise the command refuses it with `initials-not-offered`, worded "This league does not offer initials for adults, so nothing was changed. You can still choose "removed"…", so no request is saved to do nothing. "Removed" always works for everyone (R-17). To know who is a child the command reads the person's age (every role holding `people.manage` may also read sensitive fields, P4 §4), the league's audience (`PeopleStore.leagueAudience`, the query `findLeagueAudience`, unknown read as youth) and the league's own name settings (`PeopleStore.leagueSettingRows`).
- R-27, in `showName`: a request once recorded keeps taking effect until that person's own "Show as" is changed, whatever happens later to the league's initials switch or to the person's age (a child who asked for initials and is later recorded as an adult stays initials). It still never shows more than the league's choice: a recorded "initials" in a league set to hidden shows hidden. Saving the value a person already has is not a new request: the command allows it and changes nothing.
- R-26: in an archived or suspended league a request that shows less than the one kept (none to initials or removed, initials to removed) is still recorded; one that shows more is refused as `not-allowed`, as any change there is.

**The reason is one of a fixed list, and always required (R-23).** R-23 keeps the reason in the activity log, and the activity log holds ids and fixed words only, never personal details (A-6, 0004). A typed reason ("her mother phoned") would put personal details into history that is never changed or erased. So the reason is `personAsked`, `guardianAsked` or `leagueDecided`, and the entry's details are `{ showAs, reason }`.

## What obeys what today

On the web app's stand-in (the made-up leagues the app runs on until step 2.93):

- **The initials switch decides only what the command accepts, never what is shown (R-27).**
- **The names setting, saved by the admin on League settings → Privacy, reaches every public surface that shows a name:** a team's roster (team page), the statistics (statistics page and a team page's statistics), a game's page (box scores and plays), the game's snapshot (`GET …/games/{game}/snapshot`) and the live message sent after each play. Each surface takes who plays from the league. The made-up adult league has one child, Pia Hawkins, so the setting shows on its game surfaces too.
- **A person's request set by the command reaches no public page yet.** The command writes `people.visibility` in the database and in Admin → Teams' stand-in, but the stand-in rosters, statistics and tracker keep made-up requests of their own (for example a removed player on one roster). The database's public queries already hand `people.visibility` to the one name function (`list-public-roster.ts`, `list-people-for-display.ts`), so a request reaches a surface as soon as that surface reads the database: the rosters and statistics with step 2.93's teams and statistics parts, then step 2.146 (which also builds the "Show as" control and the browser checks); the game page, snapshot and live messages with step 2.93's games-area and tracker parts.

## Not done here

- Requests reaching the public pages: steps 2.93 and 2.146, as above.
