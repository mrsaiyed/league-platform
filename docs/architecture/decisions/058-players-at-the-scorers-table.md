# 058 — Players at the scorer's table: in the tracker's own queue, and a rosters address

Date: 2026-11-14. Step 2.117 (part A); answers the 2.107 audit's finding H1 (the server half); serves P7 §2 and §5.2, S-5, S-6, S-34, S-37, S-44, S-45, T6 §3 and §4, T-87, T-127. Decided by the builder of step 2.117 for the lead (technical). T-261. Corrected the same day after the step's two reviews (an independent code review and the area lead for live scoring): S-44 and S-45 decided for you by the lead, migration 0015, and the fixes below.

## Problem

A scorekeeper could not put a player into a game. No command added a person to a team from a game, the server refused any tap naming someone not on the roster, a person needed a first and a last name, and the device received the rosters once, with the page (record 054). A school arriving with eight players and no roster here, in a gym with no Wi-Fi, could not be scored at all.

## What

**The changes travel in the tracker's own queue (protocol version 2).** A batch now carries, besides the taps, three commands of the door's own (`TablePlayerInput` in `packages/contracts/src/tracker-protocol.ts`), each with a command id and the moment it was made, like a tap:

- `add-player`: a side, a random (version 4) id the device makes, a jersey (0 to 99 or 00, or empty) and a name typed in one box (empty for number only). One of the two is needed (S-34).
- `change-player`: a side, the player, and a new jersey (empty takes it away) and/or a new name.
- `remove-player`: a side and the player.

The server (`games.apply_tracker_commands`) handles each before the engine, in the batch's order, in the batch's transaction, and the engine never sees them (`packages/core/src/modules/games/table-players.ts`). Each one taken is kept as one of the game's events (`game_events`, type `add-player` and so on), so a retry, a replayed queue or a saved copy uploaded later is answered `duplicate` like any tap (T3 §12, T-129). A player added with no signal is on the team before the plays that name them, because the queue sends in order and the server applies in order; the rosters the batch holds are changed as it goes, so a lineup in the same batch can name the new player. The lines the batch started with are worked out from the rosters as they were, so a number changed in the batch is written to the lines it reaches. Nothing is taken after the game was ended earlier in the same batch (`game-over`), as the engine takes no tap then.

**Who may.** Whoever may score this game (`mayScoreGame`, read fresh, asked once for the batch), for its two teams only: the side names the team. A device that no longer holds the game, a game that cannot be scored now, someone who may not score it (a scorekeeper of another game where only those assigned score, another league's admin, a visitor) are refused as for any tap.

**What each does.**

- _Adding_ makes a new person with the device's id (the name tidied first, NFKC and spaces, then the first word as the first name and the rest as the last name; both empty for number only) and puts them at the end of that side's team's roster as a player, naming the game (`added_at_game_id`) and marked to review (`needs_review`), the columns of migration 0010. S-6's starting setting is "allowed and flagged", so the mark is always set; step 2.71 adds the league's other two choices. **S-44:** a number already worn never refuses the player: they are taken, and, where the season wants unique numbers, the answer is `accepted` with a notice (`jersey-also-worn`, with `wornBy`); elsewhere repeated numbers are allowed and the screen marks them itself. Migration 0015 makes the database's unique-number check leave out an entry still waiting for review, in both directions, and run when the mark is cleared, so the season's rule applies when an admin confirms the player (step 2.71) and on the league's own roster screens. The admin's Teams screen marks a number worn by two players on both.
- _A number_ is changed for any current player of the team (S-37). In a season that wants unique numbers, a change to a number someone on the team wears (a player waiting for review included) is refused (`jersey-taken`); the command looks itself, as the database leaves out players waiting for review. It is the team's roster number, so this game's lines and the games after it carry it; games already played keep the number they were played in.
- _A name_ is changed, **S-45**, only for a player added at a scorer's table and not yet reviewed by an admin (`on-team-roster`, `reviewed` otherwise). The name the player was first given is kept on the person (`people.previous_first_name` and `previous_last_name`, migration 0015), written by the first rename only, so later renames never lose it; an admin's review can show it and put it back. It is a personal field like the name, emptied with it on erasure, and it never goes into the activity log or the game's events. The player still waits for review after a rename (only such a player may be renamed), so the review sees it. A change that would leave a player with neither number nor name is refused. A change of number and name in one command is written together, in one savepoint, or not at all.
- _Taking off_, **S-45**, is for the same players only, added at this or an earlier game's table: their roster entry goes, and their person goes to the bin (T-45) when nothing else holds them (no other entry, no account), so it can be brought back. A player any play of this game names, judged by the batch's own state (on its list of plays or waiting to be redone), is kept (`has-plays`), so their box score line never vanishes; one with a line in another game is kept too, saying so (`has-lines`). This game's stored lines follow its plays at the end of the batch once it has an engine state; while it has none (only players added at its table, its box score entered from paper), a line of this game keeps the player too (`in-box-score`), so no line is left for a person in the bin.

**Refusals the tracker can word.** Each refusal is the code `rule` (it is about that one command, so the queue sets it aside and sends the rest, record 024) with, in version 2 only, a fixed `problem` (`contracts`: `tablePlayerProblems`). A play naming someone not on the team says which (`not-on-team`, `playerId`). When an add is refused (an id already used, a name that cannot be kept), every later command that names that player while they are not on the team, in that batch or a later one, is refused as `player-not-added`, with `playerId` and `follows` (the refused add's command id), so the screen can group them under it. The refused add is kept for the game without a table change: as one of its events, of the type `add-player-refused`, holding the side, the player's id and why, never a name (`listRefusedAdds`). So a retry of it is refused again the same way, never answered as a duplicate, and it is no play. An add is always looked at itself, so a corrected add with the same player id, in the same batch or later, adds them. `wornBy` is `{ playerId, jersey, name }`, the name as the scorekeeper sees it on the rosters, cut by the server to what the reply's schema allows (201 UTF-16 units), whole characters only: a name the database keeps (100 characters a part) can be longer in UTF-16 units, and a reply the device cannot read would be asked again for ever. The rosters reply allows 200 units a part for the same reason. `message` is for the log and holds no name. A reply to a version 1 batch carries none of these fields, so a tracker opened before reads it as it always did (T-127).

**Nothing holds the queue up.** A refused statement would end the whole transaction, and an error the server does not answer becomes a 500 the device retries for ever, blocking every later tap. So every write of a change of players runs in a savepoint of its own (`packages/database/src/queries/in-savepoint.ts`), and a refusal the database gives no known name to is that one change refused (`not-saved`), never an error for the batch. A name is tidied before it is measured, and measured in characters as the database counts them, so it can never grow past the database's limit on its way in (`name-not-readable`).

**No answer tells another league's ids apart (T-65).** A device-made id must be a random (version 4) UUID; every id the platform makes is version 7. Any other id is answered `player-id-taken` without looking, so whether it is someone's, in this league or another, never shows. A random id that collides with another league's walk-up is refused by the database (`people_pkey`): the role matrix proves it is refused and nothing is written in either league. The two-league harness cannot hold this case, and says why: the answer differs from the one the same id gets where no one holds it, so it tells the device that the id is someone's. That is unavoidable while the device makes the id (people's ids are unique across leagues), and it needs the id already, 122 random bits that never leave the league they belong to.

**Events keep no names.** A change's event holds ids, the side and the number (`named` / `renamed` as yes or no), never the typed name: events are history that is never changed, and a name must stay erasable (T-52). Each change is also logged (A-6) under `games.apply_tracker_commands` with ids and fixed words ("Changed a team's players at the scorer's table").

**They are not plays.** `gameHasPlays` leaves their types out (`tablePlayerCommandTypes`), a batch of them alone saves no engine state (an existing state still moves on with the events' numbers, which the next batch reads from `lastEventSeq`), and reopening decides "tracked" by plays. So a game with only changes of players can have its box score entered from a paper sheet and reopened with a reason, keeping every line. The database still refuses to put such a game in the bin (`check_game_bin_unscored` counts any event); changing that is a migration, left until someone needs it.

**An older tracker is still understood (T-127).** Version 1 batches are read by their own schema (`CommandBatchV1`, taps only) and answered as before; version 2 is the current one. The device's queue stores each tap with the version it was made under, so taps stored before the release go out as version 1 and new ones as version 2.

**A number-only person.** `people.first_name` and `last_name` already allow empty (0008, for erasure). The people commands still ask an admin for a name, and F-13 (the Al-Hadi transfer) is unchanged. The one name function already answers "no name" for such a person (`showName`, `no_name`); the pages word that as "#12": a team's roster, a game's box score (`PlayerRef.unnamed`, and `unnamed: true` on a snapshot's player) and its plays, the admin's Teams screen and box score grid (its checkbox's spoken label too). A name withheld (removed, hidden, a team for staff only) is still said to be withheld. S-34 says "#12" everywhere; the statistics, which list no numbers (record 056), still show such a player as "A player (name not shown)" until step 2.146.

**Pages read past fields they do not know.** `SnapshotPlayer` was a strict shape, so a page opened before `unnamed` existed rejects any snapshot carrying it. A page now reads snapshots and live messages with the contract's reading schemas (`GameSnapshotReading`, `LiveMessageReading`), which leave out a field they do not know at every level; the server still checks what it sends with the strict ones. This cannot help pages opened before it: they keep refusing such a snapshot until reloaded, and keep the players they had.

**The rosters address.** `GET /api/v1/leagues/{leagueId}/games/{game}/rosters` (`apps/web/src/server/tracker-rosters-endpoint.ts`) answers whoever may score the game with `TrackerRosters`: the game's two team ids, how it is recorded, its status, whether the season wants unique numbers, and both rosters' players with names and numbers, those who left marked, and for each whether they were added at a table, at which game, and whether they still wait for review, so step 2.118's panel knows which name boxes to open and which rows may go. Never cached. It runs `games.read_tracker_rosters`, step 2.33's command with these fields added: merging lane 2.33 must keep this copy and make its page hand the device the same fields. 401, 403 and 404 carry the tracker's own refusal bodies (record 039).

**The device.** The queue and its storage hold any command of protocol 2 (`BatchCommand`) and keep a refusal's `problem`, `playerId`, `follows` and the wearer's id and number, never their name (record 054); notices are kept in memory only, until `dismissNotices`. The controller never hands a change of players to the engine. There is no screen: step 2.118 adds the Players panel, which enqueues these commands, updates the device's rosters, reads this address, and words refusals and notices (the wearer's name from its rosters).

## Considered

- **An address of its own, as in the Al-Hadi tracker** (`POST …/roster`). Simpler on the server, but it needs a connection, and a player added offline would arrive after, or never with, the plays that name them: the spec promises a gym with no Wi-Fi (T6 §4, S-5). Refused.
- **A table of its own for the changes' ids.** It would keep them out of `game_events`, but needs a table, a fence, grants and its own order with the taps; the events table already gives each command once and in order. Not needed.
- **Mapping a device id to a server id.** The plays the device records next name the player by the id it made; keeping that id as the person's avoids rewriting them.
- **Refusing a number already worn when adding** (the first build). It loses every play recorded for that player with no signal; S-44 replaced it.
- **Adding someone already in the league's list to a team at the table.** Not asked for here; a player added at the table is always a new person, which the admin can merge later.

## Revisit if

- Step 2.71 adds the league's choice (S-6): read it where `needsReview: true` is set, and refuse `add-player` when the league allows none; its review shows `previous_*` and the clash.
- A game with only changes of players needs to go to the bin: `check_game_bin_unscored` must leave their types out (a migration).
- A person is erased (T-52, not built yet): the erasure must empty `previous_first_name` and `previous_last_name` with the name.
- Notices should survive a reload of the tracker: they are in memory only today.
