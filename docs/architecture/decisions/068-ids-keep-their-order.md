# 068 — Ids keep their order on every database, and what that order promises

Date: 2026-11-15. Step 2.151 ("Ids keep their order on every database", found by step 2.149), migration 0019; narrows T-41 (T3 §1); decides T-272. Decided by the lead (technical), written by the step's builder. The area 6 lead reviews the numbers.

**Not verified against a real PostgreSQL server or Supabase.** Everything is tested on PGlite (T-201), which is PostgreSQL 18 itself built for the browser: the same functions (`set_config`, `current_setting`, `clock_timestamp`) run the same code as on a server. PGlite is one session, so "a second connection" in the tests is a second PGlite; on a server a session setting belongs to its connection by PostgreSQL's own design.

## Problem

Migration 0002 made `public.uuid_v7()`, the default of every `id`: 48 bits of milliseconds, the version, 12 bits of finer time from the clock, the variant, random bits. Its comment said ids "made one after another on one connection keep their order". That held only where the clock is finer than the time between two ids. The hosted database's clock has microseconds; PGlite's (local work, the seed, the transfer's target, every test) moves in whole milliseconds, so the finer bits were always 0 and of two ids made in the same millisecond either could sort first. Measured here: of 5,000 ids made in one statement, 2,430 sorted below the one made before; step 2.149 found 50 of 2,000 pairs of inserts reversed. Gate tests failed by chance on it: `tracked-game-end-commands.test.ts` about four runs in ten until step 2.149 fenced it, and `box-score-commands.test.ts` on one of three GitHub runs of a lane that had not touched it.

## What

**The promise, exactly (T-272).** On one connection (one database session), every id `public.uuid_v7()` hands out sorts after every id it handed out before, as long as the transaction that made the earlier one was not rolled back. Nothing is promised across connections: two connections each keep their own order, and between them ids follow the clock only roughly. Ids made outside the database are outside the promise: the made-up stand-in's (`apps/web/src/server/stand-in-world-ids.ts`, which keeps its own order in the same way) and the ids a tablet makes for its taps and for players added at the table (record 058).

**The function (0019).** The same layout, still the default of every id, replaced in place with `create or replace` (nothing dropped or renamed, T-183; safe to run twice). It reads the clock as one 60-bit time part (milliseconds times 4,096 plus the fraction in 4,096ths), and remembers in a setting of the session, `srleagues.uuid_v7_last`, the last time part it gave. When the clock reads the same or earlier (the same millisecond on PGlite, the same instant on a fast server, a clock stepped back) it gives the last time part plus one: a count within the millisecond (RFC 9562 allows a counter there, method 1), which carries into the next millisecond after 4,096 ids. So the time part is never earlier than the clock, and runs ahead of it only while more than 4,096 ids a millisecond are made (about 25 a millisecond is what PGlite manages).

Why a session setting: it is the one piece of memory PostgreSQL keeps per connection that both PGlite and a hosted PostgreSQL have, that any role may write (a setting whose name has a dot, as `srleagues.history_purge` already is), and that needs no table, no lock and no write to disk. A sequence or a table would be shared by every connection, so a lock on every insert, and still no order across connections; a temporary table would have to be made on every connection before its first insert. PostgreSQL 18's own `uuidv7()` keeps this order too, but the hosted database may run an older version, and one form tested once serves both.

What it leaves behind:

- **A rollback** takes its change to the setting with it (PostgreSQL undoes a session setting made in a transaction that rolls back), so the next id may repeat a time part a rolled-back id had. Harmless: those rows do not exist, 62 random bits keep every id unique, and the next id still sorts after every id of the connection that does exist (tested).
- **A connection pool** that hands one connection to many requests: the memory is the connection's, so ids stay in order across those requests. A pool that resets connections (`RESET ALL`, `DISCARD ALL`) clears the memory, and ids follow the clock alone until the next is made (tested).
- **Volatility.** Still `volatile`; now `parallel unsafe`, since it writes a setting and a parallel worker may not: a query that calls it runs without parallel workers. Inserts never use them. As a column default it is called once a row in insert order, so a multi-row insert, `insert … values (…), (…)` or `insert … select … order by`, gets increasing ids in row order (tested).
- **Cost**, measured on PGlite on this computer while other lanes were running (100,000 ids in one statement, six runs of each, alternating): before 3.7 to 5.0 seconds, middle about 4.3 (about 43 microseconds an id); after 3.5 to 5.7 seconds, middle about 5.1 (about 51 microseconds an id), with one run of 9.4 seconds taken while the machine was busiest. About 8 microseconds more an id, a fifth more; an insert of a row costs far more than that.

## Every query that orders by an id

Found in `packages/database/src` (queries, stores, sign-in, league-making, transfers) and in the SQL functions of `supabase/migrations`; the stores order nothing themselves, and no migration has a view. Ordering by a link to another table's id (`team_id`, `person_id`, `game_id`) counts too: the box-score test failed on one.

The rule used to mark them: ordering by `id` is a fixed order that never changes (ids are never changed: the update trigger of 0002 refuses it). It follows creation order where one connection made the rows, and between connections it follows the clock to a 4,096th of a millisecond on the hosted database. PGlite runs one session, so on PGlite every row is made on one connection. So a query is **safe** when either its rows are made on one connection, or the order is only there to be the same every time (a display tie-break after a name, a sort or a time, or a set whose order the caller does not use). It would be **not safe** only where the order must say which of two rows written by two connections at the same moment came first; each such list already orders by a real ordering column. **None needed changing, and no query was stopped on.**

## The two tests that failed by chance

- **`box-score-commands.test.ts`** ("shows the sheet, refuses a tracked game, and is corrected by reopening", about line 252): the sheet's lines come back by `team_id, person_id`, and the test expects the home team's line first. The two teams are made one after another on the test's one PGlite connection; before 0019 they shared a millisecond often enough for the away team's id to sort first. Now the home team's id always sorts first, whatever the clock: the failure is impossible. Nothing was changed in the test.
- **`tracked-game-end-commands.test.ts`**: step 2.149 made the comparison not depend on which team's id sorts first (the standings table sorted by team; a second season whose away team is made first), and picked up each activity log entry as it was made. All of that stays: it still proves the result does not depend on the id order. One thing was plainly redundant and is removed: `nextMillisecond()`, which waited for the clock to move between the two teams so their ids would sort in the order made; ids made one after another now do, and the test still checks it (`g.homeTeamId < g.awayTeamId`, `right.awayTeamId < right.homeTeamId`). The last check of the log is made stricter: the log's own order (`at, id`) must now equal the order the entries were made in, not only hold the same entries, since on one connection entries with the same `at` are ordered by an id that keeps its order. Its comments are corrected.

Each was run 30 times in a row in this lane after the change (the counts are in the step's report).

## What else was considered

- **Waiting for the clock to move** (a loop until the next millisecond, as the test did): costs up to a millisecond an id on PGlite.
- **A sequence or a counter table**: shared by every connection, so a write and a lock on every insert, and it would promise an order across connections it could not keep (two transactions commit in another order than they took their numbers).
- **PostgreSQL 18's `uuidv7()`**: keeps the same order on one connection; the hosted database may be older, and two forms would be two things to test.
- **Ordering every list by `created_at` instead of `id`**: `created_at` is the transaction's start time, the same for every row of a transaction, so it is coarser than the id, not finer.

## Revisit if

A list ever needs the exact order in which two connections wrote rows at the same moment (a second writer to a game's events outside the game's lock, say): it gets a real ordering column taken under a lock, not a promise from the id. Or the hosted database moves to PostgreSQL 18 and its own `uuidv7()` is preferred: then 0019's function may be replaced by a call to it, with the same promise and the same tests.
