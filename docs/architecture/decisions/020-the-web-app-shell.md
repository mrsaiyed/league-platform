# 020 — The web app shell

Date: 2026-11-13. Step 1.17; carries out T-3, T-25, T-30, T-34, T-60, U-6 and U-9 in the web app; decides T-232. Decided by the lead (technical).

## What

- **Next.js 16.4.6 with React 19.3.1**, exact versions (`@types/react` 19.3.0), App Router, built with Turbopack, in `apps/web` with the folders of T2 §4. 16.4 is the current line; 16.4.6 is its newest patch, taken for its fixes. `npm run dev:web`, `build:web` and `start:web` run it through `scripts/web.mjs`, which switches Next.js's anonymous usage reporting off so nothing leaves the computer.
- **Types are checked by the gate, not by Next.js.** The repository uses TypeScript 7, which has no JavaScript interface for Next.js's own check, so `typescript.ignoreBuildErrors` is on and `npm run typecheck` checks `apps/web/tsconfig.json` instead. That file resolves imports as a bundler does (`moduleResolution: Bundler`), because Next.js's `next/navigation` and friends have no package export map.
- **The address as it arrived.** Next.js hands pages the address already decoded, but `context.ts` must see it as it came (capitals, `%2D`, U-7). `src/proxy.ts` runs before every page and writes the raw path and query into the request header `x-srleagues-path`, overwriting any header of that name the browser sent; `server/request-facts.ts` reads it with the Host and the session cookie (`srl_session`, which step 1.14 sets).
- **One answer per request, then one per page** (`server/league-gate.ts`). The request is worked out once: its context, and what the signed-in person holds in the league, read by the access module's own `myAccess` query (one request id, one read, React `cache`). Each page then gets its answer: shown, not found (404), forwarded (308) or "you do not have access" (403). The 403 is Next.js's `forbidden()` with its `authInterrupts` setting, and `app/forbidden.tsx` says it.
- **Pages refuse; layouts do not.** Every page calls `loadLeaguePage`, because Next.js does not draw a layout again when moving between pages under it, so a check only in a layout could be passed by. Layouts call `leagueView`, which never refuses: when the page may not be shown they draw only the page, whose refusal replaces them, so nothing of the league (its notice, the admin's navigation) is drawn for someone refused.
- **A refused page is filled in by the browser.** Next.js 16.4 answers `notFound()` and `forbidden()` with the right status (404, 403) and a near-empty page that its script fills with `not-found.tsx` or `forbidden.tsx`; it does so for the simplest page too, with or without `authInterrupts` (tried while building this). An address that matches no page at all is drawn by the server. Without scripts, a refused page is blank but keeps its status and `noindex`.
- **What is shown to whom** is core's, as data: `openAdminAreas` (the areas a person's roles use, at any scope, P4 §3–4) and `mayOpenLeague` (U-9) in the leagues module. The admin's navigation lists only the open areas. Any address under the admin, or the tracker, without access is "you do not have access", signed in or not (U-6); a draft or suspended league is "not found" to everyone who does not run it, and so is a former short name of it.
- **"The people who run it" are those with at least one area of the admin**: the owner, admins, registrars, schedulers, editors, scorekeepers and club admins. Coaches and captains, who do not use the admin (P4 §4), see a draft league once it is published. U-9 says "only admins can see it"; this reads "admins" as everyone who works in the admin, so a scheduler can build the schedule before launch.
- **Startup** (`server/startup.ts`, run by `src/instrumentation.ts` before the server serves anyone). Settings are checked (T-30). `APP_ENV` local or test runs on a made-up stand-in (`server/stand-in-ports.ts`: six leagues in every state, four people, no database, no sign-in service), which refuses to be made for anything else. Staging and production open `DATABASE_URL` and call `checkLoginRole` first (T-60), stopping on any problem; then they stop anyway, with a plain reason, until sign-in on the real service is wired (steps 1.14 and 1.15). Until then a made-up person is "signed in" when the session cookie holds one of the stand-in's made-up tokens.
- **The database package is loaded by Node.js, not bundled.** `container.ts` loads `@srleagues/database` at run time, past the bundler: Turbopack could not follow the migration runner's folder on disk. Node.js runs the package's TypeScript as it is, as the tracker does, so it may use only syntax that can simply be erased; one constructor parameter property in `guarded-dialect.ts` became a plain field.
- **The check against the built server** is `npm run test:web` (`scripts/check-web-shell.mjs`): it builds, starts the server on the stand-in, asks 29 addresses as five made-up people and checks the status, the refusal made, the words and the forwards, checks that a browser-sent address header is not believed, and checks that staging with a database that answers nobody refuses to start without printing the address. It is not in `npm run verify` yet: building takes a minute or two more on a gate already run by several lanes at once.
- **Next.js also builds `instrumentation.ts` for its Edge runtime** and warns that `process.exit` and `node:crypto` are not there. Nothing here runs on Edge; the warnings are left rather than reading `NEXT_RUNTIME` outside `config.ts` (T-30).

## Considered

- **Next.js 15.** Still patched, but the repository's own Next.js experiment (`apps/varsity-hosted`) is on 16 and new work should not start a major version behind.
- **Reading the league from the route's `[league]` value.** Already decoded, so `%2D` and other spellings could not be forwarded (record 017); and `context.ts` would no longer be the one place an address becomes a league.
- **Checking access in the layouts only.** Simpler, and wrong: layouts are not drawn again on moving between pages.
- **Rendering "you do not have access" as an ordinary page with status 200.** Simpler than `forbidden()`, but tools, tests and search engines would read it as a page that exists.
- **Running local work on PGlite with the migrations and seeds.** Closer to production, but the seeds are step 1.21 and PGlite runs as a superuser, which `checkLoginRole` rightly refuses. The stand-in answers through the same `myAccess` query.
- **Putting the build in the gate now.** Wanted; left for the lead to switch on (one line in `verify`) when the lanes' load allows, or with step 1.23 (CI).

## Revisit if

- Next.js makes `forbidden()` stable, draws refused pages on the server again, or changes `proxy.ts` again.
- TypeScript 7 gains the interface Next.js's own check needs.
- Sign-in arrives (1.14, 1.15): `identify` moves to the sign-in service, staging and production get their database ports, and renewing a session replaces "draw it as for a visitor".
- The founder reads U-9's "admins" more narrowly (only owner and admins): change `mayOpen` in `league-gate.ts` to ask for `league.settings` instead of any area.
