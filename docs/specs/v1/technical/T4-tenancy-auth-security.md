## 2. Keeping leagues apart

All leagues share one database (T-4), so separation is the most important property of the system. It is enforced three times over, so that one mistake is not enough to break it.

**Fence 1 — the request.** For every request the server works out, from the session and the address, _who_ is asking and _which league_ they are asking about. This "context" is built in one place (`server/context.ts`) and passed to every command and query. Nothing the browser sends can set it.

- **T-229: where the league is in an address.** A page's league is the first part of its address, and a page is served only at the league's short name exactly as stored: other capitals or encodings (`%2D` for `-`) forward to it, like a former name (U-7). The forward carries the league's state, so a draft or suspended league is forwarded only for those who may see it and is "not found" for everyone else (U-9). Only our own words, not the offensive ones on the blocked list, mean one of our pages. A JSON endpoint about one league is `/api/v1/leagues/{leagueId}/...`, built by `leagueApiUrl`: the id never changes, so a tracker's queued commands survive a change of short name, and `server/context.ts` reads that league in its own transaction, so handlers get their league in the same one place as pages. [Record 017](../../../architecture/decisions/017-the-league-of-an-endpoint.md).

**Fence 2 — the code.** Every database function that touches league data requires a league ID (T-28). There is no function that reads "all teams"; only "teams of league X".

**Fence 3 — the database itself.** PostgreSQL row-level security is switched on for every league table.

- **T-60:** the web app and worker connect as a restricted database user that cannot change the schema and cannot bypass row-level security. The one thing the worker's login may change is the job library's own schema, which holds job ids only and which the app's role cannot use (T-257, [record 053](../../../architecture/decisions/053-the-worker-starts-and-who-makes-pg-boss-tables.md)).
- **T-61:** at the start of each transaction the app tells the database which league and account it is acting for, for that transaction only. Every table's policy allows only rows whose `league_id` matches (for `leagues` itself, its `id`), for reading and writing alike. A query that forgot its `WHERE league_id = ...` returns nothing from other leagues, because the database filters it anyway; a transaction that set no league sees and writes nothing. A public page's reads run in one transaction opened as REPEATABLE READ and READ ONLY (`withTransaction(..., { snapshot: 'page' })`, T-274): every statement sees one moment, so a name is never shown by one setting read before a save and another read after it, and nothing there can write. Commands keep the default ([record 070](../../../architecture/decisions/070-the-statistics-and-team-pages-on-the-database.md)).
- **T-62:** tables that belong to a person and not a league (`accounts`, `profiles`, `notifications`) have policies keyed to the account instead.
- **T-63:** jobs that must look across leagues (finding today's games for reminders) run as a list of per-league steps, each inside its own league's fence. A separate, more powerful database user exists only for migrations.
- **T-64:** Supabase's feature that lets browsers query the database directly is given no access to our tables. All access goes through our web app (T-5).
- **T-221: what must happen before a league or account is known goes through a few narrow functions, never a wider policy.** Finding a league from the short name in an address, creating and erasing an account, finding an account by email at sign-in (without revealing whether it exists, T-68), and showing the names on a league's access list each get one function that runs as the tables' owner, does one job and returns the fewest columns. Each is reviewed and listed in a test that fails on any it does not know. The short-name lookup exists from step 1.7; the others came with step 2.92 (migration 0012): `account_of_sign_in` and `account_for_sign_in` (which of our accounts a signed-in person is; the second finds, links or makes it and never says which), `create_own_profile`, `erase_account` and `access_list_names` ([record 052](../../../architecture/decisions/052-accounts-on-the-real-database.md)). Accepting an invitation needs none: its link names the league, so it is accepted inside that league's fence (T-226). **T-269:** the leagues a signed-in person belongs to (P2 lines 67, 71 and 141) come from one more, `my_leagues` (step 2.127, migration 0018): no argument, the account set for the transaction only, its own owner, role and roster rows, no league in the bin; which of them the person may see is core's rule (U-9) ([record 066](../../../architecture/decisions/066-the-leagues-a-person-belongs-to.md)). Detail: [decision record 008](../../../architecture/decisions/008-what-the-app-role-cannot-reach-yet.md).
- **T-449, T-450 (step 2.223): one league gate for every way in.** Every league page (`resolveLeagueRequest`) and every endpoint under `/api/v1/leagues` (`resolveLeagueApi`, before any body is read) answers a league that is hidden from this person (U-9: `mayOpenLeague`), in the bin or not there with the same "not found", after the same reads in the same order: a signed-in person's access is read for a missing league too, for an id no league has. The endpoint is handed the access the gate read. A session that no longer works or an account problem is answered before any league is read, the same for every league. The invitation page, not gated (an invitee must reach a draft league), reads a missing league's held invitation with that id too, and the read looks the link up before the league (T-459), so a missing league's answer, headers included, is a hidden one's.
- **T-269 (November 15, 2026; record 066): a read across the league fence for a signed-in person, and what the next one must meet.** `public.my_leagues()` lists the leagues the signed-in account belongs to; core applies the league gate's own rule (U-9) before a league's name leaves it. From the area lead's review of it: A read across the league fence for a signed-in person is a function of its own with its own decision record, never a wider policy and never a widening of an earlier function. It takes no argument that names a person or a league: it answers only for `current_account_id()` and returns nothing when that is not set. It is SECURITY DEFINER with `search_path = pg_catalog, pg_temp` and every name written in full; it calls `require_view_of_every_league()` first, so a wrongly owned copy refuses instead of answering "none"; EXECUTE is revoked from PUBLIC and the hosted API roles and granted to `app_user` only; it is on the reviewed list in `app-role.test.ts` and in the isolation coverage list. It returns only rows that are the account's own (it owns the league, holds a grant in force, or reaches the profile) and the fewest columns: no other person, no count, nothing from a league in the bin; anything it returns about a league's state before the visibility rule (a name, a status) is named in the record. The record puts every promise beside a test, with one case for each way a row qualifies (each kind of profile link, each scope) and each way it must not (revoked, left, in the bin for the league, the team and the person, another account, no account, every setting the app role can change). In the app it is reached through one port whose account is the server session's, with one caller; its rows pass core's rule (`mayOpenLeague`, U-9) before anything is drawn, and a check fails on a second caller. Every page that draws its answer is drawn per request, answers `private, no-store`, and has a browser test that a visitor's copy holds no trace of anyone.

**And we prove it continuously.**

- **T-65:** an automated test creates two leagues and, for every command and every query in the product, tries to use league A's access against league B's records. Any success fails the build. New commands are included automatically.
- **T-66:** anything cached is keyed by league, and nothing personal or private is ever cached where another visitor could be served it.

## 3. Sign-in

- **T-67: email and password, or Google** (R-2). A new address is proved with an emailed 6-digit code (valid 10 minutes, a few attempts per code, a few codes per hour per address; the numbers are T-225) before a password is set. The same code is the forgotten-password route: asking to sign up with an address that already has an account sends a code too, and finishing it sets a new password. An account made in advance for a person is linked to whoever signs in with its address (`account_for_sign_in`), which is safe only because the sign-in service confirms addresses: the web app refuses to start in staging and production unless the service says it does (step 2.115, [record 018](../../../architecture/decisions/018-the-supabase-sign-in-adapter.md)).
- **T-85: password rules.** Passwords are handled only by the sign-in service, which keeps a one-way hash; we never store, log or see one. At least 8 characters, no rules about symbols or capitals, and refused if it appears in the public lists of leaked passwords. Wrong guesses are limited per address typed (whether or not it has an account, T-68) and per network, then slowed and locked for a while (T-225), with the bot check (section 6) in front. Changing or resetting a password signs out every other device and emails the account. There are no security questions and no hints.
- **T-225: the numbers** ([record 013](../../../architecture/decisions/013-the-sign-in-interface.md)). A code is valid 10 minutes and takes 5 attempts; an address gets at most 5 codes an hour, and one network at most 30, whatever the addresses. Passwords are 8 characters (counted as characters, so an emoji is one) to 72 bytes (the one-way hash reads no further, so a longer one is refused rather than silently cut), put in Unicode's compatible form (NFKC) before anything else so the same password typed on two keyboards is one password. Wrong passwords are counted against the address typed, whether or not it has an account, and against the network; wrong codes against the network too. For an address: from 5 wrong in 15 minutes each try waits 30 seconds, and at 10 it is locked for 15 minutes. For a network: from 30 each try waits 5 seconds, and at 100 it is locked for 15 minutes. A network is an IPv4 address, or an IPv6 /64 (one household or phone usually has a whole /64). It is the address the host's proxy was reached from, or, with Cloudflare in front of the host, the visitor's address Cloudflare names, believed only on a request that reached the host from one of Cloudflare's addresses, so nothing a visitor sends changes it (`TRUSTED_PROXY`, records [031](../../../architecture/decisions/031-the-sign-in-screens-and-the-session-cookie.md) and [081](../../../architecture/decisions/081-safety-before-real-accounts.md)). Every try is counted before the password is checked, so tries sent at once cannot slip past the limit together. The access token behind the session lasts 60 minutes and is replaced on renewal; the session itself has no limit (T-70). Google may send the browser back only to our own addresses (https, or plain http to this machine in development).
- **T-230: the Supabase adapter** ([record 018](../../../architecture/decisions/018-the-supabase-sign-in-adapter.md)) calls Supabase Auth's own web API with no vendor library. It asks Supabase for each code without Supabase sending it, and sends it through our email service. It keeps in a store of its own what Supabase does not: devices, the session list, the limits of T-225 per address and per network, attempts per code. It allows no reuse of an old renewing token itself (Supabase's own reuse window is not passed on); the one window is the web app's, in front of it (T-69). It never sends Supabase a password over 72 bytes. Not yet verified against the live service; record 018 lists what the first supervised session checks.
- **T-256: our account ids stay ours** ([record 052](../../../architecture/decisions/052-accounts-on-the-real-database.md)). The sign-in service's own id for a person is kept beside our account id (`accounts.sign_in_id`) and turned into it on every signed-in request; only owner-run functions write it. The adapter's store is in a database schema of its own, `sign_in`, which only its own restricted database user reaches: the web app's user cannot read a session or a count, and the store's user cannot read a league. The web app's user may change only an account's name, phone and last-seen time; the email changes only through T-73's confirmed change.
- **T-68:** the sign-in and sign-up screens behave identically whether or not an account exists ("wrong email or password"; on sign-up "we sent a 6-digit code to {the address typed}", which is true either way since sign-up always sends one (T-67); on the forgotten-password route "if {the address typed} has an account, we sent it a code"; "Send a new code" and every limit alike), so they cannot be used to discover who has an account. Only after a right code, which proves the mailbox, does the password screen say the account exists (R-31, step 2.163).
- **T-69: the session is a cookie the page's scripts cannot read**, sent only over HTTPS, and not sent on requests started by other websites, except a plain link followed to one of our pages, so a link from an email or a chat opens our site signed in (`SameSite=Lax`, [record 031](../../../architecture/decisions/031-the-sign-in-screens-and-the-session-cookie.md)); nothing such a link can do changes data, since every change is a form posted from our own pages. Behind it are a short-lived token and a renewing token that changes on every use; an old one used again is rejected and ends the session, with one exception. A browser sends a page and what it fetches at once, all with the same renewing token, so the web app shares one renewal: for 30 seconds after a renewing token is used, a request to the same web server with that token gets the same new tokens instead of ending the session ([record 031](../../../architecture/decisions/031-the-sign-in-screens-and-the-session-cookie.md)). Its limits: a thief who uses a stolen old token within those 30 seconds, on that server, gets the session too (the person's own renewal has just made it, so the theft is of a token seconds old); after 30 seconds, or on another web server, the old token ends the session as above; at most 10,000 renewals are remembered, the oldest forgotten first, and they are kept by a one-way hash, never as working tokens. The sign-in service itself (the stand-in and the Supabase adapter, T-230) allows no reuse at all.
- **T-70: staying signed in** follows R-9: no time limit for anyone, and the session renews itself on every visit. In place of an expiry there are three protections. Sensitive actions (export, permanent deletion, roles and ownership, payout details) need the password again if it was last entered over an hour ago. A sign-in on a device the account has not used before sends an email. A password change or "sign out everywhere" ends every other session at once.
- Sign-in emails (codes, resets, new-device notices) are sent through our own email service (T-11) from their own sending address. The sign-in vendor's built-in sender is limited to a few messages an hour and is not meant for real use.
- **T-71:** the account page lists active sessions by device and time, with "sign out everywhere". This device is listed first and said to be this one; times are in the reader's own time ("today at 8:41 PM", put in by their browser; with scripts off the time is given in UTC, said as such); "sign out everywhere" asks first, with a way back, and says what it did (step 2.163, record 091).
- **T-72: a second sign-in step** (an authenticator app) is offered to league owners at launch and required for owners once a league collects money (stage 5).
- **T-73:** changing an account's email needs confirmation from the new address and sends a notice to the old one.

## 4. Who may do what

- **T-74: permissions are checked on the server, inside each command.** Hiding a button is a courtesy, not a control.
- Roles ([P4](../product/P4-admin-dashboard.md) section 4) map to named permissions in code, for example `games.score`, `games.correct`, `schedule.publish`, `registration.read_answers`, `people.read_sensitive`, `site.publish`, `league.billing`. Each command names the permission it needs and the scope it applies to (the league, a program, a club, a team).
- **T-75:** roles are read from the database on every request, so removing someone's access works immediately.
- **T-226: invitations and the activity log.** An invitation's link carries a random secret of which only a one-way hash is stored; the secret is made as the email is sent and exists only in that email (the email job holds the invitation's id, T-131). The link works for 14 days; re-sending makes a new one and the old one stops working. Any signed-in person holding the link may accept it, once, while the person who sent it can still give that role there; removing someone's access cancels the invitations they sent. The link names the league, so accepting happens inside that league's fence. No one is invited into, or joins, an archived or suspended league; invitations can still be cancelled and access removed there. Every change to a league's settings or to who has access writes one activity-log entry (A-6) holding ids and fixed words, never copies of personal details; its summary is a message key, so the log can be shown in any language. Detail: [decision record 014](../../../architecture/decisions/014-access-roles-invitations-activity.md). **T-288:** the link itself draws nothing: it holds its secret for that browser in a cookie sent only to the league's accept page and forwards to `/{league}/invitation`, which has no secret in its address, so the secret is never in the way back from signing in or in the browser's history past the link; every link that does not work (wrong, used, cancelled, run out, replaced, no league) is answered the same way, and a signed-out visitor is asked to sign in at every such address, whether a league (even a hidden one) is behind it or not, so the page never tells a stranger that a short name exists; on the made-up database the web app sends the invitation emails itself, since no worker can reach it ([record 086](../../../architecture/decisions/086-inviting-from-the-website.md)).
- **T-76:** private fields are filtered by permission in the query, not in the page. A scorekeeper's roster query cannot return a date of birth because the query for that role does not select it.

**Our own staff.**

- **T-77:** staff have no standing access to any league. To open one, a staff member records a reason; access lasts one hour, is read-only unless the league owner asked for a change, and every such visit appears in a log the league owner can see. Staff accounts require the second sign-in step.

## 5. Safe pages on a shared address

Because every league is on `oursite.com` (U-1), content from one league must never be able to run code in a visitor's browser. The same holds after the move to league subdomains (U-13), because the sign-in is shared across them.

- **T-78: no league-supplied HTML, JavaScript or CSS exists anywhere in the system.** Formatted text (news, About pages) is stored as a structured document ("paragraph, bold text, link to X") and drawn by our own renderer. There is no raw HTML to slip a script into.
- **T-79: a content security policy** tells browsers to run scripts only from us and to show embedded frames only from the approved list (C-9). Built in step 2.98 ([record 081](../../../architecture/decisions/081-safety-before-real-accounts.md)): every answer allows scripts only from our own address or with a nonce made for that one answer, no inline code and no `eval`; frames only from the bot check's origin until the embeds of C-9 are built, each origin by name; and no other site may frame our pages. Every answer also tells the browser to use HTTPS only, for a year (`Strict-Transport-Security`). A page kept by a shared cache must not carry one answer's nonce to the next visitor (step 2.176).
- **T-80: stored uploads are images only.** Every upload is decoded and re-encoded on our side (which strips anything hidden in the file), size-limited, and served from a separate web address that has no access to anyone's session. Vector logos are converted to safe form or rejected. Spreadsheets uploaded for an import are a separate path: read once by the worker, limited in size and rows, never kept for download and never served to anyone. Its text waits in the import's row only until it is read and is then replaced by the report; if it can never be read, the last failed attempt or an admin's discard replaces it with an empty failed report (T-246, record 034).
- Links supplied by admins must be ordinary web links. Our pages cannot be framed by other sites.
- Every request that changes data is checked to have come from our own pages.

## 6. Abuse

- Limits on how often one address or account can try a password, request codes, submit registrations, upload files or post in a chat. Announcements have no limit for now (N-9); the email allowance in T-141 is the only backstop until that is revisited before stage 5.
- An invisible bot check (Cloudflare Turnstile) on sign-in and public registration. Built in step 2.98 behind an interface of our own, with a local stand-in for local work and tests ([record 081](../../../architecture/decisions/081-safety-before-real-accounts.md)): in front of signing in with a password and of asking for a code (sign-up and the forgotten password), before the sign-in service hears of the request, so a refused form counts no guess and answers alike whether or not an account exists (T-68). An answer passes only if it was made on our site for that form. "Send a new code" stands behind it too. The box is drawn in explicit mode, with a fresh answer for every try. When the person's browser cannot load it, or scripts are off, or the answer is missing or wrong, the form is refused and says truly why. When our server cannot reach the check's service (4 seconds), password sign-in goes on on the attempt limits alone and an error-level log line says so; asking for a code stays closed (T-285, Q2). What leaves: the person's browser loads Cloudflare's script and frame; our server sends Cloudflare the answer and our secret key only, never the visitor's address. Production needs Turnstile's two keys; the test copy (staging) takes both or neither, and with neither runs with the check off and says so when it starts (T-270). Public registration gets it with the registration forms (stage 4).
- A "report this league" link in every league's footer, reaching us.
- The short-name rules of U-7, and the right to suspend a league (U-9).

## 7. Children's information

Product rules are in [P6](../product/P6-registration-and-accounts.md) section 7. Technically:

- **T-81: public pages get names only through one function** that applies the league's display policy (R-14, R-24, R-29: one league-level choice the admin controls among three, full names, first name and last initial, or hidden by jersey number only, followed for every player; every league starts on full names with the confirmation not given, so adults by full name and children by first name and last initial, as before; a child, and a person of unknown age in a youth or mixed league, is shown by full name only where names are full names and the admin has confirmed the league has the permission it needs; no per-guardian consent is asked or stored), the person's own request (R-15, R-17, R-25: a request for a child to be shown as initials or removed is always honoured, whatever the league's settings, and never shows more than the league's choice; an adult's new request for initials only where the league lets adults ask; R-27: a request once recorded keeps taking effect until that person's own "Show as" is changed, whatever later happens to the switch or to the person's age) and who may see the team's statistics (T-87). The person's request is the `visibility` column of `people` (T3), read by the function as `nameRequest`: `none`, `initials` or `removed`; any other stored value counts as `removed`. **T-259** (record 056): the league's choice is the declared setting `privacy.publicNames` (`fullName`, `firstNameLastInitial` or `hidden`), beside `privacy.playersMayAskForInitials` (R-15), both read by one `readNamePolicy`; **T-268** (record 065): the confirmation is a declared setting of its own, `privacy.childrenInFullConfirmed` (yes or no, no to start), read by the same `readNamePolicy`; saying yes is refused unless the admin ticks the confirmation, taking it back always works, and a child is shown in full only where both settings say so, so no other writer of the names setting can show a child in full; a test fails if anything but the settings commands writes a setting; a save of the value already stored writes nothing; the request is set by the command `people.set_name_request` (R-23), whose reason is one of a fixed list, since the activity log holds fixed words only, and which refuses a new adult request for initials where the league does not offer them (R-25); saving the value a person already has is not a new request. In an archived or suspended league only changes that show less work: a request to initials or removed, and the names setting moved toward less (R-26, the setting's declared `protectiveOrder`). No public query can select a raw name, birth date, contact field or home address; a test scans public responses for these fields and for each made-up person's private values. No public answer carries a person's or a roster place's database id (step 2.225): a game's snapshot knows its players by a key of that game only (T-462), a page's rows by their place; a test starts the app on the made-up world and on the made-up database, fetches every public page and public API answer of each league, and finds none of the ids its owner is shown (`tests/browser/public-pages-on-database-test.mjs`, part 4). A player's own public address, `/{league}/players/{player}` (P2), is not served yet: the address helper reserves its shape and no page or link fills `{player}`, so it is keyed by nothing today; when it is built its key is not a person's or a roster place's id.
- **R-33, T-478, T-479, T-480, T-483, T-484, T-487, T-488: the scoring screens show the public's names** (step 2.226). The scorer's rosters (which the scorekeeper's device stores), the score page and the box score sheet show each player by number and by the name the public sees, through the one name function; a person's own "initials" or "removed" always holds there. The league's setting "Scorekeepers see full names" (`privacy.scorekeepersSeeFullNames`, off to start, the owner and admins change it) shows everyone else in full. Two players who would read the same are told apart by their numbers; one the number and name still do not tell apart reads "Player 1", "Player 2" in roster order, so every player can be picked. The rule is one function in core (`scoringNames`), applied by the games store as it reads a game's roster, so no recorded name it keeps back leaves the store; the rosters' two name fields carry only what it gives, and the server words a place into them from the message files ("Player 1", "Player 2 · Sam L."), so the rosters answer keeps the shape it had before the step (T-483). The device drops a game's stored roster once the game is ended and every tap of it saved, and when another account signs in on it, never while the game is live or taps wait; a stored roster from before the step is not used again unless taps wait (T-484). People, Teams and the bin show the recorded name; the person's own page shows their request; "Show as" beside the name in those lists comes with step 2.146. A fresh fetch of the rosters replaces the names the device kept (T-487): a device with signal holds a name no longer allowed no longer than its next fetch, at every opening or reload and when the network comes back; a device with no signal keeps what it has until it has signal, which cannot be otherwise. A game the device forgets loses the service worker's kept page too (T-488).
- **T-462, T-463, T-465: a game's public snapshot knows each player by a key, not an id.** The key is HMAC-SHA-256 of a fixed label, the game's id and the player's id under a secret only the server holds, cut to 16 bytes and written as a version 8 UUID so a page opened before the key existed still reads it: the same all through one game, different in every other, and not to be worked back to the id. It is made in one place, on the server (`apps/web/src/server/player-key.ts`), and core is handed it. The secret (T-465) is `SESSION_SECRET` when it is set; else, where the app runs on a real database, a secret derived (HKDF-SHA-256, a label of its own) from the sign-in service's secret key, which the settings already require there; else, only on made-up data, a random one made at start: every server process with the same settings gives the same key, starting never fails for want of `SESSION_SECRET`, and nothing of it is logged. The game page's box score rows are keyed by their place in the table (step 2.225).
- **T-87: who may see statistics (S-22) is enforced in that same one function.** The cached public page and the live-update messages contain only what everyone may see; for a team whose numbers are restricted, that is the team's totals and no player lines. Viewers who are allowed more receive it in the separate signed-in request (T-95), checked against their membership on the server. A test loads every statistics page as each kind of viewer and fails if a restricted number appears. **T-287** (step 2.46, [record 085](../../../architecture/decisions/085-the-numbers-a-page-keeps-from-the-public.md)): that request is `GET /api/v1/leagues/{leagueId}/staff-numbers`, asked by the statistics page, a team's page and a game's page once they have arrived, and only where the page already says a team's players are not shown. The league is the address's, the account the session's, and the roles are read on that request: the league's owner and admins of the whole league, and a coach or captain role on that team, see that team's player lines (box score lines, season totals, leaders, names in the plays), under a note that they are not public; everyone else, a page with nothing kept back and a question that names nothing all get the one answer `{"more":null}`, so it never tells anyone that numbers are kept from them. Every answer is private and never cached; the page asks again whenever it is shown again, and takes the numbers off before the browser keeps it.
- Every public page of a league that holds a child asks search engines not to index it, whatever the league's own "do not index" setting says (U-18, decided for you at step 2.60): a youth or mixed league, and an adult league with a child recorded in it (the publish checks' test, record 065). Children's names are on the team, statistics, home and game pages, not only player pages, so the whole league is marked and no page can be missed. The mark is `<meta name="robots">` in each page's head, set once by the league's layout; every league JSON answer carries `X-Robots-Tag: noindex`, in every league (T-312, record 107).
- No advertising or third-party tracking scripts, ever. Page analytics are cookieless and count visits, not people.
- We collect only what a league's form asks for, and encourage forms to ask for less.
- The legal review in B-10 may add requirements; this section is updated when it does.

## 8. Money

- **T-82:** card details are entered only on Stripe's pages. We store Stripe's reference numbers, amounts and statuses.
- Messages from Stripe about payments are verified by signature and handled so that the same message arriving twice has no second effect.
- Refunds need the `payments.refund` permission and are logged.
- A league's payout account is the league's own Stripe account; we cannot move its money.

## 9. Keys, vendors and the pipeline

- Secrets live in the hosting provider's secret store, are different in every environment, and are never in the repository or in browser code (T-30).
- The production database accepts connections only from our servers, encrypted. The web app and the worker check the database server's certificate on every connection, against `PLATFORM_DATABASE_CA` (its text or a file's path) when it is given, else the computer's own authorities; the check cannot be switched off for a database on another computer (the web app's `PLATFORM_DATABASE_SSL=off`, for a database without SSL, is allowed only for an address on this computer, never one reached over a network), and a start-up that cannot connect says whether the certificate, the login or the server's address is at fault, or that the server answered but refused the start (with the server's 5-character code, never its words), without printing any value (T-299, record 100).
- **T-83 (agreed by the founder November 12; due before stage 2 puts real accounts into production): two-step sign-in must be on for every account that controls the business**: GitHub, Supabase, Render, Cloudflare, Stripe, Resend, the domain registrar and the email account they all recover to. The founder asked whether this could wait until after the first version. It should not: this is not something we build, it is about twenty minutes in each vendor's own settings, and a stolen vendor password is the most likely way a small company loses everything.
- The main branch is protected: changes arrive by pull request with all checks passing.
- Dependencies are pinned and scanned for known vulnerabilities automatically; updates are proposed weekly.

## 10. Records

- The **activity log** (A-6) records admin actions per league.
- A **security log** records sign-ins, failed attempts, role changes, exports, deletions and staff access.
- Logs never contain passwords, sign-in codes, session tokens, form answers or message bodies.
- **T-86:** logs and error reports carry no personal content: names, email addresses and form answers are removed before an error report leaves our servers. Application logs are kept for 90 days and the security log for one year. An export of a league's data is delivered through a link that works for 24 hours and only for the signed-in person who asked for it, and every export appears in the activity log.

## 11. If something goes wrong

**T-84:** a written incident procedure before the first outside league joins: how we notice, how we stop it, how we tell affected leagues (promptly, and within 72 hours for anything involving personal data), and a written account afterwards of what happened and what changed. Until there is a team, the founder is the named person responsible.

## 12. What must be tested before each release

| Test                                                                                                                        | Proves    |
| --------------------------------------------------------------------------------------------------------------------------- | --------- |
| Two-league isolation across every command and query (T-65)                                                                  | Section 2 |
| Every role against every command: allowed ones succeed, all others are refused                                              | Section 4 |
| Password and code attempt limits and lock-outs                                                                              | Section 3 |
| Script-injection strings in every field of every page, as each role, come out as harmless text (what is not covered: below) | Section 5 |
| Disallowed and disguised file uploads are rejected                                                                          | Section 5 |
| Public responses contain no private fields (T-81)                                                                           | Section 7 |
| A repeated payment message changes nothing                                                                                  | Section 8 |
| Browser code contains no secrets                                                                                            | Section 9 |

The script-injection test is `tests/browser/harmful-text-test.mjs` (step 2.98): an attacker's text typed through the screens' own forms into every free-text field (it fails on a field it does not know, so a new field must join it) comes out as text on every page that shows it, with the script policy switched off in the browser, so the pages' own escaping is what keeps it text. It walks every page route, listed from the app's folders, as six made-up roles (owner, scheduler, coach, scorekeeper, a signed-in person with no role, a visitor) and fails on a route, a free-text field or a field kind it does not know; it posts the attack by hand into every field a plain form holds, of every kind (number, date, time, colour, hidden, choices), and the answer must be a refusal or a harmless page; and it fetches every answer route (JSON carries the attack only as data). It does not cover, and prints by name: the draft league's own roles, text a script draws only after a tap (beyond the games list's question, the reopen form and the scorer's table), the scorer's own Reopen question (its reason is posted to the answer route by hand instead), and the policy-on check beyond the pages that show typed text (record 081).

Before sign-up opens to strangers (stage 5), the founder decides whether to commission an independent security review (T-181). My advice at that point will be yes, because that is when strangers' data and money arrive.
