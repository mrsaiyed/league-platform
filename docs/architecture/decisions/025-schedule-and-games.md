# 025 — The schedule and games in the database

Date: 2026-11-13. Step 2.3; serves T3 §8 and §12, S-1, S-4, S-7, S-21, A-6, A-8, A-9 and T-40 to T-47, T-220. Decided by the lead (technical). T-237.

## Problem

T3 §8 lists the columns of `rounds`, `stages`, `games`, `schedule_drafts`, `schedule_revisions`, `game_assignments` and `game_corrections`, and §12 says a game's two teams differ and are of its season, and that a final game has both scores and a scheduled one none. It does not say what the other statuses allow, whether the winner is typed or worked out, what `format` holds and when it may change, which of these tables are history, how S-7's "every correction is logged" is kept by the database, what the recording modes are called, or which rows go to the bin. Migration 0009 needed answers.

## What

- **A game's place.** A game names its season, its stage (required), and optionally a division, a round, a venue and a court. Each link includes the season or venue as well as the league (T-40), so the database refuses a stage, round, division or team of another season, and a court that is not at the game's venue. A court needs its venue named, because a foreign key with an empty column checks nothing. The division is the one whose standings the game counts in; empty is a game across divisions (P7 §4.1). Both teams are required and different; a bracket game whose teams are not known yet will relax that when brackets come (S-4).
- **Scores fit the status.** Scheduled, postponed and cancelled games have no score. Final and forfeited games have both scores and `finalized_at`, and only they have `finalized_at`. A live game has both scores or neither (the tracker keeps the running score there). Scores are 0 to 999. A forfeit has a winner, so its scores differ. Ties are not refused: whether the season allows them is in its rules document, which the results command checks (step 2.23), and a level final game is reported as a tie (T3 §9).
- **The winner is worked out, never typed.** `winner_team_id` is a generated column: the team with the higher score of a final or forfeited game, empty otherwise and for level scores. It can never disagree with the scores.
- **Recording modes are spelled as T3 says.** `capture_mode` is `final`, `box` or `live`, as T3 and the statistics code (`packages/sports/src/stats`, step 2.8) already spell them. The season rules document (`RecordingMode`, step 2.5) says `final-score` and `box-score`; the commands that make games from a season's rules (steps 2.20, 2.21) translate. It has no default: the season's rules give it.
- **`format` is the rules a game is played under.** Empty while the game follows its season's rules; set when the game is given its own rules before it starts (S-21) or when it starts. It is a small versioned document (T-50) whose shape the step that starts games defines. A live, final or forfeited game always has its format (`games_format_when_started`), so the step that starts a game copies the season's rules onto it as it goes live (step 2.20) and a decided game always says which rules it was played under. Once a game has first gone live or been decided, its format cannot change (`games_format_fixed_once_started`, S-1: a game keeps the rules it was played under), even if it later goes back to scheduled or is postponed, so a game cannot be stepped back to change its rules and then restarted. `format_fixed_at` records when that first happened; the database sets it (`games_stamp_format_fixed`) and never clears it, and a value the caller gives is ignored. A game that never started (scheduled, or postponed or cancelled before it began) can still be given its own rules (S-21). The scorekeeper's changes at the table, such as switching the running clock, are plays, not changes to the format.
- **S-7 is kept by the database.** Changing a decided (final or forfeited) game's result needs a `game_corrections` row for that game written in the same transaction, before or after the change. A deferred constraint trigger checks at commit (`games_result_change_needs_correction`). It finds the correction by its time: a correction's `at` is always set by the database to the transaction's time, so the caller cannot backdate one, and an older correction never counts. The result is more than the scores: the status, either score, either team (a swap of home and away included), the division and stage (where the result counts), `finalized_at` (when it was decided, which the public page shows), and whether it is in the bin, both ways: taking a decided game back out of the bin puts a result back into the standings, so it needs a correction just as binning it does. Deciding a game (live or scheduled to final or forfeit) and changing what is not its result (time, place, round, recording mode) need none.
- **Corrections and schedule revisions are history.** Neither is ever changed or removed (T-45): their triggers refuse it even for the tables' owner, and the app has SELECT and INSERT only. `purge_league_history` (record 007) now also removes them, and the league's schedule drafts first, since a draft names a revision. A correction holds who (`account_id`, required), why (1 to 1000 characters) and the result before and after as small versioned documents with ids and numbers only, never names (T-220). The reason is never shown publicly (S-7).
- **Schedule revisions are numbered 1, 2, 3 in their season.** Revision n needs revision n − 1 of the same season, and a number is taken once, so two publications from the same revision cannot both succeed (step 2.21). The check looks only for a row that is never removed, so it takes no lock and holds at every isolation level: a snapshot too old to see the previous revision refuses rather than letting one through. `published_by` is `published_by_account_id`, empty for a publication the system made, like the activity log's actor.
- **One draft per season, based on a revision of that season.** `based_on_revision` is a foreign key to the season's revision number, empty before the first publication. `changes` is a versioned document of at most a megabyte, so a whole generated season fits. `version` stops two admins overwriting each other (A-8).
- **One regular-season stage per season, for now.** `stages.type` takes only `regular` until the playoffs migration adds brackets and `bracket_slots`; `config` is a small versioned document. A stage keeps its season and type.
- **Rounds** are numbered 1 to 1000, each number once in a season, with an optional label and date.
- **What goes to the bin.** Games have `deleted_at` (publishing removes games to the bin, step 2.21) and the app has no DELETE on games, so a decided game cannot be removed past the correction rule; removing binned games for good (T-51) is the purge's work, as for leagues. Rounds, stages, drafts and assignments are not binned: a draft is discarded by removing it, an assignment by removing it, and a round or stage that a game names (even a binned one) stays. Game numbers and outside references are unique in a season while not in the bin, because the fixture import matches by them (steps 2.10, 2.22).
- **Assignments** put an account on a game of the same league once. Whether the account still holds a scorekeeper role is the access module's question, since roles change.
- **No lock-then-look triggers.** Nothing in 0009 takes a lock and then looks, so nothing is refused under REPEATABLE READ or SERIALIZABLE: the correction check reads only rows its own transaction wrote, and the revision order check reads only rows that never go away. Tests run both at those levels.

## Considered

- **A typed `winner_team_id` with a check.** Two places for one fact; the generated column cannot drift.
- **Leaving S-7 to the results commands.** A bug in any later command (publishing, import, the Al-Hadi transfer) could then change a result with no trace. The deferred check costs one indexed look per change of a decided game.
- **Finding the correction by transaction id (`xmin`).** Savepoints give rows their own transaction ids, so it would miss corrections written inside one.
- **The season rules' words (`final-score`, `box-score`).** One spelling with the rules document, but a different one from T3 and the statistics code already built, which may not be changed here.
- **Refusing a tie the season does not allow.** That reads the rules document, and T3 §9 counts such a game as a tie and reports it, so the command refuses and the database stays out of it.
- **Binning rounds and stages.** Nothing restores them on their own; the game rows that need them keep them.

## Revisit if

Brackets need games with teams not yet known, a league needs scores above 999, a game must change rules after it starts other than by plays, a correction must be made by the system rather than a person, or removing binned games for good is built (then decide who may delete a game).
