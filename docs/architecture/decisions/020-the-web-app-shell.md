# 020 — The web app shell

Date: 2026-11-13. Step 1.17; carries out T-3, T-25, T-30, T-34, T-60, U-6 and U-9 in the web app; decides T-232. Decided by the lead (technical).

## What

- **Next.js 16.4.3 with React 19.3.1**, exact versions (`@types/react` 19.3.0), App Router, built with Turbopack, in `apps/web` with the folders of T2 §4. 16.4 is the current line. 16.4.3 (published 2026-10-23) is its newest release at least two weeks old on 2026-11-13; 16.4.4 to 16.4.6 are newer than that, and a release is given two weeks for problems to surface before we take it. `npm run dev:web`, `build:web` and `start:web` run it through `scripts/web.mjs`.
- **Next.js's anonymous usage reporting is off only through the repository's scripts** (`scripts/web.mjs` and `scripts/check-web-shell.mjs` set `NEXT_TELEMETRY_DISABLED=1`). Anything that runs Next.js another way, CI (step 1.23) and the hosting, must set `NEXT_TELEMETRY_DISABLED=1` itself.
- **Settings come from the environment, and `dev:web` and `start:web` also read the root `.env`**, the one file the tracker's scripts share (`node --env-file-if-exists=.env`). The web app's settings are listed in `.env.example`; a value meant for the tracker there is seen by the web app too, and the reverse. `build:web` reads none: the build needs no settings.
- **The build does not start the app.** `next build` loads the app to collect its pages and calls `instrumentation.ts` too; `register()` returns at once when `config.ts`'s `isBuildPhase()` says so (`NEXT_PHASE` is `phase-production-build`, read in `config.ts`, the one file that reads the environment, T-30). So `npm run build:web` works with no settings at all, and settings are checked when the server starts.
- **Types are checked by the gate, not by Next.js.** The repository uses TypeScript 7, which has no JavaScript interface for Next.js's own check, so `typescript.ignoreBuildErrors` is on and `npm run typecheck` checks `apps/web/tsconfig.json` instead. That file resolves imports as a bundler does (`moduleResolution: Bundler`), because Next.js's `next/navigation` and friends have no package export map.
- **The address as it arrived.** Next.js hands pages the address already decoded, but `context.ts` must see it as it came (capitals, `%2D`, U-7). `src/proxy.ts` runs before every page and writes the raw path and query into the request header `x-srleagues-path`, overwriting any header of that name the browser sent; `server/request-facts.ts` reads it with the Host and the session cookie (`srl_session`, which step 1.14 sets). The proxy runs for every address but `/_next/static/`, `/_next/image` and exactly `/favicon.ico` (an unanchored `favicon.ico` also skipped `/faviconXico`, whose pages would then have believed a header the browser sent). And the pages fail closed: every league page and layout passes the route's `[league]` value to `loadLeaguePage`/`leagueView`, and if the league part of the proxy's address (decoded, capitals ignored) is not that value, the proxy did not run, and the answer is "not found" (`addressMatchesRoute`).
- **One answer per request, then one per page** (`server/league-gate.ts`). The request is worked out once: its context, and what the signed-in person holds in the league, read by the access module's own `myAccess` query (one request id for everything done for it, the access read for a forwarded former name included; one read; React `cache`). Each page then gets its answer: shown, not found (404), forwarded (308) or "you do not have access" (403). The 403 is Next.js's `forbidden()` with its `authInterrupts` setting, and `app/forbidden.tsx` says it.
- **Pages refuse; layouts do not.** Every page calls `loadLeaguePage`, because Next.js does not draw a layout again when moving between pages under it, so a check only in a layout could be passed by. Layouts call `leagueView`, which never refuses: when the page may not be shown they draw only the page, whose refusal replaces them, so nothing of the league (its notice, the admin's navigation) is drawn for someone refused.
- **A refused page is filled in by the browser.** Next.js 16.4 answers `notFound()` and `forbidden()` with the right status (404, 403) and a near-empty page that its script fills with `not-found.tsx` or `forbidden.tsx`; it does so for the simplest page too, with or without `authInterrupts` (tried while building this). An address that matches no page at all is drawn by the server. Without scripts, a refused page is blank but keeps its status and `noindex`.
- **What is shown to whom** is core's, as data: `openAdminAreas` (the areas a person's roles use, at any scope, P4 §3–4) and `mayOpenLeague` (U-9) in the leagues module. The admin's navigation lists only the open areas. Any address under the admin, or the tracker, without access is "you do not have access", signed in or not (U-6); a draft league is "not found" to everyone without an admin area in it, a suspended league to everyone but its owner and admins, and so is a former short name of either (step 2.87).
- **Since step 2.87, everyone with an admin area in a draft league sees it** (U-9, decided for the founder on 2026-11-13): `maySeeDraftLeague` asks for any area of the admin (`openAdminAreas(holder).length > 0`), at any scope, so the owner, admins, schedulers, registrars, editors, scorekeepers and club admins can prepare before launch; coaches and captains, who have no admin area, see the league once it is published. The holder is read by `myAccess` inside the league's own fence, so a role in another league counts for nothing. A suspended league stays as below (`maySeeSuspendedLeague`), for exporting data. What this record first said: **U-9's "Draft: only admins can see it" is read literally**: the owner, and those who hold `league.settings` for the whole league, which is the admin role (`maySeeHiddenLeague`). An admin of one program only, schedulers, registrars, editors, scorekeepers, club admins, coaches and captains see the league once it is published; until then it is "not found" to them, admin addresses included. The wider reading, letting every role that works in the admin see a draft (so a scheduler can build the schedule before launch), is a product decision and the founder's call; it is not taken here. Taking it is a one-line change to `maySeeHiddenLeague`.
- **Startup** (`server/startup.ts`, run by `src/instrumentation.ts` before the server serves anyone). Settings are checked (T-30). `APP_ENV` local or test runs on a made-up stand-in (`server/stand-in-ports.ts`: leagues in every state (two drafts since step 2.87), made-up people for every staff role, no database, no sign-in service), which refuses to be made for anything else. Staging and production open `DATABASE_URL` and call `checkLoginRole` first (T-60), stopping on any problem; then they stop anyway, with a plain reason, until sign-in on the real service is wired (steps 1.14 and 1.15). Until then a made-up person is "signed in" when the session cookie holds one of the stand-in's made-up tokens.
- **The database package is loaded by Node.js, not bundled.** `container.ts` loads `@srleagues/database` at run time, past the bundler: Turbopack could not follow the migration runner's folder on disk. Node.js runs the package's TypeScript as it is, as the tracker does, so it may use only syntax that can simply be erased; one constructor parameter property in `guarded-dialect.ts` became a plain field.
- **The check against the built server** is `npm run test:web` (`scripts/check-web-shell.mjs`): it builds, starts the server on the stand-in, asks addresses as the made-up people and checks the status, the refusal made, the words and the forwards, checks that a browser-sent address header is not believed, and checks that staging with a database that answers nobody refuses to start without printing the address. It also checks the security headers, and sends a forged address header at addresses that look like the icon. It is part of `npm run verify`, after the unit tests; building takes a minute or two.
- **Security headers on every answer** (`next.config.ts`, `headers()`): `X-Frame-Options: DENY` and `Content-Security-Policy: frame-ancestors 'none'` (no page in another site's frame), `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin` (stricter than `no-referrer-when-downgrade`: other sites learn only our origin), and a `Permissions-Policy` that switches off camera, microphone, location, payment and USB. Addresses under `/{league}/invitation/` send `Referrer-Policy: no-referrer`, because an invitation's address holds its secret (record 023). A full content security policy for scripts waits for the pages that need one.
- **Our own pages' addresses** (`/signin`, `/account`...) are built by `platformUrl` in the leagues module, beside `leagueUrl` (T-34), so moving leagues to their own hosts later changes one file.
- **The stand-in refuses a real site address.** Besides `APP_ENV` local or test, it refuses unless `PUBLIC_BASE_URL`'s host is `localhost`, `127.0.0.1`, `[::1]` or ends in `.localhost` or `.test`, so a wrong `APP_ENV` on a real server cannot hand out the made-up sign-ins.
- **Next.js also builds `instrumentation.ts` for its Edge runtime** and warns that `process.exit` and `node:crypto` are not there. Nothing here runs on Edge; the warnings are left rather than reading `NEXT_RUNTIME` outside `config.ts` (T-30).

## Considered

- **Next.js 15.** Still patched, but the repository's own Next.js experiment (`apps/varsity-hosted`) is on 16 and new work should not start a major version behind.
- **Reading the league from the route's `[league]` value.** Already decoded, so `%2D` and other spellings could not be forwarded (record 017); and `context.ts` would no longer be the one place an address becomes a league.
- **Checking access in the layouts only.** Simpler, and wrong: layouts are not drawn again on moving between pages.
- **Rendering "you do not have access" as an ordinary page with status 200.** Simpler than `forbidden()`, but tools, tests and search engines would read it as a page that exists.
- **Running local work on PGlite with the migrations and seeds.** Closer to production, but the seeds are step 1.21 and PGlite runs as a superuser, which `checkLoginRole` rightly refuses. The stand-in answers through the same `myAccess` query.
- **Keeping the build out of the gate.** Faster, but the checks against the built server are the only ones that see the proxy, the headers and Next.js's refusals; they are in `verify`.
- **Next.js 16.4.6, the newest patch.** Published four days before this record; we wait two weeks before taking a release.

## Revisit if

- Next.js makes `forbidden()` stable, draws refused pages on the server again, or changes `proxy.ts` again.
- TypeScript 7 gains the interface Next.js's own check needs.
- Sign-in arrives (1.14, 1.15): `identify` moves to the sign-in service, staging and production get their database ports, and renewing a session replaces "draw it as for a visitor".
- The founder wants a draft league seen by fewer or more people than those with an admin area (U-9, step 2.87): change `maySeeDraftLeague`, and the draft cases in `league-visibility.test.ts`, `league-gate.test.ts` and `scripts/check-web-shell.mjs`.
- The invitation page is built for a draft league: someone invited before launch holds no grant until they accept, so `mayOpenLeague` would answer "not found" for them. The step that builds that page must let the holder of a valid invitation reach it in a hidden league, without opening anything else of the league to them.
- The live-updates authorize hook is wired (record 021): it must call `mayOpenLeague` with the subscriber's access in that league, so a draft or suspended league's live scores reach no one who may not see the league.
- A newer Next.js release has been out two weeks.
