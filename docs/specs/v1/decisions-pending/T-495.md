## T4 — Keeping leagues apart, sign-in, security

| T-495 | Nothing that no migration made may hang on what the migrations made (step 2.112, second fix round; `check-hanging.ts`). Both starts, the website's and the worker's, refuse by name: (a) a foreign key from a relation no migration made to one they made, in any schema, `pgboss` included, mended by `alter table … drop constraint …` as the table's owner (no row is lost); (b) a REFERENCES or TRIGGER right, on the table or a column, on a relation the migrations made, held by anyone but its owner (no migration grants either), mended by `revoke references, trigger on table … from … cascade`; (c) a USAGE or CREATE right on a schema the migrations made held by `queue_owner` or by a role only the worker's login reaches (not `app_user`, `sign_in_store` or a role they reach; the migrations grant their schemas to those two alone), mended by `revoke usage, create on schema … from … cascade` as the schema's owner. And a second wall in the fence's (c'): a foreign key's action (cascade, set null, set default) is followed from every relation the login or a role it reaches may change, to any depth, and the security-definer functions that triggers run on every relation reached that way are reviewed, whether or not the login may run them. Technical, decided by the lead (the fix-2 brief), built by the builder: the confirming look made the website's own delete of a code request write queued jobs through a cascade into a definer trigger, and both starts passed. | Agreed (delegated) | |
