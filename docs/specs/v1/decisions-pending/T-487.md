## T4 — Keeping leagues apart, sign-in, security

| T-487 | A fresh answer wins for names on the scorer's device (step 2.226, the review's High). When the device fetches a game's rosters fresh, their names replace the stored names of every player the server knows, in the stored rosters and on the screen at once (`freshOverKept`); the copy kept before is laid over only for a player the server does not know yet (added at the table, its change still waiting, step 2.118), never for a name. The rosters are fetched at every opening (a reload included), and while a game is open when the network comes back, on taking over, after a loss or a refused change of players, and once opening is answered after the device scored from its kept copy. The service worker replaces its kept page of a game whenever it fetched that page fresh for the same account, same release or not; a page of another release replaces it only once every code file the page names is kept too, else the kept page stays until the next fetch. So after an admin switches "Scorekeepers see full names" off, or a person's own request becomes "removed", a device with signal holds the old name no longer than its next fetch, at the latest its next opening or reload (the browser check: within 15 s of a reload). A device with no signal keeps what it has until it has signal: it cannot be otherwise. Found while building it: the opening's wrapper (`markingOnAnswer`) dropped the rosters fetch, so the real tracker never fetched rosters fresh; it passes it through now. How taps are kept, sent and counted is unchanged | Agreed (delegated) | |
