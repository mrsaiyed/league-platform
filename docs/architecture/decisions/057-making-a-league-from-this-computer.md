## Problem

T10 line 31 promises "leagues created by an internal tool" and P3 §8 says we make each league ourselves with an internal version of the four steps until self-serve sign-up. The commands existed (`createLeague`, `createSeason`, `setCurrentSeason`), but only the seed called them, so the demo league and Faraj's could not be put on a platform database. Three things were missing:

1. **Something to run**, which shows what it will make and asks first.
2. **An owner who has no account yet.** `createLeague` needs the owner's account id; an organizer we set up by hand has not signed up.
3. **The city.** P3 §1 step 2 asks "Where": a city and a time zone. The leagues table had the time zone and the contact email, not the city; `createLeague` took neither the contact email nor the city.

## What

- **`npm run league:make`** (`scripts/make-league.mjs`, words in `scripts/make-league.messages.mjs`) takes the league's name, short name, sport, who plays, whether it is listed (`--listed yes|no`), city, time zone, contact email, the owner's email, the first season's name and its rough dates (`--season-starts`, `--season-ends`, both optional: P3 §1 step 4) and `--as`, the email of the member of our staff running it. Anything not given is asked for; the time zone defaults to the computer's, the sport to basketball, and the season's name is suggested from today's date **in the league's own time zone**: "Fall 2026", and for a winter, which runs from December into the next year, both years, "Winter 2026–2027". It shows the whole plan, with where it will make it, and makes nothing unless `yes` is typed at a terminal (on a hosted database, the league's short name): no option, setting or pipe skips the question, and Ctrl+C at any question stops it with nothing made. Whatever goes wrong, it says in plain words what was and was not made, prints no error message (one could repeat an address with its login), and exits with a code other than 0.
- **Checking the answers is core's** (`planNewLeague` in `packages/core/src/modules/leagues/rules/new-league-plan.ts`): every problem is told at once; the short name follows U-7 and the blocked list; the owner's and the staff member's emails are both checked there and both refused on `.invalid`; the dates must be real days written YYYY-MM-DD, the end not before the start; the time zone must be a named zone the runtime knows (`namedTimeZone`, `time-zone.ts`), kept by its canonical name, because PostgreSQL reads an offset such as `+05:00` in `at time zone` with the opposite sign and an abbreviation such as EST is ambiguous. "Who plays" maps adults, under-18s and both to adult, youth and mixed; the plan says what follows (names shortened to first name and last initial on public pages for under-18s until the admin changes that, R-14; listed in `/find` by U-10's default unless `--listed` chooses) and that there is no screen to change "who plays" afterwards yet. The commands check everything again.
- **Local unless told otherwise** (`scripts/make-league-source.mjs`). With no `--hosted` it uses a PGlite folder on this computer, `--db <folder>` (which must already hold a database; the tool never makes one) or the local test database in `.local/seed-db`, even when hosted settings are in the environment or `.env`: it says it is not using them. `--hosted` needs a terminal (with none it opens no connection at all, not even to read), both logins given for that one command and never named in `.env` (refused if they are), and the question is answered by typing the league's short name, not "yes".
- **The wrong database** (H-A). Before anything connects, both addresses go through the tracker's database guard in `packages/providers` (`platformDatabaseProblem`, record 055), the same one the web app and the worker run, with the tracker's project from `supabase/site.json` (`trackerProjectFor`): the tracker's project in any spelling, the tracker's `DATABASE_URL`, an address that takes its host, port, user, password, options or database name from its query string, an IP address, and a host or user left to `PGHOST` and the like are all refused, and so is any address when `site.json` cannot be read. The guard gained one optional fact for this, `hosted`, so a tool with no `APP_ENV` is as strict as production, and one helper, `addressOnThisComputer`. After connecting, the first thing each login reads is whether the database holds the tracker's own schema, `live_stats`; if so it is refused, whatever the address said. The two logins must reach the same database (its name, its id in the cluster, the server's start time).
- **Where, as connected** (`openLeagueMakingTarget`, the one place the target is opened and described). The plan's "Where" line is built from the migration login's real connection: the host and port it went to and the server's own `current_database()`, never the address's guess; the Supabase project reference when the connection names one (it is public); and "NOT on this computer" for a hosted database elsewhere. Never the user name or the password.
- **The certificate** (L2). For a database not on this computer the connection must check the server's certificate: `MIGRATION_DATABASE_SSL` `verify` (the default) with `MIGRATION_DATABASE_CA`, the server's certificate file, for both logins; `off`, `no-verify` or no file is refused before connecting, by the script and again by `openLeagueMakingTarget`. A failed connection names the login and the likely cause, read from the error's code (the user name or password, the database name, the host, the network, the certificate file, the SSL setting), then the usual causes, never the address.
- **Two logins, each doing only what it must** (H-B, decided by the lead). On a hosted database the app's own restricted login, `PLATFORM_DATABASE_URL` (the one the web app uses), runs every command, through the league fence, exactly as the web app would; the migration login, `MIGRATION_DATABASE_URL`, is used only for what nothing else can do: reading the migration log and the accounts by email (accounts force row-level security, so only a login that bypasses it finds one) and adding or removing an account (`app_user` may do neither, 0005 and 0012). The product's invitation path cannot stand in for it: an invitation gives an existing account a role when it is accepted, but cannot make an account, and `createLeague` needs the owner's account id at once. On this computer one PGlite does both.
- **The logins are asked first** (`probe-logins.ts`), before the plan is shown and again before anything is made: the app's login must pass `checkLoginRole` (T-60) and really switch to `app_user` in a transaction; the migration login must see past the accounts' fence, may read, add and remove accounts, may read the migration log and may call `find_league_by_slug` and `uuid_v7`. Each refusal says in plain words what is wrong and which login to use instead, and nothing is made. Before this, a migration login that could not `set role app_user` would have made the accounts and then failed after "yes" with only a code. On Supabase the app's login, and `postgres` as the migration login, are expected to pass; not verified.
- **T-260: accounts made ahead, by email; then the league and its first season in one transaction, by our staff** (`makeLeague` in `packages/database/src/league-making/`):
  1. It asks the logins (above), then compares the database's migration log with this code's migrations folder (`migration-state.ts`) and refuses, in plain words, a database with none applied, one behind this code ("apply the migrations first"), one ahead of it, and one whose applied files differ. Then it checks no league holds the short name or still forwards from it (`find_league_by_slug`). Either refusal makes nothing, not even an account.
  2. It finds the staff member's and the owner's accounts by email, whatever the capitals, and makes any that is missing with no name and no sign-in link, under the same per-address lock `account_for_sign_in` takes. That account waits to be claimed: the owner's first sign-in with that email, once the sign-in service has proved they hold the mailbox, links it (record 052), so whoever first signs in with it owns the league (the owner is `leagues.owner_account_id`, not a grant, O-7). Whether someone "has signed up" is read from the account's sign-in link (`sign_in_id`), never from whether this run made the row: an account a run made earlier that nobody has signed in with is shown as such.
  3. `createLeague`, as our staff, with the first season: the league, its default program and its first season, as the current one, in **one transaction**, so either everything is made or nothing is. The staff member is named as platform staff for this run only, in memory (`leaguesStore`'s `platformStaff`), writes no grant, and holds nothing in the league afterwards (T-77). The activity log names our staff for the league and for its first season, with `forOwnerAccountId` in the details to say it was set up for the owner. **Nothing is done as the owner**: no command context is made for a person who has not signed in.
  - The accounts of step 2 cannot share step 3's transaction: they are written by the migration login on its own connection, outside the league's fence, while the commands run as `app_user`, which may not add an account. So when no league is made (refused, or stopped by anything unexpected and the league is surely not there), the accounts **this run** made are removed again, each only while nobody has signed in with it and nothing uses it; an account that was there before is never touched. One that cannot be removed is named, with its id and how to remove it; it does no harm, and a later run with the same email uses it. If something unexpected stops the run after the league was made, the league is whole (one transaction) and the tool says so with its id.
- **The seed** makes its leagues' seasons the same way (`createLeague` with `firstSeason`), so the seed's seasons are now current.
- **Migration 0014** adds `leagues.city` (text, empty until given, 1 to 100 characters with no spaces around it). `createLeague` now also takes the optional `contactEmail`, `city` and `firstSeason`; T3 §4 lists the column.
