## T4 — Keeping leagues apart, sign-in, security

| T-455 | A waiting change of email lives in our own store, never in the sign-in service (changed after the review of step 2.128 found an account takeover: Supabase found a pending change by address and code, not by session). One row for an account at most: the new address, the code only as its hash (bound to the account and the address), its attempts left and its end (sign_in.email_changes, migration 0031, T-461). Asking again replaces the row, so an older code is dead; a new password ends it too. The interface keeps startEmailChange (access token, current password, new address, network address, whether our own records give the address to another account) and confirmEmailChange (access token, code, network address). Start checks the password as confirmPassword does (the same guesses), then sends a code to the new address under the limits of every code (per address, per network, 10 minutes, 5 attempts); an address our records give another account gets no code, the same answer, and a row whose hash matches no code. Confirm takes one attempt of THIS account's own row, taken from the session; our code checks the code; the sign-in service is told nothing until that check has passed, and is then asked once to set the address of that account's own id (Supabase: the admin user update, confirmed at once; the stand-in the same behind the one interface). The service never looks a change up by address and code. If it then refuses (the address is another account's there), nothing changes anywhere and the person gets the same answer, with about the same work, as for a wrong code: a taken address and a free one are answered alike at every step, the first code typed included. A right code moves the address, ends every other session and keeps this one. Supabase's own email-change flow and its "secure email change" setting are not used. Not yet verified against the live service. | Agreed (delegated) | |
