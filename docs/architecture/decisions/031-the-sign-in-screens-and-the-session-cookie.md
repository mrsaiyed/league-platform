# 031 — The sign-in screens and the session cookie

Date: 2026-11-13. Step 1.14; carries out T-67, T-68, T-69, T-70, T-71, T-85 and T-225 in the web app; decides T-243. Decided by the builder of step 1.14 for the lead (technical), to be confirmed when the step lands.

## What

- **The forms' work is plain functions** (`apps/web/src/server/sign-in/flows.ts`) of the form's fields, the browser's cookies (a small `CookieJar`) and the ports, tested without a server on the sign-in stand-in (`flows.test.ts`). Next.js server actions (`actions.ts`) call them and send the browser where they answer. The forms are plain HTML forms and work with no script; Next.js refuses an action posted from another site (its `Origin` must be ours), so every change comes from our own pages (T4 §5). Google's return (`/signin/google`) is a route of its own.
- **The screens:** `/signin` (email and password, Google, links), `/signup` (email), `/signin/forgot` (email), `/signup/code` and `/signup/password` (shared by sign-up and forgotten password, T-67), `/account` (devices, "sign out", "sign out everywhere", T-71) and `/account/confirm` (the password again, T-70). Their addresses are built by `platformUrl` (T-34); their words are in the message files (T-187).
- **A problem is shown by its name in the address** (`?problem=codeWrong&wait=30`, `problems.ts`), never by anything the person typed. The address being proved and, after the right code, the proof go between the screens in a cookie of their own (`srl_flow`, 15 minutes), so no email address is ever in an address bar.
- **T-68 in the web app:** asking for a code always goes on to "enter your code" with the same cookies; a wrong address and a wrong password are one problem; lock-outs answer alike. The tests compare the answers for an address with an account and one without.
- **The cookies (T-69):** all HttpOnly, `Path=/`, `Secure` when `PUBLIC_BASE_URL` is https (plain http only on this computer), and **`SameSite=Lax`**. T-69 says "not sent on requests started by other websites": Lax keeps them off every request another site starts except a plain link followed to one of our pages. Strict would make every link from an email, a chat or a search open our site signed out, and the one change Lax still lets through (a top-level GET) changes nothing here: every change is a POST, refused unless it came from our pages. `srl_session` holds the access token and runs out 30 seconds before the token does; `srl_renew` holds the renewing token for about 13 months (the longest a browser keeps a cookie) and is set again on every renewal; `srl_device` is the device's own id (T-70), apart from any session; `srl_google` holds Google's verifier for 10 minutes.
- **Renewal is in the proxy** (`src/proxy.ts`, `renew-session.ts`). A request with the renewing token and no session cookie is renewed before any page sees it; the page sees the new token and the browser gets the new cookies. An ended session's cookies are cleared there. No identify call is made in the proxy: the session cookie's own lifetime says when to renew. A token that still fails in a page (it ran out in between, or the session ended elsewhere) is drawn as for a visitor, and the next request renews or clears it.
- **Requests sent at once share one renewal.** The renewing token changes on every use and the stand-in allows no reuse (T-69), but a browser sends a page and what it fetches together, all with the same old token. Renewals of one token are shared, and for 30 seconds a late request with the token just used gets the same new tokens (keyed by a one-way hash, so the map never holds a working token). This is a small reuse window like Supabase's own; it lives in one server's memory, so two servers do not share it.
- **Signing in again on a device ends the session it had,** so the device list does not grow with old sessions.
- **The emails (T4 §3):** the code, the new-device notice (T-70; not sent for a brand-new account) and the password-changed notice (T-85) are drawn by `packages/emails` (`sign-in-emails.ts`) and handed to the email interface (`sign-in-mail.ts`). A reset asked for an address with no account sends nothing. A notice that cannot be sent never undoes the sign-in.
- **The password again (T-70):** `needsPasswordAgain` (an hour since the password was typed; for an account with no password, an hour since a Google sign-in) and `passwordAgainAddress` for the sensitive actions' pages, which come in later steps.
- **The network a request comes from** is the last entry of `X-Forwarded-For` (`networkAddressOf`): the entry written by the nearest server in front of the app. Entries before it are what the browser claimed and are never believed. With no readable address, all such requests share one key (`0.0.0.0`).
- **The web app's stand-in runs the sign-in stand-in** of packages/providers (in memory, emails caught by the email capture). The four made-up people's tokens still work beside it, so the shell's checks can be someone with roles. The sign-in stand-in also refuses `NODE_ENV=production`, but Next.js's built server always sets that, including the test server of `npm run test:web`; the web app's own guards (APP_ENV local or test, and a site address on this computer or a `.test` name) decide instead, and the stand-in is passed the APP_ENV.

## Not done yet, and where it goes

- **Staging and production sign-in.** The Supabase adapter (record 018) is not wired into the web app: it needs the production sign-in store (devices, sessions, attempt counts, proofs; migration 0011 is reserved for it), the sending of sign-in emails on the real email service, and the database ports for staging (startup still refuses staging and production).
- **Sign-in emails through the queue.** For T-68 the cost of asking for a code must be the same whether or not an email is sent. On the stand-in it is (the capture is instant); on the real email service a sent code takes longer than a skipped one. The production wiring should record a job for every request and let the job send nothing (record 013 says so of the code sender).
- **Hosting must put exactly one proxy that appends the real address** in front of the app, or every visitor's guesses are counted against one network (or the browser's own claim). To be checked when hosting is chosen.
- **The shared renewal is per server.** With more than one web server, a renewal race between two servers ends the session; the production store (or the vendor's own window) has to cover it.
- **Reading the codes in local work.** The stand-in's emails are kept in memory only; a developer cannot yet read a code on this computer. A folder for the capture (it can write files) or a local email page is a small follow-up.
- **The header's account button** (P6 §6) still says "Sign in" for everyone; it comes with the member pages.
- **A bot check in front of sign-in** (T4 §6) is not built.
