# 055 — The web app on the database, part 1: its own setting, the made-up database, and who the signed-in person is

Date: 2026-11-14. Step 2.93 part 1; answers Stage 1 report finding R8 and carries out record 052's "wiring" for the requests every page makes; serves T2 §4, T-30, T-60, T-201, T-256. Decided by the builder of step 2.93 for the lead (technical), to be confirmed when the step lands.

**Not verified against a real PostgreSQL server or Supabase.** Everything below runs on the made-up database (PGlite) only.

## Problem

The web app's every page reads through `WebPorts` (`apps/web/src/server/ports.ts`), and only the made-up stand-in filled them (finding R1). Step 2.93 moves them onto the database area by area, which needs a way to run the app on a database before every area has moved. Two settings traps stood in the way too (R8): the web app read the tracker's setting name `DATABASE_URL`, and demanded a session secret and two Stripe keys nothing used.

## What

- **The platform's database is `PLATFORM_DATABASE_URL`** in the web app and the worker, never `DATABASE_URL`, which stays the tracker's. A settings file made for one cannot point the other at its database; a test in each app checks that `DATABASE_URL` is ignored.
- **The tracker's database guard.** Both apps' settings checks run one guard (`packages/providers/src/platform-database`) before anything connects, so neither the web app nor the worker can open the tracker's live database, whatever its settings say. It lives in packages/providers because both apps use that package and Next.js bundles it; packages/database is loaded by the web app only at run time (container.ts), so the settings check cannot import it, and the pure layers may not use the parser. The guard reads `PLATFORM_DATABASE_URL` with pg-connection-string, the parser `pg` uses, after the same change packages/database makes (the ssl settings taken out), so it checks the host, user, database and options the connection would really use, decoded. It refuses: the tracker's `DATABASE_URL`, also written another way (the same host, port, user and database); the tracker's Supabase project anywhere in the decoded host, user, database or options or in the text (percent-encoded, in capitals, in Unicode look-alikes); a host, port, user, password, options or database name taken from the query string; a host or user that is not plain ASCII; in staging and production, an IP address as the host (no name check can tell it from the tracker's; the system's old numeric forms such as `2130706433` count), and an address that leaves its host, port, user or database to `PGHOST`, `PGPORT`, `PGUSER` or `PGDATABASE` in the environment, or any `PGOPTIONS` there. `SUPABASE_URL` (web app) is checked against `DATABASE_URL` and the project, its host decoded as the browser's URL parser decodes it. Every refusal names the setting and a fixed reason, never the address or any part of it.
- **Where `supabase/site.json` is found.** The tracker's project reference comes from the repository's own `supabase/site.json` (a file read, no network), found from each app's `config.ts` file itself (`trackerProjectFor(import.meta.url)`): the first folder above it whose `package.json` lists the workspaces is the repository, and only its `supabase/site.json` counts, never one in the working folder or nearer the code. In staging and production, a `site.json` that is not there, cannot be read or names no Supabase project stops the start, in both apps. **A deployment of the web app or the worker must therefore ship `supabase/site.json` and the root `package.json` beside the code**, as a checkout of the repository does.
- `PLATFORM_DATABASE_URL` is required in staging and production only, as are `SUPABASE_URL` and `SUPABASE_SECRET_KEY`; `RESEND_API_KEY` in production only. `SESSION_SECRET`, `STRIPE_SECRET_KEY` and `STRIPE_WEBHOOK_SECRET` are optional until the step that first uses them makes them required where used; given now, they are still checked.
- **`LOCAL_DATA`** (local and test only; set anywhere else, the app refuses to start) chooses what local work runs on: `stand-in` (the default, unchanged) or `made-up-database`, the made-up database in memory that the worker already uses (`madeUpDatabase`: every migration, the seed leagues, a login that is a member of `app_user` and nothing more). Its login role is checked at start as a hosted one is (T-60). People sign in on the same sign-in stand-in as before (`standInSignIn`, split out of `stand-in-ports.ts` with its refusals), and the made-up member is made the same way. The stand-in's made-up people and their tokens do not exist there.
- **`databasePorts`** (`apps/web/src/server/database-ports.ts`) fills `WebPorts` from the database. Moved in this part: finding a league by its short name (`findLeagueByShortName`, no league set) and by its id (`findCurrentLeague`, that league set), who the signed-in person is, and what they hold in a league (`myAccess` over `accessStore`, the same code the stand-in answers through). packages/database is handed in, not imported, so Next.js never bundles it (container.ts).
- **Who the signed-in person is** (record 052, T-256): `identify` asks the sign-in service, whose `accountId` is its own user id, then turns that into our account id: `findAccountOfSignIn` for a user seen before, else `accountForSignIn` with the email the service holds for the session. That is the app's only call of `accountForSignIn`. It is safe there because the service has just proved the session, and it makes a session only after proving the mailbox (a right code, Google or a right password); the email never comes from the request. It is called only when the service also says the address is confirmed (`emailConfirmed` on the session's identity: Supabase's `email_confirmed_at`, kept by the providers' client; the stand-ins answer true, as every address there was proved): for a user seen for the first time whose address is not, nothing is linked or made, and `identify` answers `account-problem` (`address-not-confirmed`). A user already linked keeps their account whatever the service says later. An address whose account is linked to another sign-in user is refused, never answered with that account: `identify` answers `account-problem` (`sign-in-link-conflict`, `isSignInLinkConflict` tells that error from any other) and logs a warning with the sign-in user's id only, for whoever puts it right by hand (record 052). Any other refusal the database gives for linking or making the account (`isSignInRefusal`: SQLSTATE classes 22 and 23, such as an address on `.invalid` or one the accounts' email format refuses) is answered the same way, as `address-refused`; a fault (the database not reached, a lost connection, a missing grant) is still an error. Each warning is written once an hour per sign-in user, not on every request.
- **Only a plain ASCII address is linked or given an account.** `toLowerCase()` and the database's `lower()` fold some other characters into ASCII (the Kelvin sign into k), so two different mailboxes could meet in one account made before its owner signed in. The providers' Supabase client now lower-cases A to Z only, and `identify` passes `accountForSignIn` the address lower-cased as plain ASCII, so a plain ASCII address matches an account only when the two are the same after plain ASCII lower-casing. An address with any other character is refused as `address-refused`, never linked and never given an account of its own: `account_for_sign_in` cannot be asked to make an account without also linking one whose `lower()` matches, so without a migration a refusal is the only answer that never hands over another person's account (record 052 says such an address is put right by hand). **Not closed here:** an account made by hand or by the seed with a non-ASCII address could still be linked by `account_for_sign_in` to the plain ASCII address its `lower()` folds into. Today such accounts are made only by our own staff; closing it means comparing addresses without `lower()` folding inside that function, a migration of its own.
- Every league page then sends the person to the account page, which says plainly what is wrong and still offers to sign out; a league endpoint answers 403 `account-problem`, or treats them as a visitor for a public read.
- **Areas not yet moved refuse.** Each area's ports throw `NotOnTheDatabaseYet` the moment any part of them is reached, so such a page shows the error page, never made-up data that is not in the database. `liveFeed` is null and `publishPlays` refuses until the tracker moves.
- **Staging and production still refuse to start** after the login check and the email confirmation check (step 2.115, [record 018](018-the-supabase-sign-in-adapter.md): the start stops first unless the sign-in service plainly says it confirms addresses), as before: they must not serve until every area has moved. **Since step 2.93's last part** staging serves through the real sign-in service, and production still stops after every check ([record 082](082-how-the-test-copy-starts.md)).

- **A stale address after a change at the service.** Once a sign-in user is linked, `identify` finds their account by the link alone and never compares addresses, and the app may not change `accounts.email` (R9, record 052). So if a person's address changes at the sign-in service, our account keeps the old one. The web app offers no way to change an address today (it sends Supabase only a password change), so this happens only if it is changed at Supabase by hand, until T-73's confirmed change is built. What follows: the person still signs in to the same account, with the same leagues and roles; whatever we send by email goes to the old address; and if someone later proves the old address at the service as a new user, their first sign-in is refused as a link conflict (`sign-in-link-conflict` above), logged with their sign-in user id, and put right by hand (record 052). It is never another person's account. T-73's change, an owner-run function that changes `accounts.email` once the service has confirmed the new address, closes it; until then, an address changed at Supabase by hand is changed in `accounts` by hand too.

## Considered

- **Mixing: the database for what has moved, the stand-in for the rest.** The stand-in's leagues and ids are not the database's, so its pages would show leagues that do not exist next to ones that do.
- **Linking accounts in the sign-in screens, right after each proof** (the code, the password, Google). Three call sites, each to review, and a session renewed or made another way would still need the lookup. `identify` sees every session once, whichever way it began.
- **Turning a link conflict into "signed out".** The person could then never sign in, silently. A plain refusal is seen and put right.
- **Letting the conflict throw** (this part's first version). Every page the person opened, the account page included, was the error page, so they could not even sign out. The same held for every other refusal of the database, until each became `address-refused`.
- **The guard in packages/database**, beside the driver. The web app loads that package only at run time, never bundled (container.ts), so its settings check could not import it; packages/providers is used and bundled by both apps.
- **Giving an address that is not plain ASCII an account of its own.** `account_for_sign_in` cannot be told "make, never link": it links whatever account its `lower()` matches. Only a migration could offer that.
- **Finding `site.json` from the working folder** (this part's first version). Started from another folder, the app could have checked against another file.
